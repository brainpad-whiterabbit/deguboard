# 一気通し（all）

Iteration かチケットを、割り当てからリリースまでの段階で続けて進める。この手順に書くのは、段階の順・今の段階の求め方・段階の間の進み方・文脈の扱いだけ。各段階の手順は、段階に入るときにそのトピックを読んで従い、ここに写さない。

## 対象を決める

- Iteration（`s3`）：その Iteration のチケットと、そこに入れる候補（Iteration に入っていない todo）を扱う。候補を扱うのは割り当ての段階だけで、後の段階の「対象のチケット」はその Iteration に入っているもの
- チケットの ID（1 つ以上）：そのチケットを扱う。見直しとリリースは、チケットの Iteration のチケットがすべて done になったときだけ、その Iteration を対象に行う。Iteration に入っていなければ見直しとリリースはしない
- 指定が空：active の Iteration を勧めて確かめる。なければどれかを聞く
- `--no-assign`：割り当ての段階を飛ばす。点検で Iteration に入れる案が出ても反映せず、終わりの報告に残す
- `--auto`：下の「`--auto` で自動で選ぶ」に従う。`--no-assign` と一緒に指定できる

以下では対象の Iteration を `<S>` と書く。`<S>` が planned なら、始めるときに `iteration start <S>` にするかを聞く（勧める）。

## 段階

| #   | 段階     | 読むトピック                                                               | 止まって承認を求める場所（各手順のとおり）           |
| --- | -------- | -------------------------------------------------------------------------- | ---------------------------------------------------- |
| 1   | 割り当て | `dg guide assign`（`<S>` に入れるか入れないかだけを判断する）              | 入れる行の承認                                       |
| 2   | 点検     | `dg guide check`                                                           | 直す行の承認、削除・abandoned・閉じる操作            |
| 3   | 計画     | `dg guide plan`                                                            | Plan の承認                                          |
| 4   | 作業     | `dg guide work` と、マージのたびに `dg guide done`                         | PR ごとのマージ（人が行うか、人の承認を得て行う）    |
| 5   | 見直し   | `dg guide audit`                                                           | 指摘の表の承認                                       |
| 6   | リリース | `dg guide release`（リポジトリにリリースの手順がなければ `dg guide done`） | リリースの PR のマージ・公開・Iteration を閉じること |

## 今の段階を求める

始めるときと各段階を終えたときに、`dg --json --actor agent sync` の後、`iteration show <S>`・`ticket list`（対象で絞る）・`plan list --status open` と `plan show <p>`・`ticket list --label audit-<S>`（見直し済みか）を読み、次の順で最初に当たるものを今の段階にする。

1. この実行で割り当てを終えておらず、`<S>` が見直し済みでなく、Iteration に入っていない todo（ラベル `audit-<S>` のものを除く）がある（Iteration の指定で、`--no-assign` がないとき）→ 割り当て
2. この実行でまだ点検をしていない → 点検（指摘は状態に残らないので、起動のたびに 1 回）
3. 対象のチケットを含む承認待ちの Plan がある → 計画（その Plan の承認を得る）
4. 対象のチケットを含む承認済みの Plan に、done でないチケットがある → 作業
5. 対象に、開いた Plan に入っていない todo がある → 計画
6. 対象のチケットがすべて done か abandoned で、`<S>` が見直し済みでない → 見直し
7. 対象のチケットがすべて done か abandoned で、`<S>` が見直し済み → リリース
8. どれにも当たらない（PR のない in_progress だけが残る、マージ待ちの review だけが残る、など）→ 状態を示して止まる

- **見直し済み**：ラベル `audit-<S>` のチケットがある（状態と所属は問わない）か、この実行で見直しを終えた。見直しで起票したチケットを進めて done に戻っても、もう一度は見直さずにリリースに進む
- 同じ段階が続けて求められ、状態が変わらない（承認が得られなかった、マージを待っている）ときは、繰り返さずに状態を示して止まる。同じ引数で起動し直せば、状態から段階を求め直して再開する

## 段階の間の進み方

- **段階の間は止まらない**：各段階の手順の終わりの「次の手順を選ぶ」は聞かず、上の求め方で次の段階に進む。求め方で決まらない行き先（流れの外の手順）を勧められたときだけ聞く
- **承認の場所は残す**：上の表と各段階の手順が承認を求める操作は、すべてそのとおりに承認を得る。承認の選択肢には「ここで止める」を入れ、選ばれたらそこまでの結果を報告して止まる
- **作業は記録した Plan から始める**：計画の段階で承認した Plan を `plan show <p>` で読み直してから作業に入る。計画を立てたときの会話には頼らない
- **マージは人が行う**：PR を出したら、マージは人に頼むか承認を得てから行う。マージを待つ間は、Plan のほかの着手できるチケットを進め、なければ止まる。`--auto` で `auto.merge` が true なら、下の「マージの前の条件」を満たした PR だけを自動でマージする

## `--auto` で自動で選ぶ

`--auto` を付けたときは、各段階の手順が承認を求める場面のうち、勧める選択肢があって `dg` で戻せる判断を、聞かずに勧める選択肢で進める。選んだものと判断の材料（表・Plan）はその場で短く示す。`--auto` がなければ、この節は使わない。

- **自動で選ぶ**：
  - 割り当ての承認（入れた行と入れなかった行を理由と一緒に示す）。`<S>` を始めること（`iteration start`）
  - 点検の直す行のうち、直し方が 1 つに決まる本文とフィールドの修正
  - Plan の承認（`plan approve`。`approved_by` は agent になる）
  - 見直しの指摘の表の承認（勧める置き場のまま、「直さない」以外の行を反映する）
  - 照合の後の受け入れ条件の確認と `ticket check`
  - PR のマージ：`auto.merge` が true（今の設定：`{{auto.merge}}`）のときだけ、PR ごとに下の「マージの前の条件」をすべて確かめてから `dg guide done` の手順まで進める。1 つでも満たさなければその PR はマージせず、満たさなかった条件を示して承認を求めて止まる
- **自動にしない（承認を求めて止まる）**：
  - `auto.merge` が false のときのマージ。リリースの PR のマージと公開の操作（タグ・配布先）は `auto.merge` によらず聞く
  - チケットの削除・abandoned、Epic・Iteration・Plan を閉じる・再開する
  - Plan の待ち（`after`）と範囲を変えること、`--force` の付く操作
  - 勧めるものがない判断と、選択肢にできない答え（修正の中身）
- 失敗したチケット（検査が通らない、範囲がはっきりしない）は `ticket unclaim` で todo に戻し、worktree は調べられるように残して、それを待たないチケットを進める。同じ流れの中で claim し直さない
- 自動にするのは戻せる判断と、チームが `auto.merge` で明示したマージだけ。戻しにくい操作の前には人の判断を残す

### マージの前の条件

- **検査が通る**：リポジトリの規約にある検査（書式・lint・テスト）が、PR のブランチの最新のコミットで通る。CI があれば CI も通っている
- **受け入れ条件がすべてチェック済み**：`ticket show <id>` の `acceptance` がすべて `checked`
- **別のサブエージェントの見直しで重い指摘がない**：実装したのとは別のサブエージェントに、チケットの本文と PR の差分（`git diff {{git.remote}}/{{git.base_branch}}...<ブランチ>`）を渡して見直させる。受け入れ条件の漏れ・不具合・文書との食い違いが残っていない。直したら上の 2 つを確かめ直す
- **base と衝突しない**：`gh pr view <PR> --json mergeable` が `MERGEABLE`

マージはリポジトリの規約のマージの手順（squash か、ブランチと worktree を消すか）に従う。

## 文脈の扱い

この手順を進めるセッション（親）は、段階の進行・承認・`dg` の読み書きだけを行う。チケットの実装は、件数にかかわらずチケットごとにサブエージェントに任せる。

- **渡すもの**：チケットの ID・Plan の `details` の範囲と方針・claim したブランチと worktree のパス・リポジトリの規約の場所・`dg guide work` の手順 4〜6（実装・受け入れ条件の確認・PR）に従うこと
- **してはいけないこと**：claim・unclaim・Plan の操作・マージ・ほかのチケットの作業
- **返すもの**：PR の URL・確かめた受け入れ条件と付けられなかった項目（理由）・検査の結果・人に伝えること

親は返ったものを読み、`ticket check` と `ticket update --pr` を記録して次に進む。

## 結果を伝える

流れの終わり（リリースか片付けを終えた・止まった）に、段階ごとの結果を伝える。割り当てたチケット・点検で直した行・承認した Plan・出した PR とマージ・見直しで起票したチケット・リリースした版と Iteration の状態・`--no-assign` で反映しなかった割り当ての案・残ったチケットとその状態。`--auto` のときは、自動で選んだ判断の一覧と、自動でマージした PR ごとの条件の確かめの結果も伝える。
