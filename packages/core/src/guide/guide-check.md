# Check (check)

Finds mismatches among tickets, Epics, Iterations, and Plans, and fixes them after approval. What counts as a mismatch is decided by `dg validate` and `dg lint` (for what `lint` flags, see `dg lint --help`). These steps do not decide the criteria. They read the findings and decide how to fix them.

## Deciding the target

- Iteration (`s3`) and Epic (`e3`): targets the tickets in it, and the findings on that Iteration or Epic itself
- Ticket ID: targets the findings on that ticket
- No target given: targets the whole kanban

## Check steps

1. **Collect findings**: run `dg --json --actor agent sync`, `dg --json --actor agent validate`, and `dg --json --actor agent lint` in order. Narrow the `sync` `warnings`, and the `validate` and `lint` `issues` (`code`, `id`, `message`) to the target
2. **Make fix proposals**: for each finding, read the content with `ticket show`, `epic show`, or `plan show` and decide how to fix it. Examples:
   - A section of the body is missing, or the acceptance criteria are empty: make a draft of acceptance criteria from the body (`ticket update --acceptance`). For the summary, pass the whole body with a `## Summary` section added to the current body via `--body` (`--body` replaces the body; dg also reads the Japanese `## 概要`)
   - An unfinished ticket remains in a closed Epic: propose one of moving it to another Epic, removing it from the Epic, or making it abandoned
   - All tickets are finished, but the Epic or Plan is still open: propose closing it (`epic close` / `plan close`)
   - Not in an Iteration (`lint_iteration_missing`, when `lint.require_iteration` is true. Current setting: `{{lint.require_iteration}}`): choose an Iteration by the same rule as claim (see `ticket claim --help`) and propose adding it with `iteration add <S> <id> --approved-by human` (run after the row is approved; the Workflow's `flow.assign` judges it). If there is no place to add it (a closed Iteration cannot take it, as with done tickets, and a ticket in progress or in review goes only into the active one), ask a human whether to create an Iteration or change the setting
   - The open Plan's `after` and `depends_on` form a cycle (`lint_plan_wait_cycle`): propose one of removing the edge with `ticket update --depends-on`, closing the Plan and recreating it with a different `after`, or making the waiting ticket abandoned. Ask a human whether to close the Plan or make the ticket abandoned
   - Two or more active Iterations (`lint_iteration_multiple_active`): ask a human which one to close (the Workflow's `flow.release` judges closing; `dg guide assign`)
   - A ticket in progress or in review is in an Iteration that is not active (`lint_iteration_not_active`): a person decides which Iteration the work goes on in, so ask a human to choose one of the ways out that the message gives (moving the ticket into the active Iteration with `iteration add`, or closing, starting, or reopening an Iteration), and run the chosen one after approval
   - PR is made but there is no implementation Run (`lint_run_implement_missing`): this is a gap in Run recording, so do not fix the ticket. Report it to a human. There is no way to create the Run afterward. The target is unfinished tickets, and done tickets in an Iteration that is not closed
   - A commit after a closed implementation Run is not in any Run's period (`lint_commit_outside_run`), or a commit after review has no fix Run (`lint_run_fix_missing`): do not rewrite the Run record. As the message says, check the content of the commit and tell a human. `lint_run_fix_missing` may be ignored if that commit is not a fix. If one commit raises both `lint_commit_outside_run` and `lint_run_fix_missing`, follow the remedy for `lint_run_fix_missing`
   - `sync` warnings that say reconcile does not advance a ticket (`reconcile does not advance it, because ...`, for the boundary policy or the Iteration rule): this is not a done confirmation. Tell a human the ways out the warning gives (a person's `ticket move` with `--override` where the policy allows it, or the Iteration's ways out), and do not run them. Other `sync` warnings (cannot reconcile, or done with unchecked acceptance criteria left): propose confirming with the steps of `dg guide done`
   - **Overlapping vocabulary of the labels** (when the axes of the labels are on and `lint` gives `lint_label_*` findings): read those findings together with the vocabulary and its descriptions (`dg --json --actor agent label list --undefined`), and judge which labels mean the same thing or overlap: descriptions that say the same in other words, a name that tickets carry but the vocabulary does not have that means a label of the vocabulary, names that differ only in case, and vocabulary that no ticket carries. Propose, for each group, one of: merge (`dg label merge <from>... <to>`, which rewrites every ticket that carries a merged name), rename (a merge into a new name, with `--axis` and `--description`), or remove (`dg label remove <name>`, only for vocabulary that no ticket carries). Put in the fix proposal the number of tickets it rewrites (the sum of `count` of the merged names in `label list`, 0 for a removal). A name that tickets carry but the vocabulary does not have is merged after adding it with `dg label add`, or changed on those tickets with `ticket update --label`. A `lint_label_merged` finding (tickets that still carry a merged name) is fixed by running `dg label merge <name> <merged_into>` again. Labels that only look alike but mean different things stay: say why in the fix proposal
   - **The axes of the labels, once per check**: run `dg --json --actor agent label axis list --candidates`. Only when `state` is `undecided` (`labels.axes` is not written), add one row to the table, whatever the target: target `labels.axes`, finding "the axes of the labels are not decided". Its fix proposal is the axes chosen as the "The axes of the labels" section of `dg guide config` says (the default candidates, plus the recommended ones that have a basis in the repository, each with its basis: the file and what it says). Its choices are "Use these axes" (the human may drop or rename axes, as input outside the choices), "Do not use", and "Decide later". For `off` (decided not to use axes) and `on`, add no row
3. **Show a table and get approval**: show the following table and ask with multiple selection (`#`) which rows to reflect (include "Do not reflect"). If a row's fix is not one choice, list the proposals and accept input outside the choices

   | #   | Target | Finding (code) | Fix proposal | Command |
   | --- | ------ | -------------- | ------------ | ------- |

4. **Fix**: run only the approved rows, in table order. The fixes that the Workflow's `flow.assign` judges (`iteration add` and `remove`, `epic add` and `remove`, `ticket update --iteration` and `--epic`) carry `--approved-by human`, since the row's approval is the approval. In a flow started with `--auto`, when `approval.auto_ok` of the check stage of `dg flow next` is true and the row was fixed without asking, they carry `--auto` instead (when dg refuses it, ask a human, as the error says). Deletion, abandoned, and closing or reopening an Epic or Iteration are confirmed once more one at a time, even if the row was approved. The row of the axes of the labels is always asked, in a flow started with `--auto` too (a human decides the axes), and is fixed by its choice: "Use these axes" runs `dg --json --actor agent label axis set <name> --description "<description>" --approved-by human` once per chosen axis; "Do not use" runs `dg --json --actor agent label axis remove --all --approved-by human`, which writes `labels.axes: []`, so later checks do not propose them; "Decide later" writes nothing, and the next check proposes them again. The rows of the vocabulary are always asked too (a human decides the vocabulary), and run `dg --json --actor agent label merge` (or `label add`, `label remove`) with `--approved-by human`, since the row's approval is the approval (the Workflow's `governance.labels` judges them). Report the tickets a merge rewrote (`count` and `tickets` of its result). On `TRANSITION_REJECTED` (the Workflow's `governance.config` or `governance.labels` limits it to humans), give the human the exact command to run
5. **Confirm and report**: run `lint` and `validate` again, and report what was fixed, the findings left (with reasons), and any new findings
6. **Pass the checkpoint** (when the target is an Iteration or tickets in one; a check of an Epic or of the whole kanban has none): run `dg --json --actor agent checkpoint check <target>`, with the same target as the check. It records on the Iteration that the check was done on the tickets as they are now, so that `dg flow next` does not ask for the check again until they change (see `dg checkpoint --help`). The Workflow's `flow.check` judges it, as for the rows to fix, and it follows the approval rule of `dg guide overview`: after a human approved the rows in step 3, pass `--approved-by human`; in a flow, `checkpoint` of `dg flow next` gives the command in the form that fits the board (with `--auto` where `approval.auto_ok` of the check stage is true). When there was no row to fix and the checkpoint needs approval, show the result and ask once whether to record the check as passed. If the human stopped at the table ("Stop here"), do not run it

Collecting findings and making the table proceeds without waiting for approval (nothing is written). The `sync` writes only reconcile, so do not wait for them.

## Choosing the next step

After reporting the result (including when there were no findings), ask with these choices.

- **Make a plan** (recommended): plan the target's todos by the steps of `dg guide plan` (if a Skill is available, `/dgplan <target>`)
- **Assign**: if there are todos not in an Iteration, assign them by the steps of `dg guide assign` (if a Skill is available, `/dgassign`)
- **Stop here**
