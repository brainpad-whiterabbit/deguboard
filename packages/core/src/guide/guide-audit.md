# 見直し（audit）

Iteration（か Epic）のチケットがすべて done になった後、リリースの前に、リポジトリ全体を観点ごとに見直し、指摘を承認を得てチケットにする。見直しではファイルを直さない。見つけたものはチケットにして、計画と PR を通して直す。起票の形と書き方は `dg guide import` に従う。

## 対象を決める

- Iteration（`s3`）・Epic（`e3`）：直すチケットを入れる先と、見直しを終えたかを判断する単位。見直す範囲はいつもリポジトリ全体
- 指定が空：active の Iteration を勧めて確かめる。なければどれかを聞く。決めずに見直すと答えたら、指摘はどこにも入れずに起票する
- 対象に done・abandoned 以外のチケットが残っていれば、見直しを始めてよいか確かめる

以下では対象の ID を `<S>` と書く。

## 見直しの手順

1. **状態を読む**：`dg --json --actor agent sync` の後に、対象（`iteration show <S>` か `epic show <S>`）と、前回の見直しで起票したチケット（ラベルが `audit-` で始まるもの。`ticket list --label` で探す）を読む。リポジトリの規約（CLAUDE.md・README・開発の文書）から、正本とする文書・検査のコマンド・観点の足し外しを拾う。前回のリリースのタグ（`git tag --sort=-creatordate`）から、先に見る範囲（その後に変わったところ）を決める
2. **一時 worktree を作る**：`git fetch {{git.remote}} {{git.base_branch}}` の後、`git worktree add --detach {{worktree.root}}/audit-<S> {{git.remote}}/{{git.base_branch}}`。残っていれば `git worktree remove --force` で消してから作る。続けて、規約が書く依存のインストール・ビルド・検査の全体をこの順に 1 回だけ実行し、成否と失敗の出力の末尾を控える。失敗しても止めない
3. **観点を決める**：下の「観点」に規約の決まりを当てはめる。リポジトリにない対象の観点は理由を添えて飛ばす
4. **観点ごとにサブエージェントで見直す**：下の「サブエージェントに任せる」のとおり、並べて走らせる
5. **まとめて照合する**：観点の間で同じ対象・同じ食い違いの指摘を 1 つにする。下の「同じ指摘を繰り返さない」で、すでに扱ったものを除くか `ticket update` の案にする。読んだファイルの中身を、この手順を進めるセッションに持ち込まない
6. **指摘の表を示す**：重大度の高い順に、次の表で示す。重大度が低の指摘は観点ごとに 1 行にまとめる。扱いは「起票」「`ticket update <ID>`」「直さない（理由）」のどれか

   | #   | 観点 | 重大度 | 対象 | 指摘 | 置き場 | 扱い |
   | --- | ---- | ------ | ---- | ---- | ------ | ---- |

7. **承認を得る**：反映する行を `#` の複数選択で 1 回だけ聞く（「反映しない」も入れる）。承認を得るまで書き込まない
8. **反映する**：承認された行を、`dg guide import` の手順で起票する（下の「起票するチケット」）。重なるチケットには `ticket update <ID> --acceptance` や本文で指摘を足す
9. **片付けて結果を伝える**：`git worktree remove {{worktree.root}}/audit-<S>` で消す（やめたときも）。消せなければ `git -C <パス> status --short` で変わったファイルを結果に挙げてから `--force` で消す。見た観点と飛ばした観点・起票したチケット・直さない指摘を伝える

見直しの実行（サブエージェント・読み取りのコマンド・一時 worktree）は承認を待たずに進める。承認を求めるのは手順 7 の 1 回だけ。

## 観点

| 観点           | 見ること                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| 文書と実装     | 正本と実装の食い違い。実装も後続もない決めた作業。ADR の長さ・整理（「起票するチケット」）                 |
| テスト         | 仕様・受け入れ条件に対応するテストの抜け、不安定なテスト、理由のないスキップ、手順 2 の検査の失敗          |
| アーキテクチャ | 規約にある構成・依存の向き・コードの規約への違反。使われていないコード、同じ処理の重複                     |
| README         | 利用者向けの手順・コマンド・オプションが今の実装と合っているか。リンク切れ                                 |
| 依存           | 既知の脆弱性、大きく古い・更新の止まった・使われていない依存、ライセンスの表記の漏れ                       |
| 設定ファイル   | パッケージ・ビルド・lint・型検査・ツールの版の設定どうしの不整合、使われていない設定、規約の記述と違う設定 |

観点の具体（見る文書・検査のコマンド）は規約から読み、ここに書かない。前回のリリースより後に変わったところを先に見る。

## サブエージェントに任せる

観点ごとに 1 つのサブエージェントを起動し、並べて走らせる。この手順を進めるセッションは、まとめ・照合・表・承認・起票だけを行う。

- **渡すもの**：観点と見ること（上の表と規約の具体）・規約の場所・一時 worktree のパス・先に見る範囲（例 `git diff <タグ>..{{git.remote}}/{{git.base_branch}}`）。テストの観点には手順 2 で控えた検査の結果も渡す
- **してよいこと**：一時 worktree のファイルを読むこと。生成物を書かない読み取りのコマンド（audit・個別の lint や型検査など）を実行すること
- **してはいけないこと**：依存のインストール・ビルドのし直し・検査の全体の実行・生成物を消すこと（同じ worktree を並べて使うので互いに壊す）。ファイルを直すこと。`dg` で書き込むこと
- **返すもの**：指摘ごとに、対象（ファイルと行）・食い違いの両側・根拠（出力や文書の箇所）・重大度の案・直し方の案。指摘がなければ見た範囲

## 同じ指摘を繰り返さない

- **終わっていないチケット**：同じ対象・同じ食い違いのチケットがあれば起票せず、`ticket update` の案にするか除く
- **done のチケット**：同じ対象を扱った記録があれば除く。直した後に戻ったものは新しく起票し、元のチケットを本文に書く
- **意図した設計で直さないもの**：「直さない」に分け、その意図をテストかコメントで押さえるチケットの起票を勧める（ADR に書き足さず、テストかコメントで示す）。次の見直しでテストかコメントから読んで除ける

| 重大度 | 当てはまるもの      | priority |
| ------ | ------------------- | -------- |
| 高     | {{priority.high}}   | high     |
| 中     | {{priority.medium}} | medium   |
| 低     | {{priority.low}}    | low      |

置き場の勧めは対象（リリースの前に直す）。設計の判断が要る・外のものを待つ・PR 1 つで直せない・別のテーマに合う指摘だけは、理由を添えて対象に入れない（未割り当て）を勧める。

## 起票するチケット

- ラベル `audit-<S>`（例 `audit-s3`）を付ける。対象を決めずに見直したときは `audit`。対象が Iteration なら `iteration`、Epic なら `epic` に `<S>` を書く
- ラベル `audit-<S>` のチケットがあれば、`<S>` は見直し済みとみなす。この手順の起票のほかでこのラベルを付け外ししない
- ADR の細部と実装のずれは、題を「ADR の細部を消す」（ADR 番号を添える）にして起票する。判断は変えず、細部はコード・テスト・ヘルプへ移す
- ADR が長くなった（目安は 8,000 字）・要らなくなった ADR がある・同じ主題の判断が散らばっているときは、題を「ADR の分割・整理」にして起票する。分割・統合・削除・細部の削除・実装との照合、テストや lint に移せる判断の洗い出しを 1 チケットにまとめる
- 概要には観点・対象・食い違いの両側を書き、どちらに合わせて直すかは決めない（計画で決める）

## 次の手順を選ぶ

結果を伝えたら（指摘がなかったときも）、次の選択肢で聞く。

- **計画を立てる**（対象に起票したとき勧める）：`dg guide plan` の手順で対象の todo を計画する（Skill があれば `/dgplan <S>`）
- **リリースする**（起票しなかったとき勧める）：`dg guide release` の手順でリリースして閉じる（Skill があれば `/dgrelease <S>`）。対象が Epic なら `dg guide done` で片付ける
- **ここで止める**
