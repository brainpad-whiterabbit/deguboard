## 概要

VS Code のパネルでチケット詳細を新しく開くと、呼び出し 14 本が 1 本ずつ処理され、1 本ごとに Store の再走査（2,224 ファイルの stat、1 回 約 43ms）が走る。合計 約 600ms で、開く時間 1.2 秒の半分を占める。読みのコマンドは、要求が届いた後に始まった再走査を共有し、同時に届いた読みの再走査を 1 回にする（案 A）。他のプロセスの変更が見えるまでの約束は変えない。調査の結果は https://claude.ai/artifact/DRdnJTikZviCUmfaCmbnF6

## 受け入れ条件

- [x] プロセス内の CommandClient が、読みのコマンドで、要求が届いた後に始まった再走査を共有し、同時に届いた N 本の読みで rescan が 1 回になることをテストで確かめている
- [x] 同時に届いた読みの 1 本が失敗しても他の結果は返り、失敗はそのコマンドの失敗として返る
- [x] 書き込みのコマンドは再走査を共有せず、今どおり 1 本ずつ処理される
- [x] 入口（Webview・HTTP）と web は変えず、Webview と dg serve の両方で効く
- [x] チケット詳細を新しいパネルで開いたときの再走査の回数と時間を、変更の前後で計って PR に示す

## 検討（案 A に決定）

2026-11-10 に人が案 A を選んだ。受け入れ条件は案 A に合わせて書き換えた。検討は agent が 2026-11-09 にコードを読んで行い、まだ計っていない。

### 今の動き（コードで確かめた点）

- 呼び出しのたびに、local.ts の `context()` が `store.rescan()` を走らせる。呼び出しは `serialized` で 1 本ずつ並ぶ
- サイドバーとパネルは同じ client を使う（extension.ts の `clientFor(folder)`）
- チケット詳細の読みは 1 つの Promise.all にまとまっておらず、次の波に分かれて届く
  1. 開いた直後：store.reload の前半の `project.list`・`config.show`・`whoami`、`status`、`ticket.show`
  2. store.reload の後半の一覧 5 本（`ticket.list`・`epic.list`・`iteration.list`・`plan.list`・`workflow.show`）
  3. `ticket.show` が返った後（TicketPage は `if (!ticket) return` の後で子を描くので、ここで初めて届く）：`TicketRuns` の `run.list`、`TicketTimeline` の `history`、`ask-menu` など
- `useCommandData` は `store.tickets` が変わると読み直す（command-data.ts）。キャッシュから描いた後に reload が終わると、`ticket.show`・`run.list`・`history` がもう一度届く

このため、元の案（画面が束を明示して送る）で束になるのは store.reload の中の 3 本と 5 本だけになる。波 1 の `ticket.show` と波 3 は束の外に残る。

### 案 A（採用）：束を core の中で暗黙に作り、入口の形は変えない

createLocalClient に次のルールを足す。

> 読みのコマンドは、要求が届いた後に始まった再走査があり、その後に書き込みがなければ、その結果を使い回す

- 届いた後に始まった走査を使うので、「他のプロセスの変更は、要求が届く前に終わったものなら見える」という今の約束を保つ（今の走査も一瞬では終わらないので、保証の強さは今と同じ）
- 同じ瞬間に届いた要求を 1 回の走査に乗せるため、列が空のときは再走査を始める前に `setImmediate` を 1 回だけ待つ
- 直すのは packages/core/src/commands/local.ts だけ。状態として `scanGen`（始めた走査の番号）と `scanned`（最後に終わった走査の番号。失敗したら記録しない）を持つ
  - `run` と `status` に入ったときに `arrivedAt = scanGen` を記録する。順番が来たら、読み（`def.write === false`）で `scanned > arrivedAt` なら rescan を飛ばす。それ以外は今どおり rescan する
  - 書き込みは今どおり毎回自分で rescan し、終わったら `scanned` を無効にする（後に続く読みは新しく走査する）
  - rescan が失敗したら結果を共有しない（`ctxPromise = undefined` の今の扱いのまま）
- 要求ごとに別の Promise のままなので、1 本の失敗はその 1 本に留まる（元の受け入れ条件 2）。書き込みは今どおり 1 本ずつ処理される（元の受け入れ条件 3）
- 入口（vscode の webview.ts・server の app.ts）と web は直さない。dg serve も同じように速くなる
- 見込み：再走査が 14 回から波の数（3〜4 回）に減り、約 600ms が約 150ms になる。受け入れ条件 5 で計って確かめる

### 案 B（採らない）：元の案のとおり、束を明示して送る

- `WebviewRequest` に `kind: "batch"` を、HTTP に `POST /api/batch` を、web の 2 つの client に `runBatch` を足し、core に束を 1 回の rescan で処理する呼び方を足す
- 退ける理由：3 層の約束が増えるのに、束になるのは store.reload の中だけ。波 1 の `ticket.show` と波 3 まで束ねるには、web に同じ tick の `run` を集める層（DataLoader のようなもの）が要るが、それでも波をまたぐ読みはまとまらず、案 A より効かない

### テスト（案 A。bare リモート付きの一時リポジトリで、local.test.ts に置く）

1. 読みを N 本同時に投げると rescan は 1 回になる（`store.rescan` を spy するか、回数を数える内部のフックで確かめる）
2. 要求が届く前に外部でファイルを書き換えると、その要求の結果に変更が見える
3. 読みの間に書き込みが入ると、その後の読みは新しく rescan する
4. 同時に投げた読みのうち 1 本が `NOT_FOUND` で失敗しても、他の結果は返る
5. rescan が失敗すると、次の要求は自分で rescan する
