## 概要

facts.ts の branch_merged は、先端が base と同じ SHA のときだけ「切ったばかり」とみなし、それ以外は merge-base --is-ancestor で判定する。claim 直後の commit のないブランチは先端が当時の main を指しているので、その後に別の PR が main に入ると先端は main の真の祖先になり、merged と判定されて in_progress → done に進む。2026-10-31 に t36・t37（feat/actor-human-only・feat/t37-created-by-assignee、commit なし・PR なし）が #36・#37 のマージ後の dg sync で done になった。squash マージの流れでは真の ff マージは起きないので、祖先判定だけで merged と言うのは弱い。候補：(a) 先端のコミットが claim（in_progress になった時刻）より新しいときだけ merged とみなす、(b) ブランチが base との merge-base より先に 1 つも commit を持たないなら merged にしない（先端が祖先なら常に自分の commit は 0 なので、(a) と組み合わせる）、(c) software-development テンプレートの in_progress → done は pr_merged だけにし、branch_merged は gh のない general 向けに残す。ST-4・ST-5 と ADR-004 を見て決める。

## 受け入れ条件

- [ ] claim 直後の commit のないブランチは、main がいくつ進んでも照合で done にならない（bare リモート付きの一時リポジトリでテストする）
- [ ] ff マージされたブランチと、squash マージで PR が MERGED のブランチは、これまでどおり done に進む
- [ ] t23 のテストにこの形（切ったあとに main が進む）を足す
- [ ] requirements.md の ST-4 か ST-5 に判定の条件を 1 文で書き、変えた判断があれば ADR-004 を書き換える
