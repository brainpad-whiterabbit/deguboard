## Summary

Epic e40 の方針（判定は純粋な関数で網羅し、git を通す結合テストは経路の代表にする）の最初の段。ここで事実の型の作り方とテストの書き方を決め、後のチケットはそれに沿う。

今の `judgeGate`（`packages/core/src/commands/gate.ts`）は、gh を読んで pr を決め、チケットの本文を読んで受け入れ条件を決め、`latestCommit` を読んで head を決め、`judgeReview` が実行中の Run・`remoteTip`・保留の見直しを読んで review と fix_rounds を決め、最後に `judgeCheck`（`gate-check.ts`）で検査を回す、と読むことと決めることが交互に出てくる。そのため判定の組み合わせを確かめるにも、本物の git と偽の gh で事実を 1 つずつ作っている。pr.test.ts（26.1 秒・34 件）と gate.test.ts（13.1 秒・32 件）を読むと、判定の組み合わせだけを確かめている件がそれぞれ約 7 件・約 12 件、判定と経路の両方を見ている件が約 8 件・約 10 件ある。

すでに純粋な関数：`reviewedTip`・`heavyReviewRounds`（gate.ts）、`chooseCheck`（gate-check.ts）、`gateScopeOf`・`gateLevelOf`（`packages/core/src/model/ticket.ts`）。pr.ts の `passGate` は `judgeGate` の結果から越えた条件と止める条件を出す後処理を持つ。

検査は遅いので、ほかの条件がすべて満たされるか越えられたときだけ回す。この順序を保つため、決める処理は 2 段にする（1 段目でほかの条件を決めて検査を回すかを返し、回したならその結果を入れて 2 段目で結論を出す）。gh・git が読めなかったとき（PR がない、gh がない、理由つきで読めない）は、事実の型に値として持つ。

## Acceptance criteria

- [ ] gate の条件（pr・acceptance・review・fix_rounds・mergeable・head・check）の判定が、git・gh・ファイルを読まない関数にある。入力は事実の型、出力は条件ごとの結果と検査を回すかどうかで、検査を最後に回す今の順序は変えない
- [ ] pr ready・pr merge が gate の結果から越えた条件と止める条件を出す処理も、読まない関数にある
- [ ] 段（high・low・free）× for（ready・merge）× 条件ごとの事実（読めないとき・PR がないときを含む）の組み合わせを、その関数のテストで確かめる
- [ ] gate.test.ts と pr.test.ts から判定の組み合わせだけを確かめていた件を判定のテストに移し、git を使う件は経路（gh の呼び方と引数、`--match-head-commit`、記録、検査を回す）の代表にする。移した件と残した件の対応を PR に載せる
- [ ] dg gate・dg pr ready・dg pr merge の出力と終了コードが変わらない
- [ ] 全体のテストの時間と、gate.test.ts・pr.test.ts の時間の変更前後を PR に載せる
