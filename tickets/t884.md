## Summary

今は `dg pr merge` が `GATE_FAILED` を返すと、人に `gh pr merge` を打ってもらうよう案内し、フックも agent の `gh pr merge` を止める。そのためリリースの PR（t872）などで人がマージのコマンドを打っている。PR の種類は区別せず、人が承認したら、config で越えてよいとした品質ゲートの条件を満たさなくても agent がマージできるようにする。プロジェクトによって厳しくできるよう、越えてよい条件は config で決める。

承認を記録する仕組みは t883 のものを使う。

## Acceptance criteria

- [ ] 品質ゲートを満たさない PR は、マージしてよいかを人に聞き、承認されたら agent が `dg pr merge` に承認者を渡してマージする。人に gh のコマンドを打ってもらう案内は出さない
- [ ] config に、人の承認で越えてよい品質ゲートの条件の一覧（例：`merge.approval_overrides`）がある。既定は越えられる条件すべて（検査・見直し・手直しの回数・受け入れ条件）。一覧にない条件を満たさない PR は、承認者を渡しても `GATE_FAILED` のままになる
- [ ] 人の承認がなければ、agent は品質ゲートを満たさない PR をマージできない
- [ ] 衝突（`mergeable`）と head の確かめは、config でも越えられない
- [ ] guide（release・review・all）、requirements.md の項、関わる ADR、config の説明を同じ PR で直す
