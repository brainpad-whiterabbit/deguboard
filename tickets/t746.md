## Summary

採番は読めたファイルの番号だけから最大を求める。新しい版の dg が書いたファイルや壊れたファイルが最大の番号だと、同じ番号で新しいチケットを作る。作るときもファイルがあるかを確かめずに書くので、読めないファイルを上書きし、commit・push まで進む。

## 採るやり方

- 墓標（readDeletedTickets）と同じく、読めないファイルの番号もファイル名から取って store に持ち、nextId と create の両方で使う。push が拒否されたあとの採番のやり直し（DT-4）も同じ nextId を通るので、リモートから来た読めないファイルも避けられる
- createDoc も書く前にファイルがあるかを stat で確かめて断る。コメントの「既にあれば失敗する」のとおりにし、走査のキャッシュが古くても守る
- 採らない：link による原子的な作成（同じマシンの書き込みは withWriteLock で直列なので過剰で、FS によっては link が使えない）

## Acceptance criteria

- [x] 読めないチケット・Epic・Iteration・Plan のファイルも、ファイル名の番号を採番の最大に入れる
- [x] 作る先にファイルがすでにあれば ALREADY_EXISTS で断り、上書きしない。store の create は読めないファイルの ID でも断り、createDoc は書く前にファイルがあれば断る
- [x] チケット・Epic・Iteration・Plan のそれぞれで、スキーマに合わない最大の番号のファイル（t10.md など）があるときに作ると次の番号になり、そのファイルの中身が変わらないことを、並べたテストで示す
- [x] requirements.md の DT-4 を「既存（読めないファイルを含む）と墓標の最大 + 1。あるファイルは上書きしない」にする
