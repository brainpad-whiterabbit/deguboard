## Summary

見直し（s35）の観点「文書と実装」。t936 で、guide-release の手順 3 がリリースを 2 つのチケット（版を上げる PR のチケットと、タグと公開のチケット）に分け、手順 1 のあとで `<S>` に起票するようにした。一方 `dg flow next` は、`<S>` のチケットがすべて終わっているときだけ release（規則 7）を返し、そうでなければ規則 5 の「open な Plan にない todo」で plan を返す。そのため、dgall がリリースの段の途中で止まって再開すると plan の段に回され、release に戻れない。公開のチケットが in_progress の間も release が返らない。リリースの手順で起票する 2 つのチケットにラベル `release-<S>` を付け、flow は `<S>` の残りが `release-<S>` のチケットだけなら release を返し、それらを規則 5 の計画の対象に数えない（見直しの `audit-<S>` と同じく事実から決める）。リリースのチケットを Iteration の外に起票する案は、閉じる前に 2 件とも done かを Iteration の中で追えないので採らない。flow の resume にリリースを始めたことを覚える案は、同じ引数で 1 から再開すると忘れるので採らない。

## Acceptance criteria

- [ ] `<S>` に `release-<S>` のラベルのチケットが残っていても、`dg flow next` がリリースの段を返し、それらが終わるまで plan の段に戻らない
- [ ] guide-release の手順が、リリースの 2 つのチケットに `release-<S>` のラベルを付けて起票する。guide-all の手順もこの扱いと合っている
- [ ] `dg flow next --help` の規則 7 の説明が、`release-<S>` のチケットの扱いを示す
- [ ] 上の振る舞いをテストが確かめる
