## Summary

`iteration close`・`epic close`・`epic reopen` は書き込みを溜めるので、push されるまで別の環境からは開いたままに見え、二重に閉じられて sync が競合で止まった（s26 の closed_at が両側で違った）。claim・作成・`iteration start / reopen` と同じように、すぐ push し、push が通って初めて成り立つ（cas）ようにする。リモートに届かないときは閉じずに失敗する。

## Acceptance criteria

- [ ] `iteration close`・`epic close`・`epic reopen` が、溜まった変更を待たずにすぐ push する
- [ ] 別の環境がもう閉じた Iteration・Epic を閉じようとすると、取り込んでから確かめ直し、閉じ済みとして拒否される（`epic reopen` も同じく、開き済みとして拒否される）
- [ ] 二重に閉じる場面を、bare リモートの 2 つの clone で確かめるテストがある
- [ ] リモートに届かないときは、コミットを捨てて `PUSH_FAILED` で失敗するテストがある
- [ ] requirements の SY-3、ADR-027 の即時の操作の行、`dg guide overview` の「When sync stops」の列挙に、`iteration close`・`epic close`・`epic reopen` が入っている

## 取りやめた理由

競合を起こさない対策より、起きたときにすぐ解ける対策を重く見ると決めた。s26 の形（両側とも closed で closed_at だけ違う）は t775 が自動で解き、それ以外の競合は t774 の値の表から 1 回選べば解ける。cas にするとリモートに届かないときに閉じられなくなり、それに見合う効き目（数が違う二重の close、batch の利用者）は小さい（人の判断）。
