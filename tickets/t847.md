## Summary

利用者ごとに測りたいものと測れるものが違うので、振り返りの指標を dg に決め打ちしない。チームで共有する config.yaml に振り返りの観点（名前と問い）を置き、定義のない観点は、振り返りのときにエージェントが手元のデータで満たせる指標を、数え方の文・出どころのコマンド・測れない部分つきで提案する。人が承認した定義は観点の下に記録し、次の回からはその定義で、過去の回も計算し直して傾向を出す（結果は保存しない）。

既定の観点は、Agentic-Agile の評価の枠組みにもとづき、git と Run で測れる 7 つ（成果・見直しの効き目・仕様の質・分け方・エージェントの安定・コスト・改善の追跡）にする。今の retro の 4 観点（成果・流れ・やり直し・比較）は置き換え、比較は定義を残したことで毎回の傾向として出す。定義は dg が実行する式ではなく、文と出どころのコマンドで書き、エージェントが読んで計算する。指標の元のデータ（PR の変更ファイル・チケットどうしの参照）を dg から読めるようにするのは別のチケットで行う。

s29 の振り返りで、Agentic-Agile の観点で s24〜s29 を比べたときの議論から。定義を毎回考え直すと回どうしで比べられないので、承認した定義を残す。

## Acceptance criteria

- [ ] config.yaml（チームで共有）に、観点ごとの名前・問い・承認した指標の定義（数え方の文と出どころのコマンド）を置け、スキーマが検査する
- [ ] 既定の観点が Agentic-Agile の評価の枠組みにもとづく 7 つ（成果・見直しの効き目・仕様の質・分け方・エージェントの安定・コスト・改善の追跡）で、どれも定義は空である
- [ ] 承認した定義を、ファイルを直接編集せずに dg のコマンドで config.yaml に書ける
- [ ] dg guide retro の手順で、定義のない観点には指標を提案して承認を求め、承認されたら dg のコマンドで記録する
- [ ] dg guide retro の手順で、定義のある観点はその定義で対象の回と直近の回を計算して傾向を出し、出せないものは「未計測」と理由を書き、結果は保存しない
- [ ] requirements.md の設定の節（5.10）と振り返りの項が直り、設定の形を決める ADR がある
