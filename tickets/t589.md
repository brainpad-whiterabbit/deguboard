## 概要

各トピックから、エラーの文・lint の出力にある説明と、同じトピックの中の重複だけを消す。消してよいかの基準は、overview を縮めるチケットと同じ 4 つ（同じ手がその場面で届く・「しない」の決まりではない・黙って起きることではない・判断の材料ではない）。

- check：冒頭の lint の判定の一覧（`lint` の `issues` が出す）、Run の lint の起き方の説明（先のチケットで message に移したもの）
- assign：結果に出ること（開始日・終了日・件数の記録、並び順、progress の数え方）
- plan：「承認について」と手順 7 の重複、after の循環の拒否の説明（エラーに経路が出る）
- done：閉じた Plan は承認も閉じ直しもできないこと（拒否される）。記録する前にマージされた PR の項は、先のチケットで警告に移した分を短くする
- import：本文の項目の行末コメントの項（エラーの文に直し方がある）、7 項目の根拠の数字
- review：「見る」と「返す」で重い・軽いを 2 度並べている所を 1 か所にする

残す（削ると挙動が変わる）：done の `BRANCH_IN_USE` の項（エラーの文は「ブランチを消す」と言い、guide の手と逆）、import の本文以外の項目の `#` が黙って捨てられること、plan の `--depends-on` が一覧を置き換えること、assign の別の Iteration から黙って移ること・reopen で持ち越しが戻らないこと、review の品質ゲートの「検査」・確かめ直し・版上げで見直しを省く規則、check の lint の code ごとの直し方。check の `lint_run_fix_missing` の「コミットが修正でなければ無視してよい」「`lint_commit_outside_run` と両方出たらこちらを優先する」は t587 で message に移していないので、message に移してから消すか、guide に残すかを決める（PR #537 の見直しの指摘）。work・all・audit・release・run・parallel は手の順と止まる場所が大半なので変えない。
