# ADR-005 作業の実績

- ステータス：承認
- 更新日：2026-11-06

## 背景

チケットの分割の粒度やモデルの選び方を決めるのに、AI エージェントがどれだけのトークンと時間を使ったかの実績が欲しい。ただし AI の自己申告は正確でなく、会話記録は個人のデータでもある。何を、どこから、どこまで記録するかを決める。

## 決定

### 実測し、自己申告しない

- 使用量は Run 単位で記録する。1 つのチケットに複数の Run を紐づける
- 数は公式に提供される使用量の情報（今は会話記録）から取る。エージェントに数字を言わせて書かない
- 取れない指標は `null` にして警告する。架空の値で補完せず、推定した値には `estimated: true` を付ける
- エージェントごとに取得方法が違う部分は Adapter が吸収する（今は Claude Code・Codex・Copilot）
- Run のエージェント名は `run start` の `--agent` で渡すか、省けば Adapter が dg を呼んだプロセスの環境変数（製品が実行するコマンドに付けるもの）から判定する。claim で Run を開くときにもエージェントに名前を言わせずに済むため。製品が付ける変数を確かめられない Adapter は推測した変数で判定せず、`--agent` を求める。どの変数で判定するかの正本は Adapter のコード

### 記録するもの

- エージェント・モデル・日時・トークン数・結果・エラー・やり直しの理由・step（項目は RN-1）
- ツールの呼び出しの種類（読む・探す・書く・Bash・ほか）ごとの回数と、最初に書くまでの読む・探すの回数。手引き（`dg guide`）を変えたとき、調べる量が減ったかを Run で比べるため（参考節の効果は親の側に出るので Run では比べない）。Bash はコマンドで読む・書くを分けない（分けるにはコマンドの文字列を解釈することになる）。種類の分け方と、どの Adapter が数えるかの正本は Adapter のコード
- 集計は Run から Step（実装・見直し・手直しを分けて見る）までの単位で表示のたびに求め、保存しない（MT-3）
- Epic・Iteration・Project へは、Run の持つチケットの今の所属でたどる（持ち越したチケットの Run は今の Iteration に数える）。Run に所属を写すと、チケットを動かしたときに Run と食い違うため

### 実装・見直し・手直しを別の Run にする

- 実装の Run は、作業するエージェント自身の `ticket claim` が開き（Workflow の `opens_on: claim` の step。RN-5）、draft の PR を作った時点で閉じる。手順書を通らずにその場で実装すると `run start` が呼ばれず Run が残らなかったので、Run の開始をチケットの操作に付随させた。実装をサブエージェントに渡す親は `--no-run` で claim し、サブエージェントが自分で `run start` する（親が開いた Run では作業した分を数えられない。下の「会話記録を Run に結び付ける」）
- 見直し役の見直しは `review`、修正ループの 1 回と人のレビューの後の手直しは `fix` の Run にし、それぞれ作業したエージェント自身が `run start` で記録する。同梱の software-development と general の `steps` に `review`・`fix` がある
- 手直しの Run には、直した指摘を `retry_reasons` に 1 件 1 行で残す。修正ループの手直しも人のレビューの後の手直しも `fix` なので、`fix` の Run の数は手直しの回数の目安にとどまる。修正ループの上限は手順の側で数える
- 手順は `dg guide work`・`dg guide review` が持つ

### 親の使用量は Run で測らない

- 計画を立て、サブエージェントを進める親の作業は Run にしない（親が自分で実装する分は `implement` に入る）。Run の合計はチケットの作業の量として読み、全体の費用とみなさない
- 親の分は小さくない。2026-11-05 の 15 セッションの会話記録では、親が output の 23%・cache_read の 39% を使い、単価の比で重みを付けると全体の約 3 割だった
- 測るなら、まず期間を指定した会話記録の親と子の集計から考える

### 推定費用は持たない

- 費用の単価は持たず、トークン数だけを記録する。費用が要るときは利用者が単価を掛ける

### 会話記録を読む許可はリポジトリの設定に置く

- 会話記録（`~/.claude/projects/**`・`~/.codex/sessions/**`・`~/.copilot/session-state/**` など）を読むかどうかは `config.yaml` の `metrics.read_transcripts`（true / false）で決める。チームの方針として Git で共有する
- 個人が拒むときは環境変数 `DEGUBOARD_NO_TRANSCRIPTS` で、そのマシンでは読まない（MT-2）
- 許可がなければ、使用量は `null` のまま、日時・結果などの Run の記録だけを残す。読まなかったとき・取れなかったときは `run finish` が警告を返す。Adapter のない agent 名の Run は `run start` が警告する（記録はする）

### 会話記録を Run に結び付ける

- `run finish` が Run の `agent` の値で Adapter を選び、会話記録から使用量を取る。閉じた後に記録が見つかったときや Adapter を直したときは、`run refresh` が同じ探し方で取り直し、取れた値だけを書き換える（MT-5）。ツールの回数は取り直さない（閉じた Run で書き換える値を広げない。RN-4）。記録の置き場所・数える行・写し方・探す範囲の正本は Adapter のコード（`core/agents/adapters/`）
- 結び付けるのは、記録の置き場所のすべてで Run の ID を最も早く含むファイル（`dg run start` の出力を受け取ったエージェントの記録）。ID を見ただけのファイルは選ばず、呼ぶ session によらない。その中の ID が出た後から `finished_at` までの応答を数える
- 同じファイルで期間が重なる Run があっても、1 つの応答は 1 つの Run にだけ数える。ID と Run の期間で決まり、閉じる順によらない（警告では値が直らないため）
- 作業ディレクトリと時刻で絞らないのは、サブエージェントが親と同じ session・作業ディレクトリで並行して動き、区別できないため。Run の ID は開始の時刻と乱数からなるので、同じ時間帯のほかの記録に偶然現れることはまずない。親が始めた Run の作業をサブエージェントがした分は数えない

### 写すのは数だけ

- Git に入る記録には、使用量とツールの回数の数とモデル名だけを会話記録から写す。ツールは名前を種類に変えて回数だけを残す。モデル名は会話記録から取れた正式な ID を優先し、別名が残らないようにする（順の正本は `run finish` のコード）。プロンプト・ツールの結果・ファイルの中身・コマンドの文字列・ファイルのパスは写さない
- 実行中の記録は Git 管理せず、Git に入れるのは Run 完了時の集計だけ（RN-3）
- Run はチケットの ID を持ち、チケットには Run の ID を書き足さない。チケットの Run は Run の側から引く

## 理由

- 自己申告は過小・過大になり、比べられない。公式の使用量なら後から測り直せる
- 単価はモデルや契約で変わり、更新し続ける必要がある。トークン数を残せば費用はいつでも計算できる
- 集計結果はどのみち共有リポジトリに入るので、「読むかどうか」もチームで決めるのが筋。個人の逃げ道は環境変数で足りる
- 数だけなら、チケットをまたいで比べられ、秘密情報が Git に入らない
- 実装の Run の中で修正ループを回すと、見直しと手直しの量が実装に混ざり、チケットの粒度とモデルの選び方の判断に使えない。Run を分ければ `metrics show --step` で比べられる
- 親の使用量を Run で測るには Run の形と多くのコードを変えることになる。今はチケットの粒度とモデルの選び方を決める数があれば足りる
- 集計値を保存せず、チケットに Run の ID を書き足さないのは、Run を足すたびに複数のファイルを書き換えて衝突させないため

## 採らなかった案

- **推定費用を記録する**：単価表の保守が要り、「推定」が独り歩きする
- **読む許可を利用者ごとにリポジトリの外に置く**：許可の有無がマシンごとに違い、チームで集計が揃わない
- **OpenTelemetry で収集する**：collector が要り、チケットとの紐づけが別に要る
- **チケットごとの `plan` の Run**（t400）：正しく呼んでも入るのは 1 枚を読んで決める 1〜2 回の応答だけで、全体を比べて順を決める考えが入らず、計画の重さを表さない（start と finish を 1 回のシェルで呼ぶと何も取れない）
- **Plan に結び付ける親の Run**（Run に `project`・`plan` を持たせて `ticket` を省けるようにし、予約の step で親を表す）：Plan の ID は計画の後にしかできず、親の Run は会話の再開をまたいで長く、チケットがある前提のコード（作業中の判断・集計・画面）を直すことになる。親の割合を見たうえで見送った
- **すべての Run を Plan に結び付け、1 枚の作業にも軽い Plan を作る**：Plan のない作業と Skill なしの使い方が止まり、過去の Run も揃わない
- **実装の Run を開けたまま修正ループを回し、`retries` に直した回数を書く**：見直しと手直しの量が実装と分かれない
- **AI に振り返りを書かせて数字を残す**：正確でない
- **会話の中身を記録する**：個人データと秘密情報が Git に入る
