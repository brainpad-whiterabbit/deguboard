# ADR-036 手戻りの原因は見直しの指摘に固定の種類で付け、見つけ損ねた不具合は直すチケットに元のチケットと原因を残す

- ステータス：承認

## 要約

見直し役が指摘の 1 件ごとに手戻りの原因の種類（`cause`）を固定の種類で付け、見直しの Run（Git）には原因ごとの数だけを残す。見直しをすり抜けて後から見つかった不具合は、直すチケットに元のチケットの ID の配列（`origin`）と原因の種類（`origin_cause`）を項目で残す。付けるのは起票する人かエージェントで、dg は本文に書かれた ID から推し量らない。

## 背景

仕様の質（手戻りの原因がチケットにあった割合）と見直しの効き目（見直しをすり抜けて、マージの後に見つかった不具合の割合）を、振り返りで数えたい。手直しの理由の文は成果物のどこが悪いかしか書かず、なぜそうなったかは分からない。本文の ID の参照は、元のチケットか依存か例かを見分けられず、振り返りのたびに読み手が判断していた。

## 決定

### 手戻りの原因は見直しの指摘に種類で付ける

- 見直し役（実装者とも手直し役とも別のエージェント）が、指摘の 1 件ごとに原因の種類（`cause`）を付ける。種類は固定で、チケット・計画・実装・テスト・文書・環境と、分からないときの `unknown`。成果物のどこが悪いか（`category`）とは別の項目にする
- 原因の種類のない指摘は受け付けない。分からないときは推し量らせず `unknown` にする
- 見直しの Run（Git）には、重い指摘と軽い指摘のそれぞれについて原因ごとの数だけを書く。指摘の一覧は今までどおりマシンごとのローカルに置く
- `metrics show` が原因ごとの数を合計する。原因の数のない Run（この決定より前の Run と、数だけを渡した結果）は測れていないものとして件数を出し、0 で補わない

### 見つけ損ねた不具合は、直すチケットに元のチケットと原因の種類を残す

- 不具合を直すチケットは、どのチケットの変更から出た不具合か（`origin`。チケットの ID の配列）と、原因の種類（`origin_cause`）を持てる（TK-12）。数えるのは、振る舞いの誤りと、変更と同時に直すべきだった文書のずれの両方
- `origin_cause` は `cause` と同じ固定の種類にし、分からないときは `unknown` にする。見直しで見つけた手戻りと、すり抜けた不具合を同じ分け方で比べる
- 付けるのは起票する人かエージェントで、`create`・`import`・`update` が受ける。dg は本文に書かれた ID から推し量って付けず、`metrics sources` は記録した値をそのまま返す。記録のないチケット（この決定より前のチケットを含む）は空のままにし、補わない

### 細部の正本

原因の種類の名前と意味（`dg run review-result --help`）、`origin`・`origin_cause` の形と受ける値・拒む値（`dg ticket update --help`）は、次のコードとテストとヘルプが正本で、「なぜ」はそのコメントとテスト名にある。

- `packages/core/src/model/ticket.ts`（`origin`・`origin_cause` の形）・`packages/core/src/commands/ticket.ts`（受ける値と拒む値）・`packages/core/src/commands/commands-flow-ticket.test.ts`
- `packages/core/src/commands/run.ts`（`run review-result`）・`packages/core/src/model/metrics.ts`（原因ごとの数の合計）

## 理由

- Git に残る記録は指摘の数と手直しの理由の文だけで、手直しの理由は成果物のどこが悪いかの形で書かれ、なぜそうなったかは分からなかった。仕様の質を振り返りで数えるには、原因を後から文から読み取るのでなく、見直しの時に種類で付ける必要がある
- 原因を付けるのを見直し役にするのは、実装者や手直し役が自分の作業の原因を言うと自己申告になるため。種類を固定するのは、Run をまたいで足せるようにするため
- 原因ごとの数だけを Git に残すのは、「写すのは数だけ」（[ADR-029](ADR-029-work-metrics.md)）を保ったまま、どのマシンでも同じ合計を出せるようにするため。前の Run を 0 や推測で補わないのは、取れない値を架空の値で補わない決まり（RN-2）と同じ
- 見直しの効き目は、`metrics sources` の `refs` と後のチケットの本文から数えていた。`refs` は ID が書いてあることしか伝えず、依存・例・元のチケットを見分けられないので、どれが見つけ損ねかを振り返りのたびに読み手が判断していた。項目で持てば、起票の時に分かっている人が 1 回だけ判断し、後の回も同じ数になる
- 元のチケットを直すチケットの側に持つのは、不具合が分かるのが元のチケットの done の後で、分かった時に書くのが直すチケットだから。元のチケットの側に書くと、終わったチケットを後から書き換えることになり、1 つの不具合を複数のファイルに書く。配列にするのは、1 つの不具合が複数の変更の重なりから出ることがあるため
- チケットの frontmatter に足すのは、チケットの ID と固定の種類だけで、「写すのは数だけ」が守る会話の中身・パス・指摘の文を Git に入れない。項目は省けるので、前からあるチケットは書き換えずに読める

## 採らなかった案

- **手直しの理由の文（`retry_reasons`）から原因を後で読み取る**：文は成果物のどこが悪いかしか書いておらず、読むたびに分け方が変わる
- **原因の付いた指摘の一覧を Git に入れる**：指摘の文とパスが Git に入り、数だけを写す決まりを崩す
- **原因を `category` に書かせる**：`category` は自由な文で数えられず、受け入れ条件の指摘を見分ける語とも混ざる
- **元のチケットを本文の ID の参照（`refs`）から読み取る**：書かれた ID が元のチケットとは限らず、読むたびに判断が変わる
- **元のチケットの側に、後から見つかった不具合を記録する**：終わったチケットを書き換え、直すチケットと 2 か所に同じことを書く
- **すり抜けた不具合の原因に、見直しの指摘とは別の種類を作る**：見直しで見つけた手戻りと比べられない
