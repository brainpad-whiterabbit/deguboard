# ADR-037 ラベルの軸はチームの config.yaml に、語彙はボードのデータに置き、既定はオフで、統合はチケットを書き換える

- ステータス：承認

## 要約

人がチケットの中身をひと目でつかむためのラベルを、プロジェクトが決めた軸（触る部分・変更の種類など）に沿って付けられるようにする。軸（名前と 1 行の説明）は人が決め、チームで共有する `config.yaml` の `labels.axes` に置く。語彙（軸ごとのラベルの名前と説明）は、エージェントが起票のたびに足すので、`config.yaml` ではなくボードのデータに置く。既定はオフで、軸を書いていないボードには点検が勧める。ラベルをまとめる（統合・改名）ときは、読むときに読み替えず、チケットを書き換える。チケットのデータの形は変えない。

## 背景

ラベルは自由な文字列で、決まった語彙がなかった。このリポジトリでは、触る部分の名前（`ui`・`web`・`vscode`）と変更の種類の名前（`bug`・`refactor`）が同じ並びに混ざり、意味の重なる名前（`dev`・`tooling`）が増えて、行を流し読みするときの手がかりにならなくなっていた。PR の変更ファイルから分野を出す方法は、PR のない todo には使えず、バックログでの手がかりはラベルしかない。

何を手がかりにしたいかはプロジェクトで違い、語彙は最初から決められない。起票を重ねるうちに出そろい、重なるものがまとめられていく。

## 決定

### 軸はチームの config.yaml に置く

- `config.yaml` の `labels.axes` に、軸の名前と 1 行の説明の一覧を持つ。形はスキーマ（`packages/core/src/model/config.ts`）が正本で、検査する
- チームで共有する値で、個人の設定では上書きできない（人ごとに軸が違うと手がかりにならない）
- 軸は `dg label axis set`・`dg label axis remove` が、スキーマで検査してチームの `config.yaml` に書く。チームの設定の変更なので、Workflow の `governance.config` で判定する。`config set` と設定画面は葉の項目だけを扱い、軸は書かない（[ADR-035](ADR-035-retro-perspectives.md) の振り返りの観点と同じ）

### 語彙はボードのデータに置く

- 語彙は `config.yaml` に置かず、ボードのデータの `labels.yaml` に、最上位のキーをラベルの名前にして置く。データのマージドライバがラベルごとにマージできるようにするため（形の正本は `packages/core/src/model/labels.ts`）
- チケットの `labels` は文字列の配列のままにし、軸ごとの項目は持たせない
- 語彙は `dg label add`・`dg label update`・`dg label remove` が書く。チームの設定ではなくボードのデータの変更で、起票のたびに増えるので、`governance.config` と分けて Workflow の `governance.labels` で判定する（語彙だけを緩められる）。語彙の残る軸は消せない

### 既定はオフで、点検が勧める

- `labels.axes` は 3 つの状態を持つ。書いていない（まだ決めていない。既定）・`[]`（使わないと決めた）・一覧（使う）。書いていないときと `[]` のときは仕組みはオフで、ラベルは今までどおり自由に付けられる
- 軸を書いていないボードには、点検（`dg guide check`）が軸を勧める。「使わない」を選べば `[]` を書き、それからは勧めない
- 勧める出発点として、dg は軸の候補を英語で持つ（`packages/core/src/model/label-axes.ts`。`dg label axis list --candidates` が出す）。どのプロジェクトにも当てはまる既定の候補（`area`・`kind`）と、当てはまるプロジェクトが限られる推薦（`impact`・`platform`・`audience`）で、推薦はリポジトリに根拠があるときだけ足して勧める。プロジェクトによる違いが小さい `kind` には推薦の語彙も持つ。候補は config の既定ではなく、人が選んで書いたものだけが効く
- 設定画面は軸を読むだけで出し、名前と説明が候補のままの軸だけ、説明を表示言語に訳す

### 統合はチケットを書き換える

- ラベルを別のラベルにまとめる（改名も、新しい名前への統合として扱う）ときは、そのラベルを持つチケットを、done・abandoned も含めてすべて書き換える。読むときに古い名前を新しい名前へ読み替えることはしない
- 書き換えは `dg label merge` が 1 回の書き込みで行い、語彙を書く操作として `governance.labels` で判定する。チケットの中身の変更ではないので `updated_at` は進めない。元の名前は統合の記録として `labels.yaml` に残す（細部は `dg label merge --help`）

## 理由

- 軸はほとんど変わらず人が決めるので、人が承認した定義をチームの `config.yaml` に置いて専用のコマンドで書く、振り返りの観点の前例に合う。語彙は起票のたびに増え、2 人が同時に足すこともある。行単位でマージされる `config.yaml` に置くと、同時に足したときに `dg sync --resolve` で解けない競合になる
- [ADR-003](ADR-003-status-and-workflow.md) は、利用者が定義する任意フィールドを、使われなかったことと項目の定義と検証の重さから退けた。軸はチケットに項目を足さず、`labels` の 1 つの配列のまま語彙を分ける見出しにとどまるので、チケットの形と検証は増えない。使われない恐れは残るので、既定をオフにし、使うと決めたボードだけが使う
- 既定の軸を書かなくても効かせると、今あるボードは dg の版を上げたとたんに、今あるラベルが一斉に語彙にないものになる。決めるのは人で、まだ決めていないボードにだけ、直し方の案を表にする点検の場面で勧める。書いていないのと `[]` を分ければ、使わないと決めたボードに勧め続けずに済む
- 統合で書き換えれば、ファイルの中の名前と画面の名前がずれず、過去のチケットも同じ語彙で探せる。書き換えは 1 回の書き込みにまとめられ、費用は小さい

## 採らなかった案

- **flow にラベル付けの段を設ける**：ラベルは何も止めないので、段にしても判定することがない。付けるのは起票のときが最も正確で、見直しの機会は点検の段にすでにある
- **config の許可リストで、語彙にないラベルを拒む**：語彙を足すまで起票が止まる。手順が付けるラベル（`audit-<S>` など）の例外も要る
- **統合しても書き換えず、「a → b」の記録を読むときに当てる**：ファイルの名前と画面の名前がずれ、そのチケットが次に書かれるまで残る。統合を取り消すと、元からその名前だったチケットと見分けられない
- **チケットにラベルの ID を持たせる**：利点は改名で書き換えが要らないことだけで、チケットのファイルが人にもエージェントにも読めなくなり、今あるチケットの移行が要る
- **チケットに軸ごとの項目（`area: ui`）を持たせる**：ADR-003 が退けた任意フィールドそのもので、チケットの形と検証が軸の数だけ増える
- **既定の軸（`area`・`kind`）を、書かなくても効かせる**：今あるボードの今あるラベルが、版を上げたとたんに語彙にないものになる
