# ADR-029 作業の使用量は Run ごとに公式の記録から実測し、数だけを Git に写す

- ステータス：承認
- 更新日：2026-11-08

## 背景

チケットの分割の粒度やモデルの選び方を決めるのに、AI エージェントがどれだけのトークンと時間を使ったかの実績が欲しい。ただし AI の自己申告は正確でなく、会話記録は個人のデータでもある。何を、どこから、どこまで記録するかを決める。

この判断を書いた ADR-005 は、Run の開け閉めと会話記録の場所の項を [ADR-025](ADR-025-runs-by-hooks.md) に置き換えられ、失効の印が 5 つになった。[ADR-001](ADR-001-doc-strategy.md) の基準で、今の判断と理由だけをこの 1 本にまとめ直す。

## 決定

### 実測し、自己申告しない

- 使用量は Run 単位で記録する。1 つのチケットに複数の Run を紐づける
- 数は公式に提供される使用量の情報（今は会話記録）から取る。エージェントに数字を言わせて書かない
- 取れない指標は `null` にして警告する。架空の値で補完せず、推定した値には `estimated: true` を付ける（RN-2）
- エージェントごとに取得方法が違う部分は Adapter が吸収する。Run のエージェント名も、省けば Adapter が dg を呼んだプロセスの環境から判定する（エージェントに名前を言わせずに済む）

### 記録するもの

- エージェント・モデル・日時・トークン数・結果・エラー・やり直しの理由・step（項目は RN-1）と、ツールの呼び出しの種類ごとの回数と最初に書くまでの読む・探すの回数
- 集計は Run から Step までの単位で表示のたびに求め、保存しない（MT-3）
- Epic・Iteration・Project へは、Run の持つチケットの今の所属でたどる（持ち越したチケットの Run は今の Iteration に数える）

### 実装・見直し・手直しを別の Run にする

- 実装・見直し・手直しを別の step の Run にし、`metrics show --step` で分けて比べる
- 実装の Run は作業する主体のチケットの操作が開け閉めする。開くのは claim（RN-5）、閉じるのは PR の記録か照合が PR を見つけたとき（`success`）、やめるときは `unclaim` と abandoned（`failure`）、PR の要らない作業は review・done への move（RN-6）
- サブエージェントの Run と、手直しの Run の開き方と閉じ方は [ADR-025](ADR-025-runs-by-hooks.md)
- 手直しの Run には直した指摘を `retry_reasons` に 1 件 1 行で残す。`fix` の Run の数は手直しの回数の目安にとどまり、修正ループの回数は見直しの結果から数える（ADR-025・[ADR-011](ADR-011-procedure-in-code.md)）
- 実装・手直しの Run の抜けは `dg lint` が指摘する（安全網）。手順は `dg guide work`・`dg guide review` が持つ

### 親の使用量は Run で測らない

- 計画を立て、サブエージェントを進める親の作業は Run にしない（親が自分で実装する分は `implement` に入る）。Run の合計はチケットの作業の量として読み、全体の費用とみなさない
- 親の使用量を測るなら、まず期間を指定した会話記録の親と子の集計から考える

### 推定費用は持たない

- 費用の単価は持たず、トークン数だけを記録する。費用が要るときは利用者が単価を掛ける

### 会話記録を読む許可はリポジトリの設定に置く

- 会話記録を読むかどうかは `config.yaml` の `metrics.read_transcripts` で決め、チームの方針として Git で共有する
- 個人が拒むときは環境変数 `DEGUBOARD_NO_TRANSCRIPTS` で、そのマシンでは読まない（MT-2）
- 許可がなければ使用量は `null` のまま、日時・結果などの Run の記録だけを残し、Run を閉じる操作が警告を返す

### 会話記録を Run に結び付ける

- Run を閉じる操作が Run の `agent` の Adapter で会話記録から使用量を取る。`run refresh` は後から同じ探し方で取り直し、取れた値だけを書き換える（MT-5）。ツールの回数は取り直さない（閉じた Run で書き換える値を広げない。RN-4）
- Run はセッション ID を持ち、会話記録のパスはマシンごとのローカル（`deguboard-local/`）に置いて Git に入れない。数える範囲は記録の場所で決め、場所がなければ Run の ID を最初に含む記録から推測する。1 つの応答は 1 つの Run にだけ数える。セッションと記録の場所の取り方は [ADR-025](ADR-025-runs-by-hooks.md)

### 写すのは数だけ

- Git に入る記録には、使用量とツールの回数の数とモデル名だけを会話記録から写す。プロンプト・ツールの結果・ファイルの中身・コマンドの文字列・ファイルのパスは写さない。例外はセッション ID だけで、後から数え直すのに残す
- 実行中の記録は Git 管理せず、Git に入れるのは Run 完了時の集計だけ（RN-3）
- Run はチケットの ID を持ち、チケットには Run の ID を書き足さない。チケットの Run は Run の側から引く

### 細部の正本

エージェント名の判定・ツールの種類の分け方・数える範囲と重なりの分け方・モデル名の選び方・閉じる時刻・閉じた Run への操作・抜けの指摘の条件は、次のコードとテストとヘルプが正本で、「なぜ」はそのコメントとテスト名にある。

- `packages/core/src/agents/index.ts`（`detectAgent`・読む許可）・`packages/core/src/agents/adapters/`（製品ごとの Adapter と `transcript.ts` の `bindFile`・`OverlapClaims`）・`packages/core/src/agents/agents.test.ts`
- `packages/core/src/model/run.ts`（Run の形）・`packages/core/src/commands/run.ts`（`run start`・`run finish`・`run refresh`）・`packages/core/src/run/record.ts`・`packages/core/src/commands/run.test.ts`
- `packages/core/src/commands/ticket.ts`（`ticket update --pr`）・`packages/core/src/commands/setup.ts`（照合が閉じる Run と `dg lint`）・`packages/core/src/commands/commands-flow-reconcile.test.ts`
- `packages/core/src/model/metrics.ts`・`packages/core/src/commands/metrics.ts`（`dg metrics show --help`）

### 置き換えるもの

- ADR-005 の全体。ADR-025 が置き換えた項（サブエージェントが自分で Run を開く文、見直し役が `run start`・`run finish` する文、手直しの Run の開き方と閉じ方、claim の `--retry-reason`、サブエージェントの記録の場所の文）は取り込まず、ADR-025 が今の判断

## 理由

- 自己申告は過小・過大になり、比べられない。公式の使用量なら後から測り直せる
- 単価はモデルや契約で変わり、更新し続ける必要がある。トークン数を残せば費用はいつでも計算できる
- 集計結果はどのみち共有リポジトリに入るので、「読むかどうか」もチームで決めるのが筋。個人の逃げ道は環境変数で足りる
- 数だけなら、チケットをまたいで比べられ、秘密情報が Git に入らない
- ツールの回数を持つのは、手引き（`dg guide`）を変えたとき、調べる量が減ったかを Run で比べるため
- 実装の Run の中で修正ループを回すと、見直しと手直しの量が実装に混ざり、チケットの粒度とモデルの選び方の判断に使えない。Run を分ければ `metrics show --step` で比べられる
- 実装の Run の開閉をチケットの操作に付けたのは、手順書を通らずに実装すると `run start`・`run finish` が呼ばれず、Run が残らないか開いたままになったため。使用量は `finished_at` で区切るので、古い手順のまま `run finish` を呼んでも数は壊れない
- 親の使用量を Run で測るには Run の形と多くのコードを変えることになる。親の分は 2026-11-05 の会話記録で単価の比の重みを付けて全体の約 3 割と小さくないが、それを見たうえでも、今はチケットの粒度とモデルの選び方を決める数があれば足りると判断した
- 集計値を保存せず、チケットに Run の ID を書き足さないのは、Run を足すたびに複数のファイルを書き換えて衝突させないため。所属を Run に写さないのは、チケットを動かしたときに Run と食い違うため
- 記録のパスはホームのパスとユーザ名を含み、Git に入れると他人に見え、別のマシンでは読めないので、マシンごとのローカルに置き、Git にはセッション ID だけを残す

## 採らなかった案

- **推定費用を記録する**：単価表の保守が要り、「推定」が独り歩きする
- **読む許可を利用者ごとにリポジトリの外に置く**：許可の有無がマシンごとに違い、チームで集計が揃わない
- **OpenTelemetry で収集する**：collector が要り、チケットとの紐づけが別に要る
- **チケットごとの `plan` の Run**：入るのは 1 枚を読んで決める 1〜2 回の応答だけで、全体を比べて順を決める考えが入らない
- **Plan に結び付ける親の Run**：Plan の ID は計画の後にしかできず、親の Run は会話の再開をまたいで長く、チケットがある前提のコードを直すことになる
- **すべての Run を Plan に結び付け、1 枚の作業にも軽い Plan を作る**：Plan のない作業と Skill なしの使い方が止まる
- **実装の Run を開けたまま修正ループを回し、`retries` に直した回数を書く**：見直しと手直しの量が実装と分かれない
- **AI に振り返りを書かせて数字を残す**：正確でない
- **会話の中身を記録する**：個人データと秘密情報が Git に入る
- **Run の ID が最初に出た会話記録だけで結び付ける**：後から開いた見直しの応答を数えられない。場所がないときの落ち先にだけ残す
