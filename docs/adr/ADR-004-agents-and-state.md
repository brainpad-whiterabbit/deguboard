# ADR-004 エージェントと状態の記録

- ステータス：承認
- 更新日：2026-10-31

## 背景

AI エージェント（Claude Code・Codex など）がチケットを処理する。ツール側がエージェントを起動・監視して状態を進める設計と、エージェントが自分で CLI を呼んで状態を記録する設計がある。先行プロジェクトは前者（ヘッドレス起動と統合ターミナル起動）を作ったが、起動・worktree の準備・監視のどこかで失敗するたびに壊れた実行が残り、安定せずに削除した。実務は「人が動かすエージェントが CLI でチケットを操作する」形に落ち着いていた。

## 決定

### ツールはエージェントを起動も監視もしない

- `dg`・サーバー・VS Code 拡張は、チケットの作業のためにエージェントを起動しない。実行中のプロセスも監視しない
- エージェントは Bash から `dg … --json --actor agent` を呼んでチケットを読み書きし、データのファイルを直接編集しない。手順は `dg guide <topic>` が出す
- human と agent の区別は申告（`--actor`・`DEGUBOARD_ACTOR`）に基づく。Skill と guide の手順が必ず agent を名乗ることで `by: [human]` の遷移をエージェントから遠ざける。権限管理や偽装の防止はしない（同じリポジトリに書ける人を信頼する）
- Claude Code 向けには `dg guide` を読む薄い Skill を配る。ほかのエージェントは同じ手順に従う。特定の AI 製品に依存する処理は Adapter（[ADR-007](ADR-007-architecture.md)）に閉じる

### 状態はチケットのブランチの事実で前進させる

- チケットは `branch` を持つ。`dg sync`（とサーバー・拡張の定期実行）は、そのブランチについて Git から事実を集め、ワークフローの `reconcile` 規則で状態を導き、今より先のときだけ書き換える
- 事実は Git だけで取れるものを基本にする：`branch_exists`（ローカルかリモートにある）、`branch_pushed`（リモートにある）、`branch_merged`（先端が `git.base_branch` の祖先）
- PR の事実（`pr_open`・`pr_merged`・`pr_draft`）は `gh` が使えるときだけ取り、software-development ワークフローが任意で使う。`gh` がなくても照合は成り立つ
- 後退を指す事実（消えたブランチ・マージされずに閉じた PR）は書き換えずに警告する。同じ照合で done に進むときは、マージ後に消したブランチなので警告しない。取れなかった事実は不明として扱い、前進の判定では偽と読む

### 排他は claim の push で決める

- 着手（todo → in_progress）は `dg ticket claim` で行う。claim は `status`・`claimed_by`・`branch` のコミットを push できたときに取得とする。拒否されたら取り込み直して判定し直す
- 同一マシンの Run の二重起動は、`deguboard-local/locks/<ticket>` のローカルロックで防ぐ。Git 管理外で、チーム間の排他には使わない
- 応答のない claim は人が確かめてから `dg ticket unclaim --force` で解除する。生存監視はしない

### Run は受動型で記録する

- エージェント（または Skill）が `dg run start <ticket> --step <step>` と `dg run finish <run> --result <result>` を呼び、Core が開始・終了・結果・使用量を `runs/` に書く
- ツールが Run を見失っても、チケットの状態はブランチの事実で進む
- 終了していない Run は `dg run list --open` で見せ、人かエージェントが `finish --result interrupted` で閉じる。自動復旧はしない
- 依存に従う並列実行や修正ループ（Phase 4）も、Skill 側が `dg ticket list --ready` を見て進める。ツール側にスケジューラを置かない

### Plan を第一級のエンティティにする

- 「どのチケットをどの順で（依存と計画内の待ち）進めるか」と承認状態（承認者・日時）、範囲と方針を `plans/p7.yaml` に持つ
- 進捗は Plan に書かず、チケットの状態から都度求める。Plan に書き込むのは作成・承認・終了のときだけ
- 1 つのチケットは同時に 1 つの Plan にしか入らない

## 理由

- 起動と監視を持たないと、ツールはエージェントの有無や実行の状態に左右されず、保守するコードが減る。排他と状態を Git の事実だけで決められる
- ブランチの事実は作業の結果として必ず残り、取り逃しがない。PR に依存しなければ、PR のない業務（コンサルティングなど）でも同じ仕組みで動く
- Git を compare-and-swap として使えば、サーバーなしで claim を atomic にできる
- 受動型の Run は、人が Claude Code を普通に動かす対話がそのまま記録として残る。能動的に起動する仕組みは、その上に後から足せる
- Plan を分けるのは、Epic は目的の範囲、Iteration は期間、Plan は実行順、Run は実績と役割が違うため。進捗を書かないのは、push の衝突を減らすため

## 採らなかった案

- **ツールがエージェントをヘッドレス起動して監視する**：先行プロジェクトで安定せず削除された。失敗した実行とロックが残る
- **実行中のプロセスを監視して状態を進める**：監視の失敗が状態の誤りになる。事実から導けば監視は要らない
- **ロックサーバーや DB による排他**：常駐サーバーが要り、オフラインで使えない
- **主体（human / agent）をプロセスや鍵で確かめる**：Git リポジトリに書ける人はファイルを直接直せるので、CLI で確かめても守れない。申告で足りる
- **PR の状態を照合の必須条件にする**：`gh` と GitHub に依存し、PR のない業務で使えない
- **Plan を持たず Iteration だけで進める**：実行順と承認の記録を置く場所がない
