# ADR-004 エージェントと状態の記録

- ステータス：承認
- 更新日：2026-11-01

## 背景

AI エージェント（Claude Code・Codex など）がチケットを処理する。ツール側がエージェントを起動・監視して状態を進める設計と、エージェントが自分で CLI を呼んで状態を記録する設計がある。先行プロジェクトは前者（ヘッドレス起動と統合ターミナル起動）を作ったが、起動・worktree の準備・監視のどこかで失敗するたびに壊れた実行が残り、安定せずに削除した。実務は「人が動かすエージェントが CLI でチケットを操作する」形に落ち着いていた。

## 決定

### ツールはエージェントを起動も監視もしない

- `dg`・サーバー・VS Code 拡張は、チケットの作業のためにエージェントを起動しない。実行中のプロセスも監視しない
- エージェントは Bash から `dg … --json --actor agent` を呼んでチケットを読み書きし、データのファイルを直接編集しない。手順は `dg guide <topic>` が出す
- human と agent の区別は申告（`--actor`・`DEGUBOARD_ACTOR`）に基づく。Skill と guide の手順が必ず agent を名乗ることで、Workflow が `by: [human]` で人に限った遷移をエージェントから遠ざける。権限管理や偽装の防止はしない（同じリポジトリに書ける人を信頼する）
- Claude Code 向けには、段階ごとに `dg guide <topic>` を読む薄い Skill（`/dgimport` など）を配る。ほかのエージェントは同じ手順に従う。特定の AI 製品に依存する処理は Adapter（[ADR-007](ADR-007-architecture.md)）に閉じる

### 状態はチケットのブランチの事実で前進させる

- 成果をリポジトリに残すチケットは `branch` を持つ。`dg sync`（と画面の同期のボタン）は、そのブランチについて Git から事実を集め、ワークフローの `reconcile` 規則で状態を導き、今より先のときだけ書き換える
- 事実は Git だけで取れるものを基本にする：`branch_exists`（ローカルかリモートにある）、`branch_pushed`（リモートにある）、`branch_merged`（先端が `git.base_branch` の真の祖先。先端が base と同じなら切ったばかりのブランチとみなして偽にする。ff マージの直後は base が進むか PR の事実で拾う）
- commit のないブランチは base が進むと先端が真の祖先になり、グラフだけでは ff マージ後のブランチと区別できない（2026-10-31 に claim 直後の 3 枚が照合で誤って done になった）。そこで in_progress で push していないブランチは作業がまだないとみなして `branch_merged` を偽にする。review に進めたブランチと push 済みのブランチは祖先判定だけで決めるので、ff マージは従来どおり拾える。push していないブランチを in_progress のままローカルで ff マージした形は拾えず、人が `ticket move` で進める
- 照合の結果には当てはまった規則の条件（`when`）を根拠として残し、誤判定の原因を後から追えるようにする
- PR の事実（`pr_open`・`pr_merged`・`pr_draft`）は `gh` が使えるときだけ取り、software-development ワークフローが任意で使う。`gh` がなくても照合は成り立つ。チケットに `pr` がなければブランチ名で PR を引き、見つけた番号を `pr` に記録する（エージェントが記録し忘れても PR の記録が残る）
- 後退を指す事実（消えたブランチ・マージされずに閉じた PR）は書き換えずに警告する。同じ照合で done に進むときは、マージ後に消したブランチなので警告しない。PR がまだないだけの形は閉じた PR と警告しない。取れなかった事実は不明として扱い、前進の判定では偽と読む
- PR の要らない作業（データの整備・確認）は `branch` を記録せず照合から外す。エージェントが受け入れ条件をすべて確かめて done にし、残れば review に置いて人に頼む

### 排他は claim の push で決める

- 着手（todo → in_progress）は `dg ticket claim` で行う。claim は `status`・`assignee`・`branch` のコミットを push できたときに取得とする。拒否されたら取り込み直して判定し直す
- 同一マシンの Run の二重起動は、`deguboard-local/locks/runs` のロックの中で実行中の Run を見て拒む。Git 管理外で、チーム間の排他には使わない
- 応答のない claim は人が確かめてから `dg ticket unclaim --force` で解除する。生存監視はしない

### 主体の ID はユーザ名と種別で、起票者と担当者を分けて記録する

- 主体の ID は `<ユーザ>`（人）か `<ユーザ>/agent`（そのユーザの AI）の 1 文字列。ユーザ名は git の `user.name`（`--user` / `DEGUBOARD_USER` で変えられる）、種別は `--actor` の申告。ホスト名は含めない
- チケットは起票者（`created_by`）と担当者（`assignee`）を分けて持つ。起票者は起票を指示・承認した人か、人の確認を経ずに起票した AI で、既定は操作した主体。エージェントは人の指示で起票するとき `--created-by human` でユーザ本人を書く。担当者は claim で claim した主体になり、create / update で前もって付けてもよい
- 同じユーザの人と AI は互いの claim を force なしで外せる。AI の作業はそれを動かした人に帰属する

### Run は受動型で記録する

- エージェント（または Skill）が `dg run start <ticket> <step>` と `dg run finish <run>` を呼ぶ。実行中は `deguboard-local/runs/` に置き、finish が集計を `runs/` に書く
- ツールが Run を見失っても、チケットの状態はブランチの事実で進む
- 終了していない Run は `dg run list --running` で見せ、人かエージェントが `finish --result interrupted` で閉じる。自動復旧はしない
- 並列実行・修正ループ・自動マージ（`auto.merge` で許したとき）も Skill 側が `dg ticket list --ready` を見て進める。スケジューラは置かない

### Plan を第一級のエンティティにする

- 「どのチケットをどの順で（依存と計画内の待ち）進めるか」と承認状態（承認者・日時）、範囲と方針を `plans/p7.yaml` に持つ
- 進捗は Plan に書かず、チケットの状態から都度求める。Plan に書き込むのは作成・承認・終了のときだけ
- 1 つのチケットは同時に 1 つの開いた Plan にしか入らない
- Plan は残ったチケットがあっても閉じられる（立て直しで閉じるため）

## 理由

- 起動と監視を持たないと、ツールはエージェントの有無や実行の状態に左右されず、保守するコードが減る。排他と状態を Git の事実だけで決められる
- ブランチの事実は作業の結果として必ず残り、取り逃しがない。PR に依存しなければ、PR のない業務（コンサルティングなど）でも同じ仕組みで動く
- Git を compare-and-swap として使えば、サーバーなしで claim を atomic にできる
- 受動型の Run は、人が Claude Code を普通に動かす対話がそのまま記録として残る。能動的に起動する仕組みは、その上に後から足せる
- ID にホスト名を含めないのは、同じ人が別の PC から操作しても同じ人であるため。種別を ID に含めるのは、同じマシンで人と AI が動くと区別がつかず、AI がどれだけ起票・作業したかを後から数えられないため。起票者と担当者を分けるのは、AI が起票して人が進める、人が起票して AI が進める、のどちらも普通にあるため
- Plan を分けるのは、Epic は目的の範囲、Iteration は期間、Plan は実行順、Run は実績と役割が違うため。進捗を書かないのは、push の衝突を減らすため

## 採らなかった案

- **ツールがエージェントをヘッドレス起動して監視する**：先行プロジェクトで安定せず削除された。失敗した実行とロックが残る
- **実行中のプロセスを監視して状態を進める**：監視の失敗が状態の誤りになる。事実から導けば監視は要らない
- **ロックサーバーや DB による排他**：常駐サーバーが要り、オフラインで使えない
- **主体（human / agent）をプロセスや鍵で確かめる**：Git リポジトリに書ける人はファイルを直接直せるので、CLI で確かめても守れない。申告で足りる
- **ID にホスト名を含める（`eiki@laptop`）**：最初の版の形。同じ人が別の PC だと別人になり、人と AI の区別がつかなかった
- **ユーザ名と種別を 2 フィールドにする（`assignee` と `assignee_kind`）**：絞り込みはしやすいがフィールドが倍になる。`/agent` の接尾辞で足りる
- **PR の要らない作業に専用の Workflow（no-pr）を足す**：PR が要るかは 1 枚ずつの性質なので claim の指定で足りる
- **PR の状態を照合の必須条件にする**：`gh` と GitHub に依存し、PR のない業務で使えない
- **claim の時刻や base の SHA を記録して、先端がそれより進んだときだけ merged とみなす**：claim のあとに base が進んでからブランチを切ると、切ったばかりの先端が記録より新しくなり、同じ誤判定が残る。push の有無は Git の事実だけで取れ、エージェントの手順（作業を積んでから push する）と合う
- **Plan を持たず Iteration だけで進める**：実行順と承認の記録を置く場所がない
