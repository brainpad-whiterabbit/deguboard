# ADR-004 エージェントと状態の記録

- ステータス：承認
- 更新日：2026-11-07

## 背景

AI エージェント（Claude Code・Codex など）がチケットを処理する。ツール側がエージェントを起動・監視して状態を進める設計と、エージェントが自分で CLI を呼んで状態を記録する設計がある。先行プロジェクトは前者（ヘッドレス起動と統合ターミナル起動）を作ったが、起動・worktree の準備・監視のどこかで失敗するたびに壊れた実行が残り、安定せずに削除した。実務は「人が動かすエージェントが CLI でチケットを操作する」形に落ち着いていた。

## 決定

### ツールはエージェントを起動も監視もしない

- `dg`・サーバー・VS Code 拡張は、チケットの作業のためにエージェントを起動しない。実行中のプロセスも監視しない（EX-1）
- エージェントは Bash から `dg` を呼んでチケットを読み書きし、手順は `dg guide <topic>` が出す（AG-1）
- 主体（human / agent）は Adapter のフックが決める。Claude Code では SessionStart フックが、そのセッションの環境に `DEGUBOARD_ACTOR=agent` を入れ、dg はそれを読んで agent とする。フックのない製品では申告（`--actor` か `DEGUBOARD_ACTOR`）に従い、申告がなければ human になる。その製品では Skill と guide の手順が必ず agent を名乗る。こうして Workflow が `by: [human]` で人に限った遷移をエージェントから遠ざける。フックは環境を入れるだけで、エージェントを起動も監視もしない。権限管理や偽装の防止はしない（同じリポジトリに書ける人を信頼する）
- Claude Code 向けには guide を読む薄い Skill を配り（AG-2）、ほかのエージェントは同じ手順に従う。特定の AI 製品に依存する処理は Adapter（[ADR-007](ADR-007-architecture.md)）に閉じる

### 状態はチケットのブランチの事実で前進させる

- 成果をリポジトリに残すチケットは `branch` を持ち、照合がそのブランチの事実から `reconcile` 規則で状態を前進させる（ST-4）
- 事実は Git だけで取れるもの（ブランチの有無・push・base へのマージ）を基本にする（WF-2）
- commit のないブランチは base が進むと先端が真の祖先になり、グラフだけでは ff マージ後のブランチと区別できない（claim 直後のチケットが誤って done になった）。そこで in_progress で push していないブランチは merged とみなさない（ST-5）。push せずにローカルで ff マージした形は拾えず、人が `ticket move` で進める
- 照合の結果に根拠の規則の条件を残し、誤判定の原因を後から追えるようにする
- PR の事実は `gh` があるときだけ任意で使う。チケットに `pr` がなければブランチ名で引いて記録する（エージェントが記録し忘れても残る）。ブランチ名は使い回されるので、branch を記録する前にマージされた PR は根拠にしない（claim 直後のチケットが古い PR で done になった。ST-6）
- PR を見ない照合では、マージ済みのまま残った同じ名前のブランチが claim 直後に done を招く。そこで claim と branch の更新で、その名前を拒否する（ST-3）。claim の後に古いブランチが push し直される形は残る
- 後退を指す事実は書き換えずに警告し、取れなかった事実は前進の判定で偽と読む（ST-5）
- PR の要らない作業（データの整備・確認）は `branch` を記録せず照合から外し、エージェントが受け入れ条件を確かめて done にする（手順は `dg guide work`）

### 排他は claim の push で決める

- 着手は `dg ticket claim` で行い、そのコミットを push できたときに取得とする（SY-3）
- 同一マシンの二重起動は Git 管理外のローカルロックで拒み、チーム間の排他には使わない（SY-5）
- 応答のない claim は人が確かめてから強制の指定で外す。生存監視はしない（ST-7）

### 主体の ID はユーザ名と種別で、起票者と担当者を分けて記録する

- 主体の ID は `<ユーザ>`（人）か `<ユーザ>/agent`（そのユーザの AI）の 1 文字列で、ホスト名は含めない。ユーザ名の決め方は `dg --help` の `--user`。git config の `deguboard.user` を候補に持つのは、人ごとの設定で共有されず、環境変数の届かない VS Code でも効くから
- チケットは起票者（`created_by`）と担当者（`assignee`）を分けて持つ（意味は requirements の用語と TK-7）
- AI の作業はそれを動かした人に帰属し、同じユーザの人と AI は互いの claim を外せる（ST-7）

### Run は受動型で記録する

- Run は agent の `ticket claim`（RN-5）か `dg run start` で開き、エージェント（または Skill）が `dg run finish` で閉じる。Git に入れるのは完了時の集計だけ（RN-3）
- ツールが Run を見失っても、チケットの状態はブランチの事実で進む
- 終了していない Run は人かエージェントが `interrupted` で閉じ、自動復旧はしない（EX-2）
- 並列実行・修正ループ・自動マージも guide 側が Plan の待ちを見て進め、スケジューラは置かない。上限は負荷とエージェントの都合で決まるので config でなく手順に書く（EX-3）

### Plan を第一級のエンティティにする

- どのチケットをどの順で進めるかと承認・範囲・方針を Plan（`plans/p7.yaml`）に持つ（形は requirements の 5.7）
- 進捗は Plan に書かず、チケットの状態から都度求める（PL-2）
- Plan は残ったチケットがあっても閉じられる（立て直しで閉じるため。PL-4）
- チケットの難しさの段階（`tier`）を Plan の details に、段階からモデル名への対応を `config.yaml` の `models.*` に置く。そのモデルで起動するのは手順

## 理由

- 起動と監視を持たないと、ツールはエージェントの有無や実行の状態に左右されず、保守するコードが減る。排他と状態を Git の事実だけで決められる
- ブランチの事実は作業の結果として必ず残り、取り逃しがない。PR に依存しなければ、PR のない業務（コンサルティングなど）でも同じ仕組みで動く
- Git を compare-and-swap として使えば、サーバーなしで claim を atomic にできる
- 受動型の Run は、人が Claude Code を普通に動かす対話がそのまま記録として残る。能動的に起動する仕組みは、その上に後から足せる
- 主体を申告から環境の設定に移すのは、2026-11 の調査で `--actor` の申告が抜けた呼び出しが human として通り、`by: [human]` と `actor.human_only` の制限を素通りしたため。申告の抜けは手順では防げない
- ID にホスト名を含めないのは、同じ人が別の PC から操作しても同じ人であるため。種別を ID に含めるのは、同じマシンで人と AI が動くと区別がつかず、AI がどれだけ起票・作業したかを後から数えられないため。起票者と担当者を分けるのは、AI が起票して人が進める、人が起票して AI が進める、のどちらも普通にあるため
- Plan を分けるのは、Epic は目的の範囲、Iteration は期間、Plan は実行順、Run は実績と役割が違うため。進捗を書かないのは、push の衝突を減らすため
- 段階を Plan に書くのは、難しさが範囲・方針と一緒に計画で決まり、承認の表で人が確かめられるため

## 採らなかった案

- **ツールがエージェントをヘッドレス起動して監視する**：先行プロジェクトで安定せず、失敗した実行とロックが残った
- **実行中のプロセスを監視して状態を進める**：監視の失敗が状態の誤りになる
- **ロックサーバーや DB による排他**：常駐サーバーが要り、オフラインで使えない
- **主体（human / agent）をプロセスや鍵で確かめる**：リポジトリに書ける人はファイルを直接直せるので、CLI で確かめても守れない
- **申告だけに頼る（今まで）**：申告の抜けが human として通り、人に限った制限を守れなかった。毎回の申告を手順で求めても、抜けは防げなかった
- **ID にホスト名を含める（`eiki@laptop`）**：同じ人が別の PC だと別人になる
- **ユーザ名と種別を 2 フィールドにする（`assignee` と `assignee_kind`）**：フィールドが倍になる。`/agent` の接尾辞で足りる
- **PR の要らない作業に専用の Workflow を足す**：PR が要るかは 1 枚ずつの性質なので claim の指定で足りる
- **PR の状態を照合の必須条件にする**：`gh` と GitHub に依存し、PR のない業務で使えない
- **claim の時刻や base の SHA より先端が進んだときだけ merged とみなす**：claim の後に base が進んでから切ったブランチで同じ誤判定が残る
- **先端のコミット日時が `branch_at` より古ければ merged とみなさない**：PC ごとの時計のずれで判定が変わる
- **Plan を持たず Iteration だけで進める**：実行順と承認の記録を置く場所がない
- **段階（`tier`）をチケットに、モデル名を Plan に書く**：難しさは進め方の判断でチケットの約束でない。モデル名は Adapter と世代に縛られるので、計画の記録でなく環境の設定に置く
