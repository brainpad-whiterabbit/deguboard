# ADR-001 文書の方針

- ステータス：承認

## 要約

文書は読み手ごとに入口を 1 つ決め、要件定義書は利用者への約束だけを書き、細部はコード・テスト・ヘルプを正本にする。ADR は今の判断と理由だけを持つ。規約（毎回守る決まり）の正本は CLAUDE.md で、ここには写さない。

## 背景

deguboard は AI エージェント（Claude Code など）が主に実装する。エージェントは文書を丸ごと読みがちで、文書が大きいほど毎回の作業が遅く高くなる。仕様の細部を ADR・要件定義書・README・guide・コメントに写すと、1 つの変更が 3〜4 か所に波及し、ずれた箇所が手直しになる（前の運用では手直しの理由の約 3 割が、コメント・ADR・README・guide と実装のずれだった）。

## 決定

### 読み手ごとの入口

最初に読む文書を読み手ごとに 1 つに決める。ほかの文書は、入口から作業に応じて要る節だけを引く。

読み手は Claude（毎回）・利用者・開発者（人）・仕様を知りたい人・作業中のエージェントで、入口はそれぞれ `CLAUDE.md`・`README.md`・`docs/development.md`・`docs/requirements.md`・`dg guide <topic>`。仕様を知りたい人が引くものは requirements.md の冒頭に書く。

作業の手順は docs に置かず、`dg guide` として dg に同梱する。作業中のエージェントは docs を読まず、本文と読み込みは Core が持つ（[ADR-030](ADR-030-flow-and-guide-in-core.md)）。人向けの手順は development.md に置く。

### 要件定義書に書くもの

利用者（人・エージェント）から外に見え、変えると利用者に影響する「約束」だけを書く。

- コマンドがあることと、何をするか（書き込むか・push するか・止まる条件）
- データ（Ticket・Epic・Iteration・Plan・Workflow・Run・config）の配置・必須の項目・振る舞いに効く項目の意味と項目どうしの決まり。項目の全体と型は Zod のスキーマが正本で、要件定義書に列挙しない
- 状態遷移の約束（既定と制約の仕組みは該当 ADR を参照する）
- 画面に何が出て、何ができるか
- 限界

実装を読めばわかり、変えても約束が壊れないもの（CLI オプションの細部、集計の規則、画面の並び・色・文言）は書かない。要件には `TK-1` のような ID を付け、文を縮めても ID と見出しのアンカーは変えず、消した ID は再利用しない。

要件定義書の 1 項の字数の上限は 250 字（リンクの記法を含む）。超えた項は細部が入った印なので、細部を正本へ移して縮める。

### 正本と各文書の書く範囲

| 置き場所                     | 書く                                                                                                      | 書かない                              |
| ---------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| コード・テスト・`--help`     | 振る舞いの細部（項目の全体と型、オプション、集計、画面の並びと文言）。正本                                | 文書への写し、出力の要件 ID・ADR 番号 |
| requirements.md              | 上の「書くもの」の約束と、細部の正本への案内                                                              | 細部                                  |
| ADR                          | 判断の背景・今の決定・理由・採らなかった案                                                                | 細部、今の仕様の写し、経緯            |
| `dg guide`（dg に同梱）      | 作業の手順・判断・止める条件。dg と一緒に変える                                                           | 約束の細部                            |
| コードのコメント             | 「なぜ」と、守る約束の要件 ID                                                                             | 振る舞いの列挙、文書の写し            |
| README.md・README.ja.md      | 利用者の入口（導入と、画面のタブごとの使い方の流れ）。同じ節の構成で置く                                  | 規約・約束・細部                      |
| docs/how-it-works.md・.ja.md | 全体の構成・Run の範囲・次の一手の図と、その決まり。英語版と日本語版を同じ節の構成で置き、README から引く | 依存の規則・判断・要件の細部の写し    |
| docs/usage.md・usage.ja.md   | README に収めない、人がする操作。英語版と日本語版を同じ節の構成で置き、README の Tips から引く            | ヘルプ・guide・約束の写し             |
| docs/guide-notes/            | 作業の規則と根拠 1 行・外す条件（振り返りで確かめる）。英語で書き、dg guide に差し込む                    | 約束・config の写し、見出し（#）      |
| development.md               | 開発者（人）の手順と、このリポジトリ固有の決まり                                                          | CLAUDE.md の規約の写し                |
| CLAUDE.md                    | 毎回守る規約                                                                                              | 手順・細部                            |

要件の ID はコードとテストが参照する。ID は約束と守るコードを結ぶ唯一の手がかりなので消さず、機械で照らす（検査の中身は `scripts/check-docs.mjs` の冒頭）。

### ADR を書く場面

ADR に書くのは、移行・約束とデータの形・構成と技術・退ける案のどれかに当たる判断だけで、その基準は CLAUDE.md にある。当たらないもの（端のケース・バグ修正・版の扱い・1 PR で戻せる規則）は、テストとコードのコメントの「なぜ」に置く。

### ADR は今の判断だけを書き、判断を変える PR で直す

ADR の書き方（本文の中身、判断を変える PR での直し方、採らなかった案、削除）の規約は CLAUDE.md にある。ここには理由と、数字の決めだけを置く。

- 1 本の目安は 8,000 字。超えたら分割・整理を起票する（`mise run check:docs` が警告する）
- 機械で守れる判断は、テスト・lint・フック・検査に守らせる。ADR は理由の説明にとどめる

### 重複と参照の検査

文書の重複・参照の切れ・要件の 1 項の上限・ADR の字数は `mise run check:docs` が機械で検査する。検査の中身は `scripts/check-docs.mjs` の冒頭が正本。

### 言語

- 言語の決まり（人が読む文と dg が出す文の言語、例外）は CLAUDE.md の「コードの規約」が正本で、dg が出す文を英語にする理由は「理由」の節に置く
- dg の既定の値も dg の文として英語で持つ。画面は、値が既定と同じ文のときだけ訳して出す（細部は `packages/web/src/l10n.ts`）
- エージェントが書く文章（チケット・PR・コミット・人への返答）は、リポジトリの既存の文章と人の依頼の言語に合わせる

## 理由

- 入口が 1 つなら、エージェントは最初に何を開くかで迷わず、要らない文書を開かない
- 細部をいつでも消せれば、決めた時点の細部が ADR に溜まり続けない。ADR を今の判断と理由だけにすれば、読む人は細部に惑わされず判断を読める
- 約束だけを書けば、実装の細部を変える PR で要件定義書を直さずに済む。細部を写すと二重の正本になり、ずれたときにどちらが正しいか決められない
- AI で開発すると小さな仕様変更の頻度が高い。細部を正本に置き、ADR は今の判断と理由だけを書けば、細部の変更で ADR を直す必要がない。判断を変えたときだけ、同じ PR で 1 本を直す
- 本文を今の判断に直せば、読む人は古い決定を正として読まず、一覧から 1 本を引けば今の判断に当たる。古い本文を残すと、エージェントはそれを今の決定と読み違える。経緯は Git の履歴で足りる
- 番号を変えず使い回さないので、判断を変えたときに ADR を指す参照は切れず、別の判断を指すこともない。統合・削除された ADR を指す参照は切れる
- 採らなかった案に 1 行で残せば、覆した判断でも同じ議論を繰り返さず、本文の書き換えで消えない
- ADR を書く場面を 4 つに限れば、端のケースやバグ修正で ADR が増えない。テストは振る舞いを機械で守るので、細部の正本はテストに置き、「なぜ」だけを近くのコメントに書けば、コードを変えた人が同じ場所で直せる
- 重複と参照を直接検査すれば、同じ約束が 2 か所に書かれたことに気づける。要件の 1 項は約束と案内で足りるので、上限を超えたことは細部が入った印になる
- 古い記述が残ると、エージェントはそれを正として読み、ずれた実装をする。足すだけの運用では文書が膨らみ、重複が増える
- 文書のずれを PR の見直しで重い指摘にすると、変えていない文書の修正が PR ごとに積もる。Iteration の見直しに集めれば、1 回でまとめて直せる
- dg の文を英語にすれば、言語を問わず利用者とエージェントが読める。手順が英語でも、エージェントの書く文章を既存の文章と依頼の言語に合わせれば、チームの記録はチームの言語で残る
- 既定の値も dg の文なので英語で揃える。訳すのを既定と同じ文に限れば、人が書いた値を訳して見せない
- `--help` と dg の出力に要件 ID と ADR 番号を書かないのは、読み手が番号を引けず、文の中の番号が読み手の手がかりにならないため
- コードが ADR の番号を指す参照を先頭のコメントに寄せると、ADR を統合・削除したときに直す場所が 1 か所で済む

## 採らなかった案

- **細部の変更ごとに ADR を書き、古い ADR に注記を足す**：有効な決定が読み取れなくなる
- **判断ごとに新しい番号で置き換える**：古い本文と失効の印が溜まり、今の判断を知るのに何本もたどることになる（経緯は Git で足りる）
- **節・項ごとに失効の印を付ける**：印の管理が要り、有効な判断まで失効に見える
- **コードのコメントから要件 ID を消す**：約束と守るコードの対応が消え、機械で照らせなくなる
- **文書全体の大きさの予算を残す**：細部が入ったことを見ず、文を詰めさせる
- **端のケースやバグ修正ごとに ADR を書く**：判断が多数の ADR に散り、今の判断を知るのに何本も読むことになる
- **置き換え済みの ADR の本文を残す**：失効した細部を今の決定と読み違える
- **細部の削除を移行に限る**：細部が消せず、消すために別の ADR を書くことになる
- **ADR を正本にし、要件定義書は概要だけ**：今の仕様を知るのに複数の ADR をたどることになる
- **要件定義書を節ごとに複数ファイルに分ける**：細部を写す書き換えは減らず、どこに書くかの判断が増える
- **guide・Skill・dg の出力を日英の 2 本立てにする**：変更の多い文を 2 本持つと片方がずれる
- **手順書を docs に置く**：手順は CLI の版と一緒に変わるので、CLI に同梱した方がずれない
- **この決定を新しい ADR で置き換え、ADR-001 を置き換えにする**：文書の入口の規則が別の ADR に移ると、入口の規則を 2 か所で読むことになる
