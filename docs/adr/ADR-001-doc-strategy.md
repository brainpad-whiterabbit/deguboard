# ADR-001 文書の方針

- ステータス：承認
- 更新日：2026-11-09

## 背景

deguboard は AI エージェント（Claude Code など）が主に実装する。エージェントは文書を丸ごと読みがちで、文書が大きいほど毎回の作業が遅く高くなる。先行プロジェクトでは、仕様の細部を ADR と要件定義書の両方に写し、小さな変更のたびに ADR を増やした結果、要件定義書が 128KB、ADR が 67 本・670KB に膨らみ、後から運用を立て直すことになった。deguboard ではその立て直した後の形で始める。それでも s17・s19 の手直しの理由 218 件のうち 70 件（32%）は、コメント・ADR・README・guide が実装とずれていたことだった。1 つの変更が 3〜4 か所に波及し、漏れが手直しになる。

細部の正本をコード・テスト・ヘルプと決めた後も、ADR を書く基準が「細部や 1 PR で戻せるものには書かない」の一文だけだったので、端のケースやバグ修正ごとに ADR が増えた（ADR-014〜018・022・024）。今の Run の判断を知るのに約 10 本を読む。細部を消してよいのは ADR-002〜010 の移行に限られ、ADR-011 以降の細部は消せなかった（ADR-024 は ADR-008 の版の細部を消せずに生まれた）。要件定義書にも ADR の決定の写しが入り、1 項で 2,700 字近いものがある。

## 決定

### 読み手ごとの入口

最初に読む文書を読み手ごとに 1 つに決める。ほかの文書は、入口から作業に応じて要る節だけを引く。

読み手は Claude（毎回）・利用者・開発者（人）・仕様を知りたい人・作業中のエージェントで、入口はそれぞれ `CLAUDE.md`・`README.md`・`docs/development.md`・`docs/requirements.md`・`dg guide <topic>`。Claude は CLAUDE.md から、development.md・requirements.md は要る節だけ、ADR は一覧から番号で引く。仕様を知りたい人が引くものは requirements.md の冒頭に書く。

- リポジトリの規約（毎回守る決まり）は CLAUDE.md にだけ書く。README と development.md には書き写さず、参照する
- 特定の作業のときだけ要る手順は CLAUDE.md に書かない。人向けは development.md に置いて CLAUDE.md から参照し、エージェント向けは docs に置かず、`dg guide` として dg に同梱する（作業中のエージェントは docs を読まない。本文と読み込みは Core が持つ。[ADR-030](ADR-030-flow-and-guide-in-core.md)）

### 要件定義書に書くもの

利用者（人・エージェント）から外に見え、変えると利用者に影響する「約束」だけを書く。

- コマンドがあることと、何をするか（書き込むか・push するか・止まる条件）
- データ（Project・Ticket・Epic・Iteration・Plan・Workflow・Run・config）の配置・必須の項目・振る舞いに効く項目の意味と項目どうしの決まり。項目の全体と型は Zod のスキーマが正本で、要件定義書に列挙しない
- 状態遷移の約束（既定と制約の仕組みは該当 ADR を参照する）
- 画面に何が出て、何ができるか
- 限界

実装を読めばわかり、変えても約束が壊れないもの（CLI オプションの細部、集計の規則、画面の並び・色・文言）は書かない。正本はヘルプ・コード・テストにし、要件定義書からは正本のファイルを案内する。要件には `TK-1` のような ID を付け、文を縮めても ID と見出しのアンカーは変えず、消した ID は再利用しない。

1 項（`- TK-1` の箇条書きの 1 項目と、その下の字下げした行）は、約束の 1〜2 文と細部の正本への案内だけにする。ADR の決定を写さず、ADR は番号で案内する。1 項の字数の上限は 250 字（リンクの記法を含む）で、超えた項は check:docs が ID 付きで指摘する。超えたら細部を正本へ移して縮める。値は、この決定の時点の 105 項の中央値が 120 字で、約束の 2 文と案内の 1 文が 250 字に収まることから決めた（超えていたのは 20 項）。

### 正本と各文書の書く範囲

| 置き場所                 | 書く                                                                       | 書かない                   |
| ------------------------ | -------------------------------------------------------------------------- | -------------------------- |
| コード・テスト・`--help` | 振る舞いの細部（項目の全体と型、オプション、集計、画面の並びと文言）。正本 | 文書への写し               |
| requirements.md          | 上の「書くもの」の約束と、細部の正本への案内                               | 細部                       |
| ADR                      | 判断の背景・決定・理由・採らなかった案                                     | 細部、今の仕様の写し       |
| `dg guide`（dg に同梱）  | 作業の手順・判断・止める条件。dg と一緒に変える                            | 約束の細部                 |
| コードのコメント         | 「なぜ」と、守る約束の要件 ID                                              | 振る舞いの列挙、文書の写し |
| README.md・README.ja.md  | 利用者の入口（導入・使い方）。同じ節の構成で置く                           | 規約・約束・細部           |
| development.md           | 開発者（人）の手順と、このリポジトリ固有の決まり                           | CLAUDE.md の規約の写し     |
| CLAUDE.md                | 毎回守る規約                                                               | 手順・細部                 |

要件の ID はコードとテストが参照する。参照をなくさず、機械で照らす。ID は約束と守るコードを結ぶ唯一の手がかりで、消すと約束の所在が分からなくなるため。ID が要件定義書にあるかは `mise run check:docs` が検査する。

### ADR を書く場面

ADR は、次のどれかに当たる判断だけに書く。

- 戻すのに移行が要る（データの保存の形・場所・ID を変えると、既にあるデータを移す必要がある）
- 利用者に見える約束とデータの形を決める・変える
- 構成と技術を選ぶ（パッケージの分け方と依存の向き、使う道具と仕組み）
- また提案されそうな案を退ける（理由を残さないと同じ議論を繰り返す）

当たらないもの（端のケースの扱い・バグ修正・道具の版の扱い・1 PR で戻せる規則）は ADR に書かない。振る舞いはテストが正本で、「なぜ」はテスト名とコードのコメントに書く。利用者への約束が変わるなら要件定義書の項を直す。

### ADR は判断ごとに 1 本、判断と理由は書き換えない

- 判断を変えるときは新しい ADR を書き、古い ADR のステータスを `置き換え（ADR-0xx）` にする。新しい ADR に何を置き換えたかを書く
- 置き換え済みの ADR の本文は、タイトル・ステータス・置き換えた先の 1 行（「ADR-0xx で置き換えた。経緯は Git の履歴にある」）だけに削ってよい。削った節を指すリンクとアンカーは、同じ変更で置き換えた先へ張り替える
- 一節だけを置き換えるときは、新しい ADR にその節を置き換えると書き、古い ADR の該当節の頭に「※ ADR-0xx で置き換え（この節は失効）」の 1 行を足す。ステータスも一覧も変えない
- 節の中の項（箇条書きの 1 項目）だけを置き換えるときは、新しい ADR にその項を置き換えると書き、古い ADR の該当項の頭（`- ` の直後）に印を前置きする。印は句点で区切り、同じ行で項の本文を続ける。項の全体なら「※ ADR-0xx で置き換え（この項は失効）。」、項の一部なら「※ ADR-0xx で置き換え（この項の「<失効する文言>」の部分は失効）。」と書く（`<失効する文言>` は、失効する文言そのものに置き換える）。節の頭に置くと、有効な判断まで失効に見えるため項の頭に置く
- まとめ直し：1 本の ADR の失効の印（節と項を合わせて数える）が 2 つになったら、その ADR 全体を置き換える 1 本の ADR に、今の判断と理由をまとめ直す。2 つ目の印を足す変更でまとめ直すのが基本で、既に 2 つ以上ある ADR は次にその ADR に触れる変更でまとめ直す。同じ主題で互いに置き換え合う ADR は、まとめて 1 本に置き換える
- 細部を消す：判断と理由を変えずに、細部を正本（コード・テスト・ヘルプ・設定ファイルのコメント）へ移して削ることは、どの ADR でもいつでもよい。「予定。実装は tNNN」の注記と、「制限」の節の端のケースも細部に入る。正本が見つからない細部は、先に正本へ移すか残す。ADR ごとに別の PR でよい
- 決めたあとの ADR は、判断と理由を書き換えない。書き換えてよいのは、誤字、リンクとアンカーの切れの直し、置き換えの印（ステータスと失効の印。節の頭の 1 行と項の頭の前置き）、置き換え済みの本文の削り、細部を消すことと、ADR-001 自身の改訂だけ。小さな変更は要件・コード・テスト・guide で直す
- 採らなかった案は、また提案されそうな案だけを、1 案 1 行の理由で書く（経緯は Git に任せる）
- ADR-001 を変える改訂は、新しい ADR を書かず ADR-001 を直接書き換える

### 一覧

`docs/adr/README.md` に「有効な ADR」の表（番号・タイトル・テーマ・更新日）を置く。置き換えられた ADR は有効の表から外し、「置き換え済み」の表（番号・置き換えた先）に移す。「テーマ」は一覧から引くための語、「更新日」は決定・理由を最後に変えた日（細部を消すこと・リンクの直し・失効の印（節の頭の 1 行と項の頭の前置き）では変えない）で、check:docs が本文と照らす。ADR を足す・置き換えるときは同じ変更で一覧も直す。番号はマージ前に main の最大番号を確かめる。

### 文書の見直し

- この PR が変えた約束・手順・規約の文書を、同じ PR で直していないのは規約の違反。PR の見直しで重い指摘にする
- この PR が変えていない文書の、前からあるずれは PR の見直しで重い指摘にしない。Iteration ごとの文書の見直し（`dg guide audit` の文書の観点）で 1 本の指摘表にまとめ、承認を得て直す

### 重複と参照の検査

文書全体の大きさの予算は持たない。大きさで見るのは要件の 1 項の上限だけで、これは文を詰めさせる予算ではなく、1 項に細部が入ったことを見つける印にする。`mise run check:docs` は次を検査する：

- 同じ約束・手順が正本の外の文書に重複していないか
- 要件の 1 項が上限（「要件定義書に書くもの」）を超えていないか
- コードとテスト（コメント・テスト名・文字列）が、置き換え済みの ADR を指していないか。置き換え済みの本文を削ると、指した先に判断が残らないため
- 参照の切れ：相対リンクと見出しアンカー、コードの要件 ID、コードの先頭コメントが指す ADR・requirements.md の節・docs のパスとアンカー・guide、文書と packages の .ts・.tsx の文字列とコメントの `dg guide <topic>` の「節」と英語の ``the "節" section of `dg guide <topic>` `` の形（バッククォートの有無によらず、guide-<topic>.md の見出し（括弧の補足を除いた名前を含む）と、節の中の太字の項目・一覧の先頭のコードと照らす）、ADR 一覧（有効・置き換え済み・更新日）、README.ja.md の節の構成、拡張の README のアンカー

重複の判定の細部は `scripts/check-docs.mjs` の冒頭に書く。

### 書き方

- 書き足さず書き換える。ADR を除く docs・README・CLAUDE.md・コードのコメントのどれでも、古い記述を残して新しい記述を足さない
- 古くなった記述は消す（ADR を除く。ADR は「判断と理由は書き換えない」の節に従う）。変更に直接関係がなくても、作業中に実装や仕様とずれた記述を見つけたら、その変更で消す。残すのは、消すと約束や理由がわからなくなるものだけ
- 参照はファイルのパスと見出しのアンカーで書く
- `dg guide` のファイルは oxfmt の整形の対象から外す（表の列をそろえる空白を入れないため）。セルは短く、表は手で書く
- 文書・コメント・テスト名は日本語で書く。例外は README.md と packages/cli/README.md で、GitHub・Marketplace・npm で最初に読まれる入口なので英語で書く。日本語の利用者向けに、README.md と同じ節の構成の README.ja.md を置き、先頭から互いに辿れるようにする（リンクと節の構成の検査は両方にかける）。README から指す docs は日本語のままにする

## 理由

- 入口が 1 つなら、エージェントは最初に何を開くかで迷わず、要らない文書を開かない
- 約束だけを書けば、実装の細部を変える PR で要件定義書を直さずに済む。細部を写すと二重の正本になり、ずれたときにどちらが正しいか決められない
- AI で開発すると小さな仕様変更の頻度が高い。細部を正本に置き、ADR は判断だけを書いて決めたら動かさなければ、小さな変更で ADR を直す必要がなく、ADR が細部に追従してずれることもない
- 判断を変えたときは、なぜ以前の判断をやめたかが後の判断に要るので、置き換えの ADR に残す。今の決定は有効な表から 1 本ずつ引ける
- ADR を書く場面を 4 つに限れば、端のケースやバグ修正で ADR が増えない。テストは振る舞いを機械で守るので、細部の正本はテストに置き、「なぜ」だけを近くのコメントに書けば、コードを変えた人が同じ場所で直せる
- 細部をいつでも消せれば、決めた時点の細部が ADR に溜まり続けない。判断と理由を変えないので、ADR の役目（なぜそう決めたか）は残る
- 失効の印が溜まると、今の判断を知るのに古い ADR と置き換えの ADR を何本もたどる。2 つでまとめ直せば、1 つの主題の今の判断は 1 本で読める
- 置き換え済みの本文は今の判断ではなく、残すとエージェントが今の決定と読み違える。経緯は Git の履歴から引ける
- 重複と参照を直接検査すれば、同じ約束が 2 か所に書かれたことに気づける。文書全体の大きさの予算は細部が入ったことを見ず、上限に合わせて文を詰める書き方にさせるので持たない。要件の 1 項は約束の 1〜2 文と案内で足りるので、項の上限を超えたことは細部が入った印になる
- 古い記述が残っていると、エージェントはそれを正として読み、ずれた実装をする。足すだけの運用では文書が膨らみ、重複が増える
- 文書のずれを PR の見直しで重い指摘にすると、変えていない文書の修正が PR ごとに積もる。Iteration の見直しに集めれば、1 回でまとめて直せる

## 採らなかった案

- **細部の変更ごとに ADR を書き、古い ADR に注記を足す**：先行プロジェクトで有効な決定が読み取れなくなった
- **ADR を直接書き換えて 1 本に保つ**：細部が ADR に溜まり、仕様変更のたびに ADR・要件・guide の書き換えが要った（s17・s19 の手直しの 70 件）
- **コードのコメントから要件 ID を消す**：約束と守るコードの対応が消え、機械で照らせなくなる
- **文書全体の大きさの予算を残す**：細部が入ったことを見ず、文を詰めさせる
- **端のケースやバグ修正ごとに ADR を書く**：ADR-014〜018・022 が足され、Run の判断が ADR-012〜018・022 の 8 本に散り、今の判断を知るのに約 10 本を読むことになった
- **置き換え済みの ADR の本文を残す**：失効した細部を今の決定と読み違える。経緯は Git の履歴で足りる
- **細部の削除を ADR-002〜010 の移行に限る**：後から書いた ADR の細部が消せず、版の細部を消すために ADR-024 を書くことになった
- **ADR を正本にし、要件定義書は概要だけ**：今の仕様を知るのに複数の ADR をたどることになる
- **要件定義書を節ごとに複数ファイルに分ける**：細部を写す書き換えは減らず、どこに書くかの判断が増える
- **手順書を docs に置く**：手順は CLI の版と一緒に変わるので、CLI に同梱した方がずれない
- **この決定を新しい ADR で置き換え、ADR-001 を置き換えにする**：文書の入口の規則が別の ADR に移ると、入口の規則を 2 か所で読むことになる
