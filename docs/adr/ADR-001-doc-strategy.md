# ADR-001 文書の方針

- ステータス：承認

## 要約

文書は読み手ごとに入口を 1 つ決め、要件定義書は利用者への約束だけを書き、細部はコード・テスト・ヘルプを正本にする。ADR は今の判断と理由だけを書き、判断を変える PR で同じ ADR の本文を直接書き換える（番号は変えず、履歴は Git に任せる）。docs（GitHub の入口の README.md と SECURITY.md、README から引く英語の docs/usage.md を除く）とコメントは日本語、dg がエージェントと利用者に出す文は英語で書く。

## 背景

deguboard は AI エージェント（Claude Code など）が主に実装する。エージェントは文書を丸ごと読みがちで、文書が大きいほど毎回の作業が遅く高くなる。先行プロジェクトでは仕様の細部を ADR と要件定義書の両方に写し、小さな変更のたびに ADR を増やした結果、文書が膨らみ、後から運用を立て直すことになった。deguboard ではその後の形で始める。それでも s17・s19 の手直しの理由 218 件のうち 70 件（32%）は、コメント・ADR・README・guide が実装とずれていたことだった。1 つの変更が 3〜4 か所に波及し、漏れが手直しになる。

細部の正本をコード・テスト・ヘルプと決めた後も、ADR を書く基準が「細部や 1 PR で戻せるものには書かない」の一文だけだったので、端のケースやバグ修正ごとに ADR が増え、今の判断を知るのに何本も読むことになった。

## 決定

### 読み手ごとの入口

最初に読む文書を読み手ごとに 1 つに決める。ほかの文書は、入口から作業に応じて要る節だけを引く。

読み手は Claude（毎回）・利用者・開発者（人）・仕様を知りたい人・作業中のエージェントで、入口はそれぞれ `CLAUDE.md`・`README.md`・`docs/development.md`・`docs/requirements.md`・`dg guide <topic>`。Claude は CLAUDE.md から、development.md・requirements.md は要る節だけ、ADR は一覧から番号で引く。仕様を知りたい人が引くものは requirements.md の冒頭に書く。

- リポジトリの規約（毎回守る決まり）は CLAUDE.md にだけ書く。README と development.md には書き写さず、参照する
- 特定の作業のときだけ要る手順は CLAUDE.md に書かない。人向けは development.md に置いて CLAUDE.md から参照し、エージェント向けは docs に置かず、`dg guide` として dg に同梱する（作業中のエージェントは docs を読まない。本文と読み込みは Core が持つ。[ADR-030](ADR-030-flow-and-guide-in-core.md)）

### 要件定義書に書くもの

利用者（人・エージェント）から外に見え、変えると利用者に影響する「約束」だけを書く。

- コマンドがあることと、何をするか（書き込むか・push するか・止まる条件）
- データ（Project・Ticket・Epic・Iteration・Plan・Workflow・Run・config）の配置・必須の項目・振る舞いに効く項目の意味と項目どうしの決まり。項目の全体と型は Zod のスキーマが正本で、要件定義書に列挙しない
- 状態遷移の約束（既定と制約の仕組みは該当 ADR を参照する）
- 画面に何が出て、何ができるか
- 限界

実装を読めばわかり、変えても約束が壊れないもの（CLI オプションの細部、集計の規則、画面の並び・色・文言）は書かない。正本はヘルプ・コード・テストにし、要件定義書からは正本のファイルを案内する。要件には `TK-1` のような ID を付け、文を縮めても ID と見出しのアンカーは変えず、消した ID は再利用しない。

1 項（`- TK-1` の箇条書きの 1 項目と、その下の字下げした行）は、約束の 1〜2 文と細部の正本への案内だけにする。ADR の決定を写さず、ADR は番号で案内する。1 項の字数の上限は 250 字（リンクの記法を含む）で、超えた項は check:docs が ID 付きで指摘する。超えたら細部を正本へ移して縮める。

### 正本と各文書の書く範囲

| 置き場所                   | 書く                                                                                           | 書かない                   |
| -------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------- |
| コード・テスト・`--help`   | 振る舞いの細部（項目の全体と型、オプション、集計、画面の並びと文言）。正本                     | 文書への写し               |
| requirements.md            | 上の「書くもの」の約束と、細部の正本への案内                                                   | 細部                       |
| ADR                        | 判断の背景・今の決定・理由・採らなかった案                                                     | 細部、今の仕様の写し、経緯 |
| `dg guide`（dg に同梱）    | 作業の手順・判断・止める条件。dg と一緒に変える                                                | 約束の細部                 |
| コードのコメント           | 「なぜ」と、守る約束の要件 ID                                                                  | 振る舞いの列挙、文書の写し |
| README.md・README.ja.md    | 利用者の入口（導入と、画面のタブごとの使い方の流れ）。同じ節の構成で置く                       | 規約・約束・細部           |
| docs/usage.md・usage.ja.md | README に収めない、人がする操作。英語版と日本語版を同じ節の構成で置き、README の Tips から引く | ヘルプ・guide・約束の写し  |
| development.md             | 開発者（人）の手順と、このリポジトリ固有の決まり                                               | CLAUDE.md の規約の写し     |
| CLAUDE.md                  | 毎回守る規約                                                                                   | 手順・細部                 |

要件の ID はコードとテストが参照する。参照をなくさず、機械で照らす。ID は約束と守るコードを結ぶ唯一の手がかりで、消すと約束の所在が分からなくなるため。

### ADR を書く場面

ADR は、次のどれかに当たる判断だけに書く。

- 戻すのに移行が要る（データの保存の形・場所・ID を変えると、既にあるデータを移す必要がある）
- 利用者に見える約束とデータの形を決める・変える
- 構成と技術を選ぶ（パッケージの分け方と依存の向き、使う道具と仕組み）
- また提案されそうな案を退ける（理由を残さないと同じ議論を繰り返す）

当たらないもの（端のケースの扱い・バグ修正・道具の版の扱い・1 PR で戻せる規則）は ADR に書かない。振る舞いはテストが正本で、「なぜ」はテスト名とコードのコメントに書く。利用者への約束が変わるなら要件定義書の項を直す。

### ADR は今の判断だけを書き、判断を変える PR で直す

- ADR の本文は、今の判断と理由だけを書く。判断を変える PR は、同じ PR でその ADR の本文を直接書き換える。番号は変えない
- 経緯は Git の履歴に任せ、本文に以前の判断や覆した経緯を書かない。覆した判断のうち、また提案されそうなものだけは「採らなかった案」に 1 行（案と退けた理由）で残す。エージェントは Git の履歴を読まないため
- テーマごと要らなくなった ADR と、統合で元になった ADR は、ファイルごと削除する。判断を変えて ADR を書く場面に当たらなくなった ADR も同じに削除する。番号は使い回さない
- PR が誤りにした ADR の細部は、その PR で消す。細部は正本（コード・テスト・ヘルプ・設定ファイルのコメント）へ移す。判断と理由を変えずに細部を正本へ移して削ることは、どの ADR でもいつでもよい
- 各 ADR の冒頭に、決定の要約（2〜3 文）を置く
- 1 本が長くなったら（目安は 8,000 字）、または Iteration の見直しで、分割・統合・削除・細部の削除・実装との照合、テストや lint に移せる判断の洗い出しを起票する
- 機械で守れる判断は、テスト・lint・フック・検査に守らせる。ADR は理由の説明にとどめる。コードのコメントから指すのは、番号の変わらない要件 ID と「なぜ」。ADR の番号はファイルの先頭のコメントに 1 つまでにする（ADR は統合・削除されるため）

### 一覧

`docs/adr/README.md` に「有効な ADR」の表（番号・タイトル・テーマ）と「最後に使った番号」を置く。新しい ADR は最後に使った番号の次の番号にし、マージ前に main の最大番号を確かめる。ADR を足す・削除するときは同じ変更で表と「最後に使った番号」を直す。「テーマ」は一覧から引くための語。

### 文書の見直し

- この PR が変えた約束・手順・規約の文書を、同じ PR で直していないのは規約の違反。PR の見直しで重い指摘にする
- この PR が変えていない文書の、前からあるずれは PR の見直しで重い指摘にしない。Iteration ごとの文書の見直し（`dg guide audit` の文書の観点）で 1 本の指摘表にまとめ、承認を得て直す

### 重複と参照の検査

文書全体の大きさの予算は持たない。大きさで見るのは要件の 1 項の上限だけで、これは文を詰めさせる予算ではなく、1 項に細部が入ったことを見つける印にする。`mise run check:docs` が、文書の重複・参照の切れ・要件 ID・1 項の上限・ADR の番号と一覧を検査する。検査の対象と判定の細部は `scripts/check-docs.mjs` の冒頭に書く。

### 書き方

- 書き足さず書き換える。ADR を除く docs・README・CLAUDE.md・コードのコメントのどれでも、古い記述を残して新しい記述を足さない。古くなった記述は、変更に直接関係がなくても見つけた変更で消す。残すのは、消すと約束や理由がわからなくなるものだけ
- 参照はファイルのパスと見出しのアンカーで書く

### 言語

- docs・CLAUDE.md・コードのコメント・テスト名は日本語で書く。例外は英語で書く README.md（GitHub・Marketplace の入口）・SECURITY.md（GitHub の Security タブの入口）・docs/usage.md（README から引く使い方の英語版）。日本語の README.ja.md と docs/usage.ja.md は、それぞれ英語版と同じ節の構成にし、先頭から互いに辿れるようにする。README から指すほかの docs（要件定義書・開発ガイド・ADR 一覧）は日本語のままにする
- dg がエージェントと利用者に出す文は英語だけで書く。範囲は、guide・Skill の雛形、CLI のヘルプ、MCP のツールの説明、エラー・警告、`dg next`・`flow next` の段階の理由、brief の定型の文、フックが止める文、データのブランチへのコミットの 1 行目、`dg pr ready` が PR の本文に足す定型の節、`dg ask`・`dg ask-menu` の候補の名前と札の sub と人が打つコマンドの雛形。`dg ask` の依頼文と札の説明の定型の文（候補の 1 文・対象の 1 行）は、言語（ja・en）を選べる（細部は `packages/core/src/commands/ask.ts`）。画面（VS Code 拡張と web）の定型の文は、dg の英語の文も訳して表示言語で出す（要件 UI-11）
- エージェントが書く文章（チケット・PR・コミット・人への返答）は、リポジトリの既存の文章と人の依頼の言語に合わせる

## 理由

- 入口が 1 つなら、エージェントは最初に何を開くかで迷わず、要らない文書を開かない
- 細部をいつでも消せれば、決めた時点の細部が ADR に溜まり続けない。ADR を今の判断と理由だけにすれば、読む人は細部に惑わされず判断を読める
- 約束だけを書けば、実装の細部を変える PR で要件定義書を直さずに済む。細部を写すと二重の正本になり、ずれたときにどちらが正しいか決められない
- AI で開発すると小さな仕様変更の頻度が高い。細部を正本に置き、ADR は今の判断と理由だけを書けば、細部の変更で ADR を直す必要がない。判断を変えたときだけ、同じ PR で 1 本を直す
- 本文を今の判断に直せば、読む人は古い決定を正として読まず、一覧から 1 本を引けば今の判断に当たる。古い本文を残すと、エージェントはそれを今の決定と読み違える。経緯は Git の履歴で足りる
- 番号を変えず使い回さないので、判断を変えたときに ADR を指す参照は切れず、別の判断を指すこともない。統合・削除された ADR を指す参照は切れる
- 採らなかった案に 1 行で残せば、覆した判断でも同じ議論を繰り返さず、本文の書き換えで消えない
- ADR を書く場面を 4 つに限れば、端のケースやバグ修正で ADR が増えない。テストは振る舞いを機械で守るので、細部の正本はテストに置き、「なぜ」だけを近くのコメントに書けば、コードを変えた人が同じ場所で直せる
- 重複と参照を直接検査すれば、同じ約束が 2 か所に書かれたことに気づける。文書全体の大きさの予算は細部が入ったことを見ず、文を詰めさせるので持たない。要件の 1 項は約束と案内で足りるので、上限を超えたことは細部が入った印になる
- 古い記述が残ると、エージェントはそれを正として読み、ずれた実装をする。足すだけの運用では文書が膨らみ、重複が増える
- 文書のずれを PR の見直しで重い指摘にすると、変えていない文書の修正が PR ごとに積もる。Iteration の見直しに集めれば、1 回でまとめて直せる
- dg の文を英語にすれば、言語を問わず利用者とエージェントが読める。手順が英語でも、エージェントの書く文章を既存の文章と依頼の言語に合わせれば、チームの記録はチームの言語で残る

## 採らなかった案

- **細部の変更ごとに ADR を書き、古い ADR に注記を足す**：先行プロジェクトで有効な決定が読み取れなくなった
- **判断ごとに新しい番号で置き換える**：古い本文と失効の印が溜まり、今の判断を知るのに何本もたどることになった（経緯は Git で足りる）
- **節・項ごとに失効の印を付ける**：印の数の管理が要り、有効な判断まで失効に見えた
- **コードのコメントから要件 ID を消す**：約束と守るコードの対応が消え、機械で照らせなくなる
- **文書全体の大きさの予算を残す**：細部が入ったことを見ず、文を詰めさせる
- **端のケースやバグ修正ごとに ADR を書く**：Run の判断が 8 本に散り、今の判断を知るのに約 10 本を読むことになった
- **置き換え済みの ADR の本文を残す**：失効した細部を今の決定と読み違える。経緯は Git の履歴で足りる
- **細部の削除を移行に限る**：後から書いた ADR の細部が消せず、版の細部を消すために別の ADR を書くことになった
- **ADR を正本にし、要件定義書は概要だけ**：今の仕様を知るのに複数の ADR をたどることになる
- **要件定義書を節ごとに複数ファイルに分ける**：細部を写す書き換えは減らず、どこに書くかの判断が増える
- **guide・Skill・dg の出力を日英の 2 本立てにする**：変更の多い文を 2 本持つと片方がずれる（背景の 32% のずれと同じ）
- **手順書を docs に置く**：手順は CLI の版と一緒に変わるので、CLI に同梱した方がずれない
- **この決定を新しい ADR で置き換え、ADR-001 を置き換えにする**：文書の入口の規則が別の ADR に移ると、入口の規則を 2 か所で読むことになる
