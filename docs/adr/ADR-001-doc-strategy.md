# ADR-001 文書の方針

- ステータス：承認
- 更新日：2026-11-02

## 背景

deguboard は AI エージェント（Claude Code など）が主に実装する。エージェントは文書を丸ごと読みがちで、文書が大きいほど毎回の作業が遅く高くなる。先行プロジェクトでは、仕様の細部を ADR と要件定義書の両方に写し、小さな変更のたびに ADR を増やした結果、要件定義書が 128KB、ADR が 67 本・670KB に膨らみ、後から運用を立て直すことになった。deguboard ではその立て直した後の形で始める。

## 決定

### 読み手ごとの入口

最初に読む文書を読み手ごとに 1 つに決める。ほかの文書は、入口から作業に応じて要る節だけを引く。

読み手は Claude（毎回）・利用者・開発者（人）・仕様を知りたい人・作業中のエージェントで、入口はそれぞれ `CLAUDE.md`・`README.md`・`docs/development.md`・`docs/requirements.md`・`dg guide <topic>`。そこから引くものは CLAUDE.md の「ドキュメント（入口と正本）」と requirements の冒頭に書く。

- リポジトリの規約（毎回守る決まり）は CLAUDE.md にだけ書く。README と development.md には書き写さず、参照する
- エージェント向けの作業手順は docs に置かず、`dg guide` として CLI に同梱する

### 要件定義書に書くもの

利用者（人・エージェント）から外に見え、変えると利用者に影響する「約束」だけを書く。

- コマンドがあることと、何をするか（書き込むか・push するか・止まる条件）
- データ（Project・Ticket・Epic・Iteration・Plan・Workflow・Run・config）の形と意味
- 状態遷移の約束（既定と制約の仕組みは該当 ADR を参照する）
- 画面に何が出て、何ができるか
- 限界

実装を読めばわかり、変えても約束が壊れないもの（CLI オプションの細部、集計の規則、画面の並び・色・文言）は書かない。正本はヘルプ・コード・テストにし、要件定義書からは正本のファイルを案内する。要件には `TK-1` のような ID を付け、文を縮めても ID と見出しのアンカーは変えず、消した ID は再利用しない。

### ADR はテーマごとに 1 本、直接書き換える

- ADR に書くのは背景・決定・理由・採らなかった案だけ。形式や細部は requirements の節を参照する
- 採らなかった案は、また提案されそうな案だけを、1 案 1 行の理由で書く（経緯は Git に任せる）
- ADR はテーマごとに 1 本とし、そのテーマの「今の決定」を常に表す
- **小さな変更は該当 ADR を直接書き換える**。決定・理由・採らなかった案を今の内容に直し、更新日だけ変える。変更履歴は Git に任せ、ADR の中に「〜は△△に変更」の注記を積まない。新しい ADR も作らない
- **新しい ADR を書くのは大きな方針変更だけ**。目安は、テーマの決定を反転する（例：orphan ブランチをやめる、ツールがエージェントを起動する）、採らなかった案を採り直す、利用者のデータや運用に移行作業が要る、のいずれか。このときは新しい ADR に何を置き換えたかを書き、古い ADR のステータスを `置き換え（ADR-0xx）` にして本文は決めた時点のまま残す。消さない・動かさない
- 小さいか大きいかを迷ったら小さい方に倒して書き換える。大きい変更は PR の説明に「ADR を置き換える」と明記する
- ADR を書くのは、利用者から見える振る舞いやデータの形を決めるとき、構成や技術を選ぶとき。実装の細部や 1 PR で戻せるものには書かない

### 一覧

`docs/adr/README.md` に「有効な ADR」の表（番号・タイトル・テーマ・更新日）を置く。置き換えが起きたときだけ「置き換え済み」の表（番号・移った先）を足す。ADR を足す・置き換えるときは同じ変更で一覧も直す。番号はマージ前に main の最大番号を確かめる。

### 大きさの予算

CLAUDE.md・README・requirements・development.md と、ADR 1 本・`dg guide` のトピック 1 本ずつに大きさの予算を決める。値の正本の `scripts/check-docs.mjs`（`mise run check:docs`）が予算と ADR 一覧の整合（載り方と更新日）を検査し、超えたら失敗にする。予算の 90% を超えたら、失敗にはせず警告を出す。README・CLAUDE.md・docs の相対リンクと見出しアンカー（GitHub 流）の切れも検査する。超えそうなら、細部を正本へ移すか、約束を見直す。

### 書き方

- 書き足さず書き換える。docs・README・CLAUDE.md・コードのコメントのどれでも、古い記述を残して新しい記述を足さない
- 古くなった記述は消す。変更に直接関係がなくても、作業中に実装や仕様とずれた記述を見つけたら、その変更で消す。残すのは、消すと約束や理由がわからなくなるものだけ
- 参照はファイルのパスと見出しのアンカーで書く
- 文書・コメント・テスト名は日本語で書く

## 理由

- 入口が 1 つなら、エージェントは最初に何を開くかで迷わず、要らない文書を開かない
- 約束だけを書けば、実装の細部を変える PR で要件定義書を直さずに済む。細部を写すと二重の正本になり、ずれたときにどちらが正しいか決められない
- AI で開発すると小さな仕様変更の頻度が高い。変更のたびに ADR を増やすと、今の決定を知るのに置き換えの連鎖をたどることになる。テーマごとに 1 本を書き換えれば、常に 1 本を読めば足り、経緯は Git が持つ
- 大きな方針変更だけ ADR を残すのは、「なぜ以前の方針をやめたか」が後の判断に要るのはその規模の変更だけだから
- 予算を数字で決めて検査すれば、細部が入り込んだことに気づける。`dg guide` はエージェントが作業のたびに読み、docs から外した手順の行き先にもなるので、docs と同じく予算で押さえる。超えて初めて気づくと、上限に合わせて文を詰める書き方になるので、手前の 90% で知らせて細部を正本へ移すきっかけにする
- 古い記述が残っていると、エージェントはそれを正として読み、ずれた実装をする。足すだけの運用では文書が膨らみ、予算も守れない

## 採らなかった案

- **変更のたびに新しい ADR を書き、古い ADR に注記を足す**：先行プロジェクトで有効な決定が読み取れなくなった
- **ADR を正本にし、要件定義書は概要だけ**：今の仕様を知るのに複数の ADR をたどることになる
- **要件定義書を節ごとに複数ファイルに分ける**：細部を写す書き換えは減らず、どこに書くかの判断が増える
- **手順書を docs に置く**：手順は CLI の版と一緒に変わるので、CLI に同梱した方がずれない
