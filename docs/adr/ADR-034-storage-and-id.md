# ADR-034 チケットの保存と ID

- ステータス：承認

## 要約

チケットなどのデータは orphan ブランチ `deguboard`（データのリモートでの名前は config で変えられる）に 1 件 1 ファイルで置き、ID は `t12` のような連番をそのままファイル名にする。作成は採番から push までを 1 単位にし、衝突は push の拒否で検出する。取り込みはフィールド単位のマージドライバで行い、config.yaml と workflows は行単位のままにする。

## 背景

チケット・プロジェクト・イテレーション・計画・ワークフロー定義・Run の集計を、専用サーバーや DB なしに Git で管理し、人と AI エージェントの両方が読み書きできる形で置きたい。作業は Git worktree で並列に進むので、どの worktree からも同じチケットの状態を見られる必要がある。複数のエージェントが同時に起票するので、ID の衝突も避けたい。

## 決定

### 置き場所：orphan ブランチ `deguboard`

- データは orphan ブランチ `deguboard` に置き、専用の worktree で読み書きする。作業ブランチや作業 worktree にはデータを置かない
- ブランチは保護せず、`dg` が直接 commit・push する
- データを fetch・push するリモートは、既定でコードのリモートと同じにし、config の `git.data_remote` でコードとは別のリポジトリのリモートにできる。分けるのは fetch・push の先だけで、手元の置き場所（データの worktree と Git 管理外の場所）と、作業ブランチ・PR の照合の先（コードのリモート）は変えない
- config にはリモートの名前を持ち、URL は各クローンの git の設定に置く。config はデータの中にあるので、最初の `dg init` は取り込む先を名前か URL で受ける
- 名指ししたデータのリモートがクローンにないときは、同期なし（SY-6）として手元に書かせず、push の要る操作を止めて足し方を示す。取り込んだ config でデータのリモートが変わったら、push せずに止めてもう一度の実行を求める
- 別のリポジトリへ移すのは、新しいリポジトリへの push → config の変更を元と新しいリモートの両方へ push（`git.data_remote` の変更はすぐ元のリモートへ push する）→ 全員が移ってから元のブランチを消す、の順にする（手順は [usage.ja.md](../usage.ja.md#データを別のリポジトリに置く)）
- データのリモートでのブランチ名は、既定で `deguboard` にし、config の `git.data_branch` で変えられる。取り込み・push・外の変更の検出はこのブランチだけを見るので、1 つの専用のリポジトリにリポジトリごとのブランチ（`deguboard-<名前>` を勧める）で別々のカンバンを置ける。手元の worktree のブランチは名前によらず `deguboard` のままにする
- `/` を含むブランチ名は拒む。名前はリモートの URL から自動では決めず、最初の `dg init` が `--data-branch` で受ける（config はデータの中にある）
- 取り込んだ config でブランチ名が変わったときも、データのリモートと同じく push せずに止め、ブランチ名を変える移行もリモートを移すのと同じ順にする（`git.data_branch` の変更はすぐ元のブランチへ push する）。リモートとブランチ名の両方を変えるときは 1 つずつ移す（手順は [usage.ja.md](../usage.ja.md#1-つのリポジトリに複数のカンバンを置く)）
- Git 管理外のもの（ローカルロックなど）は、データ worktree の外の専用の場所に置く。索引の持ち方は [ADR-033](ADR-033-architecture.md)

### 形式：1 件 1 ファイル

- 本文を持つチケットと Epic は Markdown で属性を frontmatter に、ほかは人が読む YAML、機械だけが書く Run の集計は JSON にする。置き場所は requirements の 5.1
- 削除したチケットは墓標として残し、番号を再利用しない
- 書き込みは原子的にし、読めないファイルは止めずに報告する（DT-1）

### ID：連番をそのまま ID とファイル名にする

- ID は `t12` のような接頭辞＋連番で、ファイル名は ID そのまま。ゼロ埋めせず、title の slug も入れない。番号はプロジェクトをまたいでリポジトリ全体で一意（DT-3）
- **作成は採番から push までを 1 単位**にし、push が拒否されたら採番し直す（DT-4）。同じパスの add/add で衝突を検出できる
- チケットの起票は、オフラインで push できないときは仮番号でローカルに commit し、次の `dg sync` が衝突した番号と参照を振り直してから push する（DT-5）。Epic・Iteration・Plan の作成は、届かなければコミットを捨てて失敗する（SY-3）
- 作業ブランチ名と PR は claim（[ADR-028](ADR-028-agents-and-state.md)）の後に作り、仮番号のチケットは claim できないので、仮番号がブランチ名に入ることはない
- Run の ID は採番せず、開始日時から作る。辞書順が開始の順になる

### 同期の競合：フィールド単位でマージする

- 取り込みは rebase で行い、git のマージドライバを、チケット・墓標・Epic の Markdown と、`plans/`・`iterations/`・`projects/` の YAML に当てる。規則の正本は core の `git/merge.ts`
- frontmatter はフィールドごとに 3-way で決め、片側だけ変えた値を採る。素の YAML は全体を frontmatter と同じに扱い、最上位のフィールドごとに決める。両側が違う値に変えたフィールドと本文の同じ行のぶつかりを競合にする。ただし両側が同じ状態（同じ status。status のない Plan は、両側が同じ時刻のフィールドを持つこと）で、状態と一緒に書く時刻だけがずれたときは早い方を採る（SY-4）
- `config.yaml` と `workflows/` は当てず、行単位のマージのままにする
- 登録は `dg init` と `dg sync` が行い、ドライバは絶対パスで指す。`.gitattributes` はデータのブランチにコミットし、既にあるものには足りない行を足す
- VS Code 拡張の同期も、同梱の `dg` を呼ぶドライバを登録する

### 複数 Project

- 1 リポジトリに複数の Project を置ける（形は requirements の 5.3）
- Ticket・Epic・Iteration は `project` フィールドで所属を表す。ディレクトリはプロジェクトごとに分けず flat に置く

### 呼称

- 製品名・ブランチ名・環境変数の接頭辞は deguboard に揃え、CLI は `dg`
- 作業の最小単位は ticket、期間の単位は iteration、目的で束ねる単位は epic と呼び、CLI のサブコマンド名にする

## 理由

- 作業ツリー直下に置くと、`git worktree add` した各ブランチにデータのスナップショットが入り、worktree 内で更新すると feature ブランチにチケットの変更が混ざって乖離する。保護ブランチには状態変更を直接 push できない。orphan ブランチなら、どの worktree からも `git rev-parse --git-common-dir` で同じ場所を見られ、コードの PR にチケットの差分が混ざらない
- データのリモートを分けられれば、カンバンをコードのリポジトリと別の場所（カンバン専用のリポジトリ）に置ける。手元の置き場所を変えなければ、worktree・ロック・マージドライバ・フックの検出はそのまま使え、移すのに手元のデータの移行が要らない
- 名指ししたリモートがないクローンを同期なしで動かすと、データは別のリポジトリにあるのに手元だけが進み、気づかないまま採番と claim が食い違う。リモートを設定していないリポジトリ（SY-6）と違い、設定の誤りなので止める
- 移す途中に元のリモートを使うクローンは、config の変更を元のリモートから取り込んで初めて移ったことを知る。そのまま元のリモートへ push すると、移した先に届かない変更が残る。変更を元のリモートにすぐ push し、取り込んだ側は push の前に止めれば、取りこぼさない
- カンバン専用のリポジトリを 1 つにまとめられれば、リポジトリごとに専用のリポジトリを作らずに済む。見る権限は Git のホストがリポジトリ単位で与えるので、同じ専用のリポジトリに置いたカンバンは、そこを読める人にはどれも見える。分けたいカンバンは別のリポジトリに置く
- 手元のブランチ名を変えないのは、ブランチ名を変える移行で手元のブランチを付け替えずに、取り込みと push の先だけを変えれば済むから
- `/` を拒むのは、`deguboard/webapp` が同じリモートの `deguboard` ブランチと ref の上でぶつかる（`refs/heads/deguboard` がファイルとディレクトリを兼ねられない）から。URL から決めないのは、接続の仕方で URL が人ごとに違い、同じカンバンが別の名前になるから
- 1 件 1 ファイルなら競合が 1 件に閉じる。全件 1 ファイルは競合が集中する
- 連番は人にもエージェントにも読みやすい。衝突は「作成 = push の CAS」で解決でき、残る窓はオフライン作成だけなので、仮番号で補えば足りる。仮番号を付けるのは、オフラインでも書き留めたいチケットの起票だけにする。Epic・Iteration・Plan は作る回数が少なく、振り直すと参照の追従が広がるので、届くまで待ってもらう
- ゼロ埋めしないのは、ID とファイル名が同じ文字列になり、桁数の上限を決めずに済むから。AI が起票すると週に数百件増えるので、4 桁は数か月、5 桁でも数年で足りなくなる。並び順は CLI と UI が番号で担う
- 番号を全体で一意にすれば、プロジェクトごとにディレクトリを分ける必要がなく、プロジェクト間の移動がファイルの改名にならない
- 墓標を残せば、削除後に同じ番号が再利用されて古い参照が別のチケットを指すことがない
- Run は並行して始まり、実行中はコミットしないので、連番の CAS が使えない
- フィールド単位でマージすれば、同じチケットの別々の属性を 2 人（やエージェント）が変えても止まらない。行単位では `updated_at` の行が毎回ぶつかり、ほぼすべての同時更新が競合になる
- 状態と一緒に書く時刻（`closed_at`・`started_at`・`approved_at`）は、両側が同じ status に着いたときは同じ遷移の記録で、どちらを採っても状態は変わらない。人が選ぶほどの違いがないのに競合にすると、同じ状態への同時の遷移（s26 の close）で sync が止まる。採るのは早い方にすると、どちらの環境が解いても同じ値になり、両側が独立に解いても一致する。Plan は status を持たず、承認した・閉じた時刻そのものが状態なので、両側がその時刻を持てば同じ遷移の記録になる。status が違うとき、片側だけに時刻があるとき、時刻が読めないときは状態の判断に関わるので、競合のまま人に選んでもらう
- Plan・Iteration・Project も `dg` が書き込みのたびに `updated_at` を変えるので、行単位ではチケットと同じく同時の更新がほぼすべて競合になる（Plan の `closed_at` の競合で同期が 3 日止まった）。frontmatter の YAML と同じ読み書きで扱えるので、規則を分けずに済む
- `config.yaml` と `workflows/` は人が手で書く設定で、入れ子の深い値を行単位で見て解く方が意図を壊しにくい
- ドライバを PATH の `dg` で登録しないのは、`npx`・`mise run`・`node_modules/.bin` 経由で動かす環境では PATH に `dg` がないから。絶対パスは古くなりうるが、init と sync のたびに書き直すので直る。拡張が登録しないと、拡張だけで使うリポジトリでは行単位のマージに落ちて近いフィールドの変更で同期が止まる

## 採らなかった案

- **作業ツリー直下の `.deguboard/`**：worktree ごとにデータが乖離し、コードの PR にチケットの差分が混ざる
- **config にデータのリポジトリの URL を持つ**：接続の仕方（https・ssh）と認証は人ごとに違う。名前だけを共有し、URL は各クローンの git のリモートに任せる
- **ハッシュ短縮 ID を正にし、表示用の連番を別に持つ**：ID が 2 種類になる。連番の衝突は CAS で解決できる
- **プロジェクトごとの orphan ブランチ**：同期と排他が倍になる
- **1 つのカンバンで複数のリポジトリを扱う**：番号・依存・Iteration・Epic と作業ブランチの照合がリポジトリをまたぎ、照合の先（コードのリモート）が 1 つに決まらない。カンバンはリポジトリごとに分ける
- **プロジェクトごとのディレクトリと独自採番**：`webapp-12` のような複合 ID が要り、依存の参照が長くなる
- **Epic・Iteration・Plan にも仮番号を付ける**：振り直しの範囲がチケットの `epic`・`iteration`・`plan` の参照まで広がる
- **ファイル名をゼロ埋めする**：桁数の上限が要り、ID とファイル名が食い違う
- **閉じる・開き直す操作をすぐ push する（cas）**：リモートに届かないと閉じられなくなり、二重に閉じた時刻のずれは早い方を採れば解ける（t772）
- **SQLite などの DB**：Git で diff・マージ・履歴を扱えなくなる
- **`merge=union` や行単位のマージ**：union は同じフィールドの行を 2 本残して YAML を壊し、行単位は `updated_at` で毎回止まる
- **すべての `*.yaml` にドライバを当てる**：人が手で書く設定までフィールド単位にすると、入れ子の深い値を 1 つの値として比べるので、別々の行の変更まで競合になる
- **ドライバを `dg merge-driver` と PATH で登録する**：PATH に `dg` がない環境で動かない
- **`.gitattributes` を `<git-common-dir>/info/attributes` に置く**：作業ブランチの worktree にも効いてしまう
