# ADR-006 UI と書き込み

- ステータス：承認
- 更新日：2026-11-06

## 背景

カンバン・バックログ・チケット詳細・イテレーション・実行状況・実績を、ブラウザと VS Code の両方で見たい。UI からチケットを書き換えてよいか、2 つの UI をどう共通化するか、UI の操作をいつ Git にコミットするかを決める。

## 決定

### Web UI と VS Code 拡張を最初の版から両方提供する

- ※ ADR-023 で置き換え（この項の「Web ではローカル HTTP サーバー（`dg serve`）が配信し、」の部分は失効）。画面は 1 つの React アプリ（`packages/web`）で作る。Web ではローカル HTTP サーバー（`dg serve`）が配信し、VS Code では拡張の Webview に同じアプリを載せる
- アプリは `CommandClient` という 1 つのインターフェースだけを通じて Core を呼ぶ。Web では HTTP の実装、VS Code では Webview の `postMessage` を拡張ホストが受けて Core を直接呼ぶ実装にする
- VS Code 拡張はサーバーを起動しない
- ※ ADR-023 で置き換え（この項の「Web ではそれに値を与える層を 1 枚置く」の部分は失効）。テーマは VS Code の CSS 変数を基準にし、Web ではそれに値を与える層を 1 枚置く
- VS Code では Activity Bar から開くサイドバーのビューを主画面にし、エディタ領域のパネルには詳細（チケット・Iteration・Epic・Plan）だけを開く（UI-12）。一覧の画面をパネルに出すコマンドは持たない（一覧が 2 つ並んでも見るものが重なるだけ）。画面は載っている場所（`surface`）でリンクの挙動とレイアウトを変え、画面の外への働きかけ（遷移・コピー・ウィンドウやエディタを開くなど。ターミナルへの送信は [ADR-010](ADR-010-ui-writes-and-agent-requests.md)）は `CommandClient` の postMessage に core が決めた形を足して通し、拡張ホストが実行する
- ※ ADR-023 で置き換え（この項の「ブラウザは前のまま（属性はまとめて直し、Status を全部並べ、依存先は右の列で知らせる）」の部分は失効）。チケット詳細は `surface` で編集の仕方・選択肢・知らせ方も分ける。パネルでは属性を 1 つずつその場で直し、Status の選択肢を Workflow で今から移れるものに絞り、終わっていない依存先は本文の上の帯で知らせる。ブラウザは前のまま（属性はまとめて直し、Status を全部並べ、依存先は右の列で知らせる）

### 画面の書き込みは Core を通す

- 画面から直接書き込めるのはチケット詳細と設定画面だけで、ほかの変更はエージェントへの依頼文を作って渡す（[ADR-010](ADR-010-ui-writes-and-agent-requests.md)）
- 書き込みは必ず Core の同じコマンド（`core/commands`）を通る。`transitions` の制約の検査、採番、検証は CLI と同じ経路で行われ、UI だけの近道を作らない
- カンバンには Iteration の一覧の画面を置かず、Iteration は Epic・担当者と同じ絞り込みで選ぶ（一覧の表は縦に場所を取り、絞り込みが 2 か所に分かれる）。サイドバーは閉じていない Iteration を札の列で並べる（開かずに進みを見渡せる）。開始・閉じるは画面に置かない（開始は claim の手順が行い、閉じるはエージェントに頼む。ADR-010）。カンバンは planned と active の Iteration（1 つか「すべて」）のチケットだけを出し（全チケットを出すと、帯に閉じた Plan がすべて並ぶ）、Iteration に入っていないチケットはバックログで見る
- カンバンの見出しの下に実行計画（Plan）の帯を置き（UI-13）、表示だけにする。Plan の承認と閉じるは、`dgplan`・`dgdone` の会話の中で人が答える判断なので、画面にボタンを置くと流れの外で状態が変わる
- ※ ADR-023 で置き換え（この項の「Run の実行状況と実績（UI-9）は Run で見る」の部分は失効）。画面のタブはカンバン・バックログ・履歴・Run の 4 つにし、計画中のもの（planned・active の Iteration、open の Epic）はカンバンとバックログ、終わったもの（closed の Iteration と Epic）は履歴、Run の実行状況と実績（UI-9）は Run で見る。VS Code の左パネルは Run を除く 3 つにし、履歴からのリンクも出さない（実行中の Run はカンバンの行の印で見え、実績は振り返りでたまに見るだけで、狭い幅では表が読みにくい）。Epic のタブは置かない（計画を立てるときに Iteration・Epic・未割り当てのチケットが 3 つの画面に分かれる）。open の Epic はバックログの欄に進捗つきで並べて絞り込みを兼ねる
- カンバンの列は 5 つの Status に固定し、表示名と表示項目はワークフロー定義に追従する
- 設定はチームで共有する `config.yaml` を基本にし、人ごとに違ってよい項目（マシンの配置・作業の好み・使えるモデル・自分のマシンで許すこと。項目ごとの範囲はスキーマの scope）だけを Git に入らない `deguboard-local/config.yaml` で上書きできる。読むのは Core（個人 > チーム > 既定）で、CLI・`dg serve`・VS Code 拡張は同じ値を見る。VS Code の settings.json は使わない（settings.json に置くと CLI とエージェントに届かず、VS Code だけ値が違う）。エージェントに許す操作のうち記録と PR に関わるもの（`metrics.read_transcripts`・`auto.merge`・`actor.human_only`・`actions.test`）はチーム専用のまま（個人の拒否は `DEGUBOARD_NO_TRANSCRIPTS`）。設定画面（UI-14）は画面のタブにせず（たまにしか開かない）、歯車で切り替える。画面の中は書き先で「チーム」と「自分」のタブに分け、チームのタブは全項目でチームの `config.yaml` を、自分のタブは上書きできる項目だけで個人のファイルを書く（1 つの欄に重ねた値を出すと、どちらに書いたか分からず、個人の上書きがある項目ではチームへの保存が効かなかったように見える）。チームのタブでは自分が上書きしている項目に印を出す。保存前に確かめるのは、どちらのタブでも、誤ると同期・照合・worktree・実行するコマンド・エージェントに許す操作を壊す項目だけにする（`auto.merge` は PR のマージを許すので、エージェントに許す操作に当たる）
- 画面からの操作の主体は常に human（画面に `--actor` はない）。エージェントは CLI から agent を名乗る（[ADR-004](ADR-004-agents-and-state.md)）

### コミットの単位は設定で選ぶ

- `config.yaml` の `commit.mode` でコミットの単位を、`push.mode` で push の時期を選ぶ。既定はまとめてコミットする `batch`。時間でまとめるのは Core ではなく server・拡張の責務
- claim・作成・Iteration の開始と再開は mode によらず即座にコミットして push する（排他と採番のため。CL-3、[ADR-002](ADR-002-storage-and-id.md)・[ADR-004](ADR-004-agents-and-state.md)）

### `dg` は npm で配り、拡張は同梱しない

- `dg` は npm で配る。実行環境に Node.js を要求しているので、前提は増えない。cli が依存する `core` と `server` も `@deguboard/*` として同じ版で公開し、cli に束ねない。画面（`web` のビルド結果）は cli のパッケージに同梱する
- 拡張は Webview のために `core` と `web` だけを同梱する。画面の閲覧と操作は `dg` なしで動く
- 拡張は `dg` を PATH から引く。同梱は npm が使えない環境が実際に出たときに足す
- `dg` がないときと、`dg` の版のメジャーが同梱の `core` と違うときは知らせる（UI-11）

### サーバーは localhost に閉じる

- `dg serve` は既定で `127.0.0.1` にバインドし、認証は持たない（UI-8）

## 理由

- 画面を 1 つにすれば、機能の追加と修正が 1 回で済む。transport だけを差し替えれば、HTTP と Webview の違いは画面に漏れない
- VS Code からは拡張ホストが Core を直接呼べるので、サーバーを立てる理由がない
- 画面の書き込みを Core に通せば、CLI と同じ保証が効く。画面から書き込む範囲を絞った理由は ADR-010
- UI の操作は頻繁で小さい。1 操作 1 コミットにすると履歴が埋まる。まとめる既定にし、排他に関わる操作だけ即座にする
- localhost に閉じれば、認証なしでも他のマシンから触れない
- `dg` の実体が 1 つなら版ずれが起きず、Skill は「PATH の `dg`」とだけ書けば済む。VS Code を使わないエージェント（Codex、素のターミナル）にも同じ `dg` が届く
- 拡張が `dg` に依存しなければ、エージェントを使わない利用者も拡張を入れるだけで画面の閲覧とチケット詳細の編集ができる
- サイドバーはエディタで何を開いていても見え、幅が狭いので一覧に向く。詳細は本文と属性を並べるのでエディタ領域の幅が要る。先行プロジェクトで定着した形で、利用者が迷わない
- パネルの詳細は 1 件ずつ開いて少しずつ直すので、一括編集や、選んでから拒否される選択は手間が大きく、右の列の下の知らせは見落とす。ブラウザは広い画面で一括編集に困っていない

## 採らなかった案

- **VS Code 拡張だけ**：ブラウザで使えず、VS Code を使わない業務で困る
- **Web と VS Code を別の UI にする**：機能のずれと二重の保守が起きる
- **VS Code 拡張もローカルサーバー経由にする**：ポートの衝突と起動順の問題が増える
- **UI の操作ごとに即コミット**：履歴が埋まり、push の衝突も増える
- **VSIX に `dg` を同梱して PATH に足す**：PATH の注入は統合ターミナルにしか効かず、Claude Code の拡張が起動する `claude` に届かない
- **拡張が `core` を同梱せず、`dg` を子プロセスで呼ぶ**：`dg` がないと画面が動かなくなる
- **詳細もサイドバーの中で開く**：狭い幅に本文と属性を押し込み、一覧に戻る操作も増える
- **サイドバーとパネルで別の画面を作る**：1 つの React アプリを両方に載せる決定に反する
- **個人の設定を VS Code の settings.json に置く**：CLI とエージェントに届かず、同じ項目の値が入口で食い違う
- **利用者ごとの上書きを設けない**：worktree の置き場所・使えるモデル・通知のように人ごとに違う値をチームのファイルで取り合うことになる
