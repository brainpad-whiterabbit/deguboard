# ADR-006 UI と書き込み

- ステータス：承認
- 更新日：2026-11-03

## 背景

カンバン・バックログ・チケット詳細・イテレーション・実行状況・実績を、ブラウザと VS Code の両方で見たい。UI からチケットを書き換えてよいか、2 つの UI をどう共通化するか、UI の操作をいつ Git にコミットするかを決める。

## 決定

### Web UI と VS Code 拡張を最初の版から両方提供する

- 画面は 1 つの React アプリ（`packages/web`）で作る。Web ではローカル HTTP サーバー（`dg serve`）が配信し、VS Code では拡張の Webview に同じアプリを載せる
- アプリは `CommandClient` という 1 つのインターフェースだけを通じて Core を呼ぶ。Web では HTTP の実装、VS Code では Webview の `postMessage` を拡張ホストが受けて Core を直接呼ぶ実装にする。画面のコードは両方で同一
- VS Code 拡張はサーバーを起動しない
- テーマは VS Code の CSS 変数を基準にし、Web ではそれに値を与える層を 1 枚置く
- VS Code では Activity Bar から開くサイドバーのビューを主画面にし、エディタ領域のパネルには詳細（チケット・Iteration・Epic）だけを開く（UI-12）。一覧の画面をパネルに出すコマンドは持たない（一覧が 2 つ並んでも見るものが重なるだけ）。画面は載っている場所（`surface`）でリンクの挙動とレイアウトを変え、サイドバーとパネルの間の働きかけは `CommandClient` の postMessage に core が決めた形を足して通し、拡張ホストが実行する

### UI からの書き込みを許す

- ドラッグ＆ドロップでのステータス変更、属性の編集、イテレーションへの割り当てなどを UI から行える
- 書き込みは必ず Core の同じコマンド（`core/commands`）を通る。`transitions` の制約の検査、採番、検証は CLI と同じ経路で行われ、UI だけの近道を作らない
- カンバンには Iteration の一覧の画面を置かず、Iteration は Epic・担当者と同じ絞り込みで選ぶ（一覧の表は縦に場所を取り、絞り込みが 2 か所に分かれる）。サイドバーは閉じていない Iteration を札の列で並べ（開かずに各 Iteration の進みを見渡せる）、サイドバーでは開始・閉じるを詳細から行う（開始は `dg guide work` の手順が claim のときに行い、閉じるは人の指示のときだけ）。Iteration を使わない Project では全チケットのカンバンにする
- カンバンの見出しの下に実行計画（Plan）の帯を置き（UI-13）、表示だけにする。Plan の承認と閉じるは、計画を立てて進める会話（`dgplan`・`dgdone`）の中で人が答える判断なので、画面にボタンを置くと流れの外で状態が変わる
- 画面のタブはカンバン・バックログ・履歴・Run の 4 つにし、計画中のもの（planned・active の Iteration、open の Epic）はカンバンとバックログ、終わったもの（closed の Iteration と Epic）は履歴、Run の実行状況と実績（UI-9）は Run で見る。VS Code の左パネルは Run を除く 3 つにし、履歴からのリンクも出さない（実行中の Run はカンバンの行の印で見え、実績は振り返りでたまに見るだけで、狭い幅では表が読みにくい。ブラウザか `dg metrics show` で見る）。Epic のタブは置かない（計画を立てるときに Iteration・Epic・未割り当てのチケットが 3 つの画面に分かれる）。open の Epic はバックログの欄に進捗つきで並べて絞り込みを兼ね、詳細の画面はバックログの下に置く
- カンバンの列は 5 つの Status に固定し、表示名と表示項目はワークフロー定義に追従する
- 設定画面（UI-14）は `config.yaml` だけを書き、VS Code の settings.json は使わない（設定はチームで共有し、利用者ごとの上書きを設けない）。たまにしか開かないのでタブにせず、歯車で切り替える。保存前に確かめるのは、誤ると同期・照合・worktree・実行するコマンド・エージェントに許す操作を壊す項目だけにする（`actions.test` はシェルの許可と同等、[ADR-007](ADR-007-architecture.md)。`auto.merge` はエージェントに PR のマージを許すので、エージェントに許す操作に当たる）
- 画面からの操作の主体は常に human（画面に `--actor` はない）。エージェントは CLI から agent を名乗る（[ADR-004](ADR-004-agents-and-state.md)）

### コミットの単位は設定で選ぶ

- `config.yaml` の `commit.mode` でコミットの単位を、`push.mode` で push の時期を選ぶ（値の意味は設定のスキーマの説明）。既定はまとめてコミットする `batch`。時間でまとめるのは Core ではなく server・拡張の責務
- claim・作成・Iteration の開始と再開は mode によらず即座にコミットして push する（排他と採番のため。CL-3、[ADR-002](ADR-002-storage-and-id.md)・[ADR-004](ADR-004-agents-and-state.md)）

### `dg` は npm で配り、拡張は同梱しない

- `dg` は npm で配る（入れ方は README）。実行環境に Node.js を要求しているので、前提は増えない。cli が依存する `core` と `server` も `@deguboard/*` として同じ版で公開し、cli に束ねない。画面（`web` のビルド結果）は cli のパッケージに同梱する
- 拡張は Webview のために `core` と `web` だけを同梱する。画面の閲覧と操作は `dg` なしで動く
- 拡張が使う `dg` の解決は「PATH のグローバル → 同梱」の順で引く 1 か所の関数に置く。最初の版では同梱せず、npm が使えない環境が実際に出たときに足す
- `dg` が見つからないときと、`dg` と同梱の `core` の版のメジャーが違うときは知らせる（UI-11）

### サーバーは localhost に閉じる

- `dg serve` は既定で `127.0.0.1` にバインドし、認証は持たない（UI-8）

## 理由

- 画面を 1 つにすれば、機能の追加と修正が 1 回で済む。transport だけを差し替えれば、HTTP と Webview の違いは画面に漏れない
- VS Code からは拡張ホストが Core を直接呼べるので、サーバーを立てる理由がない。ポートの管理と起動の失敗が減る
- UI からの書き込みを禁じると、エージェントを使わない利用者が CLI を覚える必要があり、カンバンの価値が落ちる。Core を通せば CLI と同じ保証が効く
- UI の操作は頻繁で小さい。1 操作 1 コミットにすると履歴が埋まる。まとめる既定にし、排他に関わる操作だけ即座にする
- localhost に閉じれば、認証なしでも他のマシンから触れない
- `dg` の実体が 1 つなら版ずれが起きず、Skill は「PATH の `dg`」とだけ書けば済む。VS Code を使わないエージェント（Codex、素のターミナル）にも同じ `dg` が届く
- 拡張が `dg` に依存しなければ、エージェントを使わない利用者は拡張を入れるだけでカンバンを使える
- サイドバーはエディタで何を開いていても見え、幅が狭いので一覧に向く。詳細は本文と属性を並べるのでエディタ領域の幅が要る。先行プロジェクトで定着した形で、利用者が迷わない

## 採らなかった案

- **UI は表示専用にし、書き込みは CLI とエージェントだけにする**：カンバンの操作性が落ちる。保証は Core で担える
- **VS Code 拡張だけ**：ブラウザで使えず、VS Code を使わない業務で困る
- **Web と VS Code を別の UI にする**：機能のずれと二重の保守が起きる
- **VS Code 拡張もローカルサーバー経由にする**：ポートの衝突と起動順の問題が増える
- **UI の操作ごとに即コミット**：履歴が埋まり、push の衝突も増える
- **VSIX に `dg` を同梱して PATH に足す**：PATH の注入は統合ターミナルにしか効かず、Claude Code の拡張が起動する `claude` に届かない
- **拡張が `core` を同梱せず、`dg` を子プロセスで呼ぶ**：`dg` がないと画面が動かなくなる
- **詳細もサイドバーの中で開く**：狭い幅に本文と属性を押し込み、一覧に戻る操作も増える
- **サイドバーとパネルで別の画面を作る**：1 つの React アプリを両方に載せる決定に反する
