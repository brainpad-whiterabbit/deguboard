# ADR-006 UI と書き込み

- ステータス：承認
- 更新日：2026-11-01

## 背景

カンバン・バックログ・チケット詳細・イテレーション・実行状況・実績を、ブラウザと VS Code の両方で見たい。UI からチケットを書き換えてよいか、2 つの UI をどう共通化するか、UI の操作をいつ Git にコミットするかを決める。

## 決定

### Web UI と VS Code 拡張を最初の版から両方提供する

- 画面は 1 つの React アプリ（`packages/web`）で作る。Web ではローカル HTTP サーバー（`dg serve`）が配信し、VS Code では拡張の Webview に同じアプリを載せる
- アプリは `CommandClient` という 1 つのインターフェースだけを通じて Core を呼ぶ。Web では HTTP の実装、VS Code では Webview の `postMessage` を拡張ホストが受けて Core を直接呼ぶ実装にする。画面のコードは両方で同一
- VS Code 拡張はサーバーを起動しない
- テーマは VS Code の CSS 変数を基準にし、Web ではそれに値を与える層を 1 枚置く
- VS Code では Activity Bar のアイコンから開くサイドバーのビューを主画面にし、チケット詳細はエディタ領域のパネルに開く（UI-12）。画面はどこに載っているか（`surface`）を `<html>` の data 属性で受け取り、サイドバーではリンクの挙動とレイアウトを変える。サイドバーと詳細のパネルの間の働きかけ（エディタで開く・読み直す・遷移）は、`CommandClient` の postMessage に `action` と `event` の形を足して通す。形は core が決め、拡張ホストが実行する

### UI からの書き込みを許す

- ドラッグ＆ドロップでのステータス変更、属性の編集、イテレーションへの割り当てなどを UI から行える
- 書き込みは必ず Core の同じコマンド（`core/commands`）を通る。`transitions` の制約の検査、採番、検証は CLI と同じ経路で行われ、UI だけの近道を作らない
- カンバンは KanbanForge のサイドバーと同じ 3 層（Iteration の表 → 選んだ Iteration の見出し → 状態ごとの節）にし、Iteration の一覧の画面は置かない。planned・active は表で、closed は履歴で見るので一覧の役目がなく、タブを増やさずに済む。Iteration を使わない Project では表を出さず、全チケットのカンバンにする
- カンバンの列は 5 つの Status に固定し（abandoned は最後の畳んだ列）、表示名はワークフロー定義の `labels`、表示項目は `fields` に追従する
- 画面からの操作の主体は常に human（画面に `--actor` はない）。エージェントは CLI から agent を名乗る（[ADR-004](ADR-004-agents-and-state.md)）

### コミットの単位は設定で選ぶ

- `config.yaml` の `commit.mode`：`each`（書き込みのたびにコミット）/ `batch`（作業ツリーに残し、`dg commit`・`dg sync`・即時の操作がまとめてコミット）/ `manual`（`dg commit` と即時の操作だけ）。既定は `batch`。時間でまとめるのは Core ではなく server・拡張の責務
- `push.mode`：`auto` / `manual`。既定は `auto`
- claim と作成は mode によらず即座にコミットして push する（排他と採番のため。[ADR-002](ADR-002-storage-and-id.md)・[ADR-004](ADR-004-agents-and-state.md)）

### `dg` は npm で配り、拡張は同梱しない

- `dg` は npm で配る（`npm i -g deguboard`。mise なら `mise use -g npm:deguboard`）。実行環境に Node.js 24 以上を要求しているので、前提は増えない。cli が依存する `core` と `server` も `@deguboard/*` として同じ版で公開し、cli に束ねない。画面（`web` のビルド結果）は cli のパッケージに同梱する
- 拡張は Webview のために `core` と `web` だけを同梱する。画面の閲覧と操作は `dg` なしで動く
- 拡張が使う `dg` の解決は「PATH のグローバル → 同梱」の順で引く 1 か所の関数に置く。最初の版では同梱せず、npm が使えない環境が実際に出たときに足す
- `dg` が見つからなければ通知でインストールを案内し、`dg --version` と同梱の `core` のメジャーが違えば知らせる

### サーバーは localhost に閉じる

- `dg serve` は既定で `127.0.0.1` にバインドする。認証は持たない

## 理由

- 画面を 1 つにすれば、機能の追加と修正が 1 回で済む。transport だけを差し替えれば、HTTP とWebview の違いは画面に漏れない
- VS Code からは拡張ホストが Core を直接呼べるので、サーバーを立てる理由がない。ポートの管理と起動の失敗が減る
- UI からの書き込みを禁じると、エージェントを使わない利用者が CLI を覚える必要があり、カンバンの価値が落ちる。Core を通せば CLI と同じ保証が効く
- UI の操作は頻繁で小さい。1 操作 1 コミットにすると履歴が埋まる。まとめる既定にし、排他に関わる操作だけ即座にする
- localhost に閉じれば、認証なしでも他のマシンから触れない
- `dg` の実体が 1 つなら版ずれが起きず、Skill は「PATH の `dg`」とだけ書けば済む。VS Code を使わないエージェント（Codex、素のターミナル）にも同じ `dg` が届く
- 拡張が `dg` に依存しなければ、エージェントを使わない利用者は拡張を入れるだけでカンバンを使える
- サイドバーはエディタで何を開いていても見え、幅が狭いので一覧に向く。詳細は本文と属性を並べるのでエディタ領域の幅が要る。先行プロジェクトで定着した形で、利用者が迷わない

## 採らなかった案

- **UI は表示専用にし、書き込みは CLI とエージェントだけにする**：先行プロジェクトはこの形だったが、deguboard はカンバンの操作性を優先する。保証は Core で担う
- **VS Code 拡張だけ**：ブラウザで使えず、VS Code を使わない業務で困る
- **Web と VS Code を別の UI にする**：機能のずれと二重の保守が起きる
- **VS Code 拡張もローカルサーバー経由にする**：ポートの衝突と起動順の問題が増える
- **UI の操作ごとに即コミット**：履歴が埋まり、push の衝突も増える
- **VSIX に `dg` を同梱して PATH に足す**：PATH の注入は統合ターミナルにしか効かず、Claude Code の拡張が起動する `claude` には届かない。Node がない環境では VS Code 内蔵の Electron を Node 代わりにするシムの保守を抱える。npm が使えない環境が出たら、tarball の `npm i -g ./deguboard-x.y.z.tgz` で足りるか、同梱まで要るかを見て決める
- **拡張が `core` を同梱せず、`dg` を子プロセスで呼ぶ**：拡張ホストが Core を直接呼ぶ設計を崩し、`dg` がないと画面が動かなくなる
- **詳細もサイドバーの中で開く**：拡張ホストの変更は要らないが、狭い幅に本文と属性を押し込むことになり、一覧に戻る操作も増える
- **サイドバーとパネルで別の画面を作る**：1 つの React アプリを両方に載せる決定に反する。`surface` で振る舞いを変えるだけにする
