# ADR-009 Epic と Iteration

- ステータス：承認

## 要約

Epic は目的ごとにチケットを束ねる独立したエンティティで、期間の目標は Milestone を置かず Iteration で表す。Epic の閉じる・再開は Workflow の `governance.epic` で、Iteration の閉じる・再開は `flow.release` で判定する。既定は、Epic がエージェントに人の承認を求め（`always_ask`）、Iteration が人に限る（`human_only`）。active な Iteration はカンバンに 1 つに限る。Iteration の期間は予定を持たず、実績（始めた日時と閉じた日時）だけを記録する。

## 背景

チケットは目的ごと・期間ごとに束ねて進める。束ねる単位をチケットの一種にするか独立したエンティティにするか、所属をどちらに持つか、期間の目標を何で表すか、同時に進める期間をいくつ許すか、期間を予定と実績のどちらで持つかを決める。チケットの Status と遷移は ADR-003 で決める。

## 決定

### Epic は置き、Milestone は置かない

- Epic は目的ごとにチケットを束ねる独立したエンティティ（`epics/e3.md`）。チケットの一種にはせず、claim・ブランチ・5 つの Status を持たない
- 状態は `open` / `closed` で、進捗は保存しない（EP-1・EP-3）。所属はチケット側の `epic` だけで表し、入れ子にせず、Iteration をまたぐ（EP-2）。チケットの遷移は縛らない
- Milestone は持たず、期間の目標は Iteration で表す。Iteration の所属もチケット側の `iteration` だけで表す（IT-2）

### 閉じる・再開するのは Workflow の値で判定する

- Epic を閉じる・再開するのは、カンバンの管理の操作として Workflow の `governance.epic` の値で判定する（値の意味と判定の順は [ADR-003](ADR-003-status-and-workflow.md)）。既定は `always_ask` で、エージェントは人の承認（`--approved-by`）があるときだけ行える。人に限りたいカンバンは値を `human_only` に書き換える。細部は EP-4
- Iteration を閉じる・再開するのは、流れのリリースの段階の操作として Workflow の `flow.release` の値で判定する。既定は `human_only` で、エージェントの呼び出しは拒否する。細部は IT-1
- Iteration・Epic へのチケットの出し入れは、流れの割り当ての段階の操作として `flow.assign` の値で判定する（既定は `ask_unless_auto`。`--auto` の扱いは [ADR-030](ADR-030-flow-and-guide-in-core.md)）

### active の Iteration はカンバンに 1 つ

- active の Iteration はカンバンに 1 つに限り（カンバンの中を分ける単位は持たない。[ADR-034](ADR-034-storage-and-id.md)）、`start`・`reopen` はほかに active があれば拒否する。claim と同じく即座に push して排他にし、それでも 2 つになったもの（直接の編集・マージ）は `lint` が指摘する（IT-1）

### 期間は実績だけを記録する

- Iteration は予定の開始日・終了日を持たない。active になった日時 `started_at` と閉じた日時 `closed_at` だけを書き、画面の期間もこれで出す（IT-1・UI-5）。終了日の超過を前提にした案内（期限切れの次の操作・持ち越しの相談）も置かない
- 前に書いていた `start`・`end` は読むときに値に出さず、Iteration を書くたびにファイルから消す（スキーマにない項目を残す DT-2 の例外。dg 自身が書いた古い形だけを移す）
- claim の入れ先は active、なければ planned がただ 1 つのときのそれ。planned が複数なら順を決める日付がないので入れず、人に頼む（ADR-031）

## 理由

- Epic（目的の範囲）・Iteration（期間）・Plan（実行順）は役割が違うので別のエンティティにする。Epic に 5 つの Status を持たせないのは、「作業中」「確認待ち」が Epic に意味を持たないため。進捗を保存しないのは、チケットを動かすたびに Epic も書き換えて衝突させないため
- Epic を閉じる・再開する権限を Workflow の `governance` に置くのは、チケットの Status の動きと同じ 5 つの値で「誰に任せるか」を 1 つのファイルに書けるようにするため。コマンド名の一覧では、拒否するかしないかの 2 値しか書けず、人の承認で任せる形を表せない
- Epic の既定を `always_ask` にするのは、Epic を閉じると目的の範囲が終わったことになり、閉じた Epic にはチケットを足せなくなるため、中身を見て決めるのは人だが、その指示を実行するのは頼まれたエージェントでよいため（abandon・reopen の既定と同じ。[ADR-003](ADR-003-status-and-workflow.md)）。`human_only` では人が頼んでもエージェントが拒否され、人がコマンドを打ち直すことになる。`always_ask` なら承認者の記録なしには閉じず、聞かずに閉じることは防げる。閉じても再開でき、外れるチケットもない
- Iteration の既定を `human_only` にするのは、閉じると終わっていないチケットが外れ、期間の実績が確定するため。リリースの段階の操作でもあり、人が手で閉じる
- Iteration を閉じる・再開するのを規約でなく `flow.release` で判定するのは、規約は LLM が読んで守るので、指示のないまま閉じる誤りを止められないため。Epic と同じ 5 つの値で書けば、人の承認で任せるカンバンは値を書き換えるだけで済む
- 期間を実績だけにするのは、Iteration を閉じるのは「中のチケットが終わったとき」で、日付は運用の目安にとどまるため。予定の日付は始める日・閉じる日とずれ、ずれたまま残ると画面の期間と履歴が実際と食い違う。超過の案内は、閉じる判断を日付で促すことになり、閉じる・持ち越すは人が中身を見て決めるという扱いと合わない
- active を 1 つに限るのは、「今の Iteration」を手順（チケットを入れる先・既定の勧め）とカンバンの既定の選択が同じ 1 つに決められるようにするため。複数を許すと、前の Iteration を閉じ忘れたまま次を始めたときに古い方が既定になる。閉じ忘れは拒否で気づかせ、どちらを閉じるかは人が決める

## 採らなかった案

- **Epic をチケットの一種にする**（`type: epic` と `parent`）：claim・カンバン・照合に例外が入る
- **Epic や Iteration 側にチケットの一覧を持つ**：チケット側と二重の正本になり、食い違いと push の衝突が起きる
- **ラベルで Epic を代用する**：目的の本文・進捗・閉じる操作を表せない
- **Milestone を置く**：Iteration と役割が重なり、データモデルが増えるだけ
- **active を複数許し、画面と手順が選ぶ**：「今の Iteration」が人と画面と手順で食い違う。並行の作業は 1 つの Iteration の中で表せる
- **Epic の閉じる・再開の既定を `human_only` にする**：人が頼んだ操作をエージェントが実行できない。人に限りたいカンバンは値を書き換える
- **閉じる・再開する制限を config のコマンド名の一覧（`actor.human_only`）に置く**：拒否の 2 値しか書けず、Status の動きの権限と書く場所が分かれる
- **Iteration を閉じる・再開するのを dg では判定せず、人の指示があるときだけ行う規約にとどめる**：守るかが LLM 次第で、人の承認で任せる形も書けない
- **予定の開始日・終了日を持ち、超過を案内する**：予定は実際とずれ、始めた日・閉じた日に書き換える規則と超過の判定が増えるだけで、閉じる判断は日付でなく中身で決まる
