# ADR-003 ステータスとワークフロー

- ステータス：承認

## 要約

チケットの Status は todo・in_progress・review・done と、やめた場合の終端 abandoned の 5 つに固定する。Workflow はカンバンに 1 つ（`workflow.yaml`）で、状態の表示名と、境目・例外の動き・流れの段階・カンバンの管理ごとの方針（越える条件と、決める人の権限の値）を書く。Run の step の語彙と `workflow set` の決まりは Core が固定で持つ。

## 背景

同じソフトウェア開発でも、チームやリポジトリごとに進め方（見直しの有無・承認する人など）が違うので、利用者が進め方を決められる必要がある。一方で、何でも書ける宣言的エンジンは実装が重く、AI エージェントとの対話を硬直させる。人とエージェントの分担を決める設定が、遷移・step・コマンド名と別々の単位で散らばると、どれが本当に止まるのかが設定した人に見えない。ステータスを固定するか、Workflow をどの単位で持ち、何を書かせるかを決める。

## 決定

### Status は 5 つに固定する

チケットの進捗は `status` の 1 軸で表し、値は 5 つに固定する。前進の順は todo → in_progress → review → done で、`abandoned` は前進の軸の外の終端（WF-1）。

- Workflow は Status を増やせない。表示名（`states` の `label`）だけを変えられる
- 工程（調査・実装・テストなど）はチケットの属性にしない。Run が `step` を持ち、「チケットがどこまで進んだか」と「Run が何をしたか」を分ける

### Workflow はカンバンに 1 つにする

- Workflow はカンバンに 1 つの `workflow.yaml` で、チケットには紐づけない。進め方が違う仕事はカンバンを分ける（ADR-034）
- 同梱するのは既定の `workflow.yaml` を 1 つだけにする。PR を使う進め方も使わない進め方も同じ既定で動き、進め方の違いは値を書き換えて表す
- どの項目も省け、省いた項目は同梱の既定と同じ Core の既定になる。ファイルがなくても同じに動く

### 状態と境目の方針の枠組みで書く

`workflow.yaml` に書くのは、状態と、場面ごとの方針だけ。項目の一覧と形は requirements の 5.8 と Zod のスキーマ（`core/model/workflow.ts`）、既定の値は `core/workflow/resolve.ts` が正本。

- `states`：5 つの Status の表示名
- `boundaries`：前へ進む隣どうしの 3 つの境目ごとの、越える条件と、決める人の権限の値。境目は増やせない
- `exceptions`：流れの外の動きの権限の値。名前で書き、`from`・`to` は書かせない
- `wip`：列ごとの上限。最初の版は着手を拒否しない。人の見直しや承認を待つ列が埋まるだけで作業が止まらないよう、拒否より先の列を進める案内を選ぶ（振る舞いは WF-8）。config の `work.parallel` は同時に動かすサブエージェントの数で、流れの上限とは目的が違うので別に持つ
- `flow`：流れの段階ごとの権限の値
- `governance`：カンバンの管理の操作ごとの権限の値

権限の値は、どの場面も同じ 1 つの語彙で書く（値は `core/model/workflow.ts` の `DECISIONS`）。条件は組み込みの事実とその否定だけ（WF-2）。

書かないもの：

- 手続き（何をどの順で行うか、条件分岐、失敗時の処理）。既定の手続きは Core が持つ（ADR-011）
- 利用者のスクリプト
- Run の step の語彙と、Run を開く操作

### 遷移は既定で自由にし、Workflow が制約を足す

- 既定ではどの遷移も human / agent / reconcile の誰でも条件なしで行える。Core が固定するのは Status の集合と前進の順、同じ Status への move の拒否、遷移の副作用だけ（ST-2・ST-8）
- Workflow の `transitions` は遷移ごとに主体（`by`）と条件（`requires`）の制約を足す（WF-1）
- 照合（reconcile）は遷移の制約とは別の仕様で、前進の順に進めるだけ（ST-4）。`by` に `reconcile` を含まない遷移は照合でも止まる

### Core が固定で持つもの

`workflow.yaml` では緩められない決まりは Core が持つ。

- Run の step の語彙（investigate・implement・review・fix・merge）と、Run を開く操作（agent の claim は implement、もう一度の claim は fix）。`dg run start` は語彙にない step を拒否する
- `dg workflow set`（Workflow の変更）は、いつも人の承認が要る。エージェントは人の承認を `--approved-by` で記録して呼ぶ
- `workflow set` は書く前に読み込み時と同じ検証をし、誤りがあれば何も書かない（WF-6）

## 理由

- Status を固定すれば、UI・CLI・照合・集計を 1 つの実装で書け、進め方ごとの差を吸収する層が要らない
- `abandoned` を終端として持つのは、「やめた」を done と混ぜると完了件数と実績が歪み、削除すると経緯が消えるため
- Status と工程を独立した 2 軸にすると、遷移表が積になり、カンバンの列も決まらない。必要なのは「チケットの進捗」と「Run が何をしたか」の区別で、後者は Run の属性で足りる
- Workflow をカンバンに 1 つにするのは、Workflow がチケットごとに付くと、Iteration を閉じる・起票する・設定を変えるといったチケットの外の判断を決める場所がないため。列の上限も流れの段階も、カンバンの単位でしか意味を持たない
- 方針を状態と境目の単位で書くのは、利用者が進め方を考える単位（どの列からどの列へ、誰が決めるか）と合わせるため。遷移・step・コマンド名と単位がばらばらだと、どれが止まるのかが読めない
- 同梱を 1 つにするのは、テンプレートごとの差が照合の規則と step の語彙だけで、どちらも 1 つの既定で両方の進め方を覆えるため。選ぶ手間と、選んだ後に同梱の更新が届かない写しをなくせる
- 項目を省けるようにするのは、変えたい値だけを書いたファイルが、既定が変わったときも残りの既定に追従するため
- step の語彙を Core が持つのは、書き換えない `runs/` の集計（ADR-029）に表記の揺れを残さず、フックと `dg next` が同じ名前で Run を開いて探せるようにするため
- `workflow set` にいつも人の承認を求めるのは、Workflow が人とエージェントの分担そのものを決めるので、エージェントが自分の権限を自分で広げられないようにするため。Workflow の中の値にすると、その値を書き換えて外せる
- 条件を組み込みの事実に限るのは、照合が全員のマシンで走るため
- `workflow set` が書く前に検証するのは、誤った定義は使われず、遷移と照合が止まるため
- 遷移を既定で自由にするのは、望ましい遷移が業務で違う（レビューを経ない作業、やり直し、やめる判断）ため

## 採らなかった案

- **チケットごとに Workflow を選ぶ**（`workflows/<id>.yaml` と、チケットの `workflow`・config の `default_workflow`）：チケットの外の判断（Iteration・起票・設定）を決める場所がなく、列の上限と流れの段階を持てない。進め方が違う仕事はカンバンを分ければ足りる
- **チケットに利用者が定義する任意フィールドを持たせる**（Workflow の `fields` と `--field`）：1011 件のチケットで 1 件も使われず、型の検査と画面の入力欄だけが残った。束ねるのは Epic・Iteration・ラベルで足りる
- **`workflow set` を人だけにする**：人が頼んだ変更もエージェントが書けず、人が YAML を手で直すことになる。承認者の記録が残れば、エージェントが黙って権限を広げることは防げる
- **業務ごとのテンプレートを同梱する**：差は 1 つの既定で覆え、選んだ写しに同梱の更新が届かない
- **ワークフローごとに Status を定義し、category で抽象化する**：UI・CLI・照合に category を介す層が増える。段階の違いは 5 つで覆える
- **Status と工程の 2 軸**：遷移表が積になり、カンバンの列も決まらない
- **step の語彙を Workflow に書かせる**：Run の集計に表記の揺れが残り、Run を開く操作と探す側が名前を引き直す
- **Core が固定の遷移表を持ち、Workflow は狭めるだけ**：一律の拒否が業務に合わず、YAML で緩める手段がない
- **手続きまで YAML に書く**：対話が硬直し、手順の変更のたびにスキーマが変わる
- **条件にユーザーのスクリプトを許す**：全員のマシンで走り、安全性と再現性が落ちる
- **受け入れ条件のチェックを遷移の条件にする**：マージ済みなのに done にならないチケットが残る。照合の `sync` の警告にとどめる
- **Iteration に入れることを遷移の条件（`requires`）にする**：受け入れ条件と同じく照合の遷移が止まる。`lint.require_iteration` の指摘にとどめる
- **`abandoned` を持たず削除で表す**：経緯と実績が消える
