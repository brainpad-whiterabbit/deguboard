# ADR-003 ステータスとワークフロー

- ステータス：承認
- 更新日：2026-10-31

## 背景

deguboard はソフトウェア開発だけでなく、コンサルティングや調査などの業務にも使う。業務ごとにステータスや工程が違うので、ユーザーがワークフローを定義できる必要がある。一方で、何でも書ける宣言的エンジンは実装が重く、AI エージェントとの対話を硬直させる。ワークフロー定義に「何を書かせ、何を書かせないか」を決める。

## 決定

### Status は 1 軸、category を持つ

- チケットの進捗は `status` の 1 軸で表す。Status の集合はワークフローごとに定義する
- 各 Status は `category`（`todo` / `active` / `review` / `done`）を持つ。UI と CLI は Status の名前ではなく category で動く（カンバンの列の並び、「done になった件数」、照合の「前進」の判定）
- 工程（Stage）はチケットの属性にしない。Phase 3 で Run に `step`（planning / implementation / review …）を持たせ、「チケットがどこまで進んだか」と「Run が何をしたか」を分ける

### Workflow YAML は制約と語彙を書く

ワークフロー定義（`workflows/<id>.yaml`）に書くもの：

- `statuses`：id・label・category の並び。並びがカンバンの列の順と「前進」の基準
- `transitions`：許される遷移。`from`・`to`・誰が行えるか（human / agent / reconcile）・`requires`（組み込みの条件）
- `reconcile`：Git の事実から状態を導く規則。上から評価し、前進するときだけ書き換える
- `fields`：チケットに追加する任意フィールド（UI の表示項目が追従）
- Phase 3 で `steps`（Run の step の語彙）と、各 step で使える Action・承認の要否を足す

書かないもの：

- 手続き（何をどの順で行うか、条件分岐、失敗時の処理）。手順は `dg guide <topic>` のテキストとして CLI に同梱し、AI が読んで判断する
- ユーザーのスクリプト。`requires` と `reconcile` の条件は組み込みの事実（`deps_done`、`branch_exists`、`branch_merged`、`pr_open` など）とその否定だけ

### 表にない遷移は拒否する

- `dg ticket move` と UI からの変更は、Core が遷移表と `requires` を検査する。表にない遷移は受け付けない
- 定義の検証（存在しない Status を指す遷移、category の欠け、未知の条件）は `dg workflow validate` と読み込み時に行う

### テンプレート

`software-development`・`consulting`・`general` の 3 つを CLI に同梱し、`dg init --template` でコピーする。利用者はコピーを編集する。

### Milestone は置かない

MVP では Milestone を持たない。期間の計画は Iteration で表す。必要になったら Iteration の属性として足す。

## 理由

- Status と Stage を独立した 2 軸にすると、遷移表が積になり、カンバンがどちらの軸で列を作るかも決まらない。実際に必要なのは「チケットの進捗」と「Run が何をしたか」の区別で、後者は Run の属性で足りる
- category があれば、ステータス名が業務ごとに違っても、UI と CLI と照合を 1 つの実装で動かせる。これが汎用性の要
- 状態遷移・承認・排他・記録はプログラムで保証し、要件整理・分解・実装方針・レビュー判断は AI に任せるのが、再現性と柔軟さの両方を保つ境界。Workflow YAML を「制約と語彙」に限れば、エンジンは遷移表の検査と照合だけで済み、手順は AI が文脈に合わせて解釈できる
- 条件を組み込みの事実に限るのは、照合が全員のマシンで走るため。利用者のスクリプトを走らせると安全性と再現性が落ちる
- 表にない遷移を拒否すれば、依存が終わっていない着手やマージ前の完了を作れない

## 採らなかった案

- **Status と Stage の 2 軸**：遷移表が積になる。上記
- **手続きまで YAML に書く**（step ごとの実行フロー・分岐・失敗時処理）：再現性は上がるが対話が硬直し、エンジンの実装量が増える。手順の変更のたびに YAML のスキーマを変えることになる
- **条件にユーザーのスクリプトを許す**：全員のマシンで走る。安全性と再現性が落ちる
- **Status を固定の 4 段階にする**：ソフトウェア開発以外で使えない
- **Milestone を MVP に含める**：Iteration と役割が重なり、データモデルが増えるだけ
