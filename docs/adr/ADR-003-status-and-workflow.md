# ADR-003 ステータスとワークフロー

- ステータス：承認
- 更新日：2026-10-31

## 背景

deguboard はソフトウェア開発だけでなく、コンサルティングや調査などの業務にも使う。業務ごとに工程が違うので、ユーザーがワークフローを定義できる必要がある。一方で、何でも書ける宣言的エンジンは実装が重く、AI エージェントとの対話を硬直させる。ステータスを固定するか、ワークフロー定義に何を書かせるかを決める。

## 決定

### Status は 5 つに固定する

チケットの進捗は `status` の 1 軸で表し、値は全ワークフロー共通の 5 つに固定する。

| status        | 意味                       | 前進の順 |
| ------------- | -------------------------- | -------- |
| `todo`        | 未着手                     | 1        |
| `in_progress` | 作業中（claim 済み）       | 2        |
| `review`      | 確認待ち                   | 3        |
| `done`        | 完了。終端                 | 4        |
| `abandoned`   | やめた。終端。前進の軸の外 | -        |

- ワークフローは Status を増やせない。表示名（label）だけを変えられる
- 工程（調査・実装・テストなど）はチケットの属性にしない。Phase 3 で Run に `step` を持たせ、「チケットがどこまで進んだか」と「Run が何をしたか」を分ける。工程をチケットに表示したいだけなら Workflow の `fields` で任意フィールドを足す

### 遷移表は Core が持つ

| from                        | to          | 誰が                      | 備考                              |
| --------------------------- | ----------- | ------------------------- | --------------------------------- |
| todo                        | in_progress | human / agent             | claim。依存が done でなければ拒否 |
| in_progress                 | review      | human / agent / reconcile |                                   |
| review                      | in_progress | human                     | 差し戻し                          |
| review                      | done        | human / reconcile         |                                   |
| in_progress                 | done        | human                     | レビューを要しない作業            |
| todo / in_progress / review | abandoned   | human                     | claim を外す                      |
| abandoned / done            | todo        | human                     | 再開                              |

- 表にない遷移は拒否する。照合（reconcile）は前進の順に進めるだけで、`abandoned` と `done` には触れず、そこからも動かさない
- ワークフローは組み込みの遷移に `requires`（組み込みの条件）を足すか、`by` を狭める（例：review → done を human だけにする）ことができる。遷移を増やしたり外したりはできない

### Workflow YAML は制約と語彙を書く

ワークフロー定義（`workflows/<id>.yaml`）に書くもの：

- `labels`：Status の表示名（任意）
- `transitions`：組み込みの遷移に足す `requires` と `by` の絞り込み（任意）
- `reconcile`：Git の事実から状態を導く規則。上から評価し、前進するときだけ書き換える
- `fields`：チケットに追加する任意フィールド（UI の表示項目が追従）
- Phase 3 で `steps`（Run の step の語彙）と、各 step で使える Action・承認の要否を足す

書かないもの：

- 手続き（何をどの順で行うか、条件分岐、失敗時の処理）。手順は `dg guide <topic>` のテキストとして CLI に同梱し、AI が読んで判断する
- ユーザーのスクリプト。`requires` と `reconcile` の条件は組み込みの事実（`deps_done`、`branch_exists`、`branch_pushed`、`branch_merged`、`pr_open`、`pr_draft`、`pr_merged`）とその否定だけ

定義の検証（存在しない Status や遷移を指す項目、未知の条件）は `dg workflow validate` と読み込み時に行う。

### テンプレート

`software-development`・`consulting`・`general` の 3 つを CLI に同梱し、`dg init --template` でコピーする。違いは `reconcile`・`fields`・`labels`（Phase 3 からは `steps`）で、Status は共通。

### Epic は置き、Milestone は置かない

- Epic は目的ごとにチケットを束ねる独立したエンティティ（`epics/e3.md`）。チケットの一種にはせず、claim・ブランチ・5 つの Status を持たない
- 状態は `open` / `closed` で、閉じる・再開は人だけが行う。進捗はチケットの状態から都度求め、保存しない
- 所属はチケット側の `epic` で表し、Epic 側に一覧を持たない。入れ子にせず、Iteration をまたぐ。チケットの遷移は縛らない
- Milestone は持たず、期間の目標は Iteration で表す

## 理由

- Status を固定すれば、UI・CLI・照合・集計を 1 つの実装で書け、ワークフローごとの差を吸収する層（category のような抽象）が要らない。業務の違いは工程（Run の step）と照合規則と任意フィールドで表せ、進捗の段階そのものは 5 つで覆える
- `abandoned` を終端として持つのは、「やめた」を done と混ぜると完了件数と実績が歪み、削除すると経緯が消えるため
- Status と工程を独立した 2 軸にすると、遷移表が積になり、カンバンがどちらの軸で列を作るかも決まらない。実際に必要なのは「チケットの進捗」と「Run が何をしたか」の区別で、後者は Run の属性で足りる
- 状態遷移・承認・排他・記録はプログラムで保証し、要件整理・分解・実装方針・レビュー判断は AI に任せるのが、再現性と柔軟さの両方を保つ境界。Workflow YAML を「制約と語彙」に限れば、エンジンは遷移表の検査と照合だけで済み、手順は AI が文脈に合わせて解釈できる
- 条件を組み込みの事実に限るのは、照合が全員のマシンで走るため。利用者のスクリプトを走らせると安全性と再現性が落ちる
- 表にない遷移を拒否すれば、依存が終わっていない着手やマージ前の完了を作れない
- Epic（目的の範囲）・Iteration（期間）・Plan（実行順）は役割が違うので別のエンティティにする。進捗を保存しないのは、チケットを動かすたびに Epic も書き換えて衝突させないため

## 採らなかった案

- **ワークフローごとに Status を定義し、category で抽象化する**：UI・CLI・照合が category を介して動く層が増える。名前の違いは `labels` で足り、段階の違いは 5 つで覆える
- **Status と工程の 2 軸**：遷移表が積になる。上記
- **手続きまで YAML に書く**（step ごとの実行フロー・分岐・失敗時処理）：対話が硬直し、エンジンが増え、手順の変更のたびにスキーマが変わる
- **条件にユーザーのスクリプトを許す**：全員のマシンで走る。安全性と再現性が落ちる
- **`abandoned` を持たず削除で表す**：経緯と実績が消える
- **Epic をチケットの一種にする**（`type: epic` と `parent`）：claim・カンバン・照合に例外が入り、Status を固定した利点が薄れる
- **Epic に 5 つの Status を使う**：「作業中」「確認待ち」が Epic に意味を持たない
- **Epic 側にチケットの一覧を持つ**：チケットの `epic` と二重の正本になり、push が衝突する
- **ラベルで Epic を代用する**：目的の本文・進捗・閉じる操作を表せない
- **Milestone を MVP に含める**：Iteration と役割が重なり、データモデルが増えるだけ
