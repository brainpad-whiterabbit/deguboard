# ADR-003 ステータスとワークフロー

- ステータス：承認

## 要約

チケットの Status は todo・in_progress・review・done と、やめた場合の終端 abandoned の 5 つに固定する。Workflow はカンバンに 1 つ（`workflow.yaml`）で、状態の表示名と、境目・例外の動き・流れの段階・カンバンの管理ごとの方針（越える条件と、決める人の権限の値）を書く。Run の step の語彙と照合のきっかけと `workflow set` の決まりは Core が固定で持つ。

## 背景

チームやリポジトリごとに進め方（見直しの有無・承認する人など）が違うので、利用者が進め方を決められる必要がある。一方で、何でも書ける宣言的エンジンは実装が重く、AI エージェントとの対話を硬直させる。人とエージェントの分担を決める設定が、遷移・step・コマンド名と別々の単位で散らばると、どれが本当に止まるのかが設定した人に見えない。

## 決定

### Status は 5 つに固定する

チケットの進捗は `status` の 1 軸で表し、値は 5 つに固定する。前進の順は todo → in_progress → review → done で、`abandoned` は前進の軸の外の終端（WF-1）。

- Workflow は Status を増やせない。表示名（`states` の `label`）だけを変えられる
- 工程（調査・実装・テストなど）はチケットの属性にしない。Run が `step` を持ち、「チケットがどこまで進んだか」と「Run が何をしたか」を分ける

### Workflow はカンバンに 1 つにする

- Workflow はカンバンに 1 つの `workflow.yaml` で、チケットには紐づけない。進め方が違う仕事はカンバンを分ける（ADR-034）
- 同梱するのは既定の `workflow.yaml` を 1 つだけにする。PR を使う進め方も使わない進め方も同じ既定で動き、違いは値を書き換えて表す
- どの項目も省け、省いた項目は Core の既定になる。ファイルがなくても同じに動く

### 状態と境目の方針の枠組みで書く

`workflow.yaml` に書くのは、状態と、場面ごとの方針だけ。項目の一覧と形は requirements の 5.8 と Zod のスキーマ（`core/model/workflow.ts`）、既定の値は `core/workflow/resolve.ts` が正本。

- `states`：5 つの Status の表示名
- `boundaries`：前へ進む隣どうしの 3 つの境目ごとの、越える条件と、決める人の権限の値。境目は増やせない
- `exceptions`：流れの外の動きの権限の値。名前で書き、`from`・`to` は書かせない
- `wip`：列ごとの上限。最初の版は着手を拒否しない。人の見直しや承認を待つ列が埋まるだけで作業が止まらないよう、拒否より先の列を進める案内を選ぶ（振る舞いは WF-8）。config の `work.parallel` は同時に動かすサブエージェントの数で、目的が違うので別に持つ
- `flow`：流れの段階ごとの権限の値と、プロジェクト独自の段階（[ADR-030](ADR-030-flow-and-guide-in-core.md)）
- `governance`：カンバンの管理の操作ごとの権限の値（操作は WF-7）

権限の値は、どの場面も同じ 1 つの語彙で書く（下の節）。条件は組み込みの事実とその否定だけ（WF-2）。手続き（順・分岐・失敗時の処理。Core が持つ、ADR-011）、利用者のスクリプト、Run の step の語彙と Run を開く操作、照合のきっかけは書かない。

### Status の変更は、境目と例外の動きの方針で判定する

- 前へ進む操作は、越える境目の `requires`（越える条件）と `decide`（権限の値）で判定する。`decide` は境目を越えるすべての操作（claim・PR を出す操作・`pr merge`・手の move）に同じ値を当てる。境目を飛ばす動きは間の境目をすべて越えたものとし、厳しいほうの値が効く。着手の `decide` の既定は `ask_unless_auto`
- `requires` は越える条件で、きっかけではない。満たしても自動では進まず、満たさずに手で越える操作は拒否する。事実を作る操作（`pr merge`）は `decide` だけで判定し、Status を進めるのは事実を見た照合
- 照合（reconcile）は、越える境目の `requires` と `decide` をエージェントの側として判定し、`human_only` では止まり、人の承認を求める値では止まらない。進めなかったチケットは `sync` が理由を警告する
- ブランチなしで着手したチケットにはブランチと PR の事実の条件を、PR のないチケットの照合には PR の事実の条件を当てない。手で越える操作と着手していない todo には当てたままにする（範囲は `core/workflow/resolve.ts` の `requiresForTicket` と `core/workflow/reconcile.ts`）
- 前へ進まない動きは `exceptions`（`abandon`・`reopen`・`back`）の値で判定し、`abandon` と `reopen` の既定は `always_ask`
- 書き込みの操作は、Core の固定・`exceptions`・`boundaries`・`flow`・`governance` のうち最初に当てはまったものの値で判定し、行き先はコマンドの名前と引数だけで決まる。順と操作の対応は `core/workflow/resolve.ts` の `operationPolicy` が正本。Core の固定は [ADR-026](ADR-026-guard-pr-and-data.md)、`flow` と `--auto` は [ADR-030](ADR-030-flow-and-guide-in-core.md)

### 権限の値は 5 つで、承認と強制を記録する

値は `human_only`・`always_ask`・`ask_unless_auto`・`anyone`・`agent_only` の 5 つ。人・エージェント・聞かずに進める流れのエージェントのそれぞれに何を許すかの表は [usage の「What the values mean」](../usage.md#what-the-values-mean) と `core/workflow/conditions.ts` が、方針の引き方は `core/workflow/resolve.ts` が、拒否の文と記録は `core/commands/permission.ts` が正本。

- 照合はエージェントと同じ側に数える。聞かずに進める流れは `--auto` で伝え、効くのは `ask_unless_auto` の場面だけ（[ADR-030](ADR-030-flow-and-guide-in-core.md)）
- 人の承認は、エージェントが `--approved-by <人>` を付けて渡し、dg は承認者を記録する。人の指示は承認とみなす。人の強制は `--override "理由"` で渡し、`agent_only` と満たさない `requires` を越えられるのは人だけで、履歴に残す
- 権限は誤操作を防ぐ手すりで、安全の壁ではない。dg は主体を自己申告（`--actor`）で知るので、申告を偽る呼び出しと dg を経由しない操作は止められない。それを止めるフック（AG-10、ADR-026）は権限の値があっても要る

### Core が固定で持つもの

`workflow.yaml` では緩められない決まりは Core が持つ。

- Status の集合と前進の順、3 つの境目、遷移の副作用（ST-8）
- Run の step の語彙と Run を開く操作（語彙は `dg run start --help`）
- 照合のきっかけ（ブランチ・PR・マージの事実。正本は `core/workflow/reconcile.ts` と `dg sync --help`）。`workflow.yaml` に照合の規則は書けない
- `dg workflow set` は、いつも人の承認が要り、書く前に検証して誤りがあれば何も書かない（WF-6）

## 理由

- Status を固定すれば、UI・CLI・照合・集計を 1 つの実装で書け、進め方ごとの差を吸収する層が要らない
- `abandoned` を終端として持つのは、「やめた」を done と混ぜると完了件数と実績が歪み、削除すると経緯が消えるため
- 工程を Status と別の軸にすると遷移表が積になり、カンバンの列も決まらない。「Run が何をしたか」は Run の属性で足りる
- Workflow をカンバンに 1 つにするのは、チケットごとに付くと、Iteration を閉じる・起票する・設定を変えるといったチケットの外の判断を決める場所がないため。列の上限も流れの段階も、カンバンの単位でしか意味を持たない
- 方針を状態と境目の単位で書くのは、利用者が進め方を考える単位（どの列からどの列へ、誰が決めるか）と合わせるため
- 同梱を 1 つにするのは、進め方の差が照合のきっかけと step の語彙だけで、どちらも 1 つの既定で覆えるため。選んだ写しに同梱の更新が届かない問題もなくせる。項目を省けるのは、変えたい値だけを書いたファイルが、既定の変更に追従するため
- step の語彙を Core が持つのは、書き換えない `runs/` の集計（ADR-029）に表記の揺れを残さず、フックと `dg next` が同じ名前で Run を開いて探せるようにするため
- `workflow set` にいつも人の承認を求めるのは、Workflow が分担そのものを決めるので、エージェントが自分の権限を広げられないようにするため。Workflow の中の値にすると、その値を書き換えて外せる。書く前に検証するのは、誤った定義では遷移と照合が止まるため
- 条件を組み込みの事実に限るのは、照合が全員のマシンで走るため
- 条件（`requires`）と決める人（`decide`）を分けるのは、1 つの欄に兼ねさせると「人が手で done にしない」を書こうとして `pr merge` まで縛るため。`decide` を境目の単位にするのは、同じ境目を別の操作で越える抜け道をなくすため。飛ばす動きに間の境目を効かせるのも同じ理由
- 権限の値を 1 つの語彙にするのは、どの場面も同じ表で「止まるか・聞くか・通るか」を読めるようにするため。承認を引数で受けて記録するのは、エージェントが人に聞いたかを dg は確かめられないので、聞かずに進めた操作と区別できる跡を残すため
- ブランチなしの着手と PR のないチケットの照合でブランチ・PR の事実の条件を外すのは、PR の要らない作業や PR を使わない進め方が、既定の `requires: [pr_merged]` のままでは done にできないため。`requires` は AND だけで `workflow.yaml` では書き分けられず、画面の Status の選択は `--override` を渡せない。手で越える操作に当てたままにするのは、「人が手で done にしない」を保つため
- 照合のきっかけを Core に固定するのは、PR を使わない進め方でも、ブランチのマージという同じきっかけで done に進むため。進め方の違いは境目の `requires` だけで書け、きっかけと条件が食い違う定義を書けなくなる
- 照合が人の承認を求める値で止まらないのは、照合は人に聞けず、その判断は事実を作る操作（`pr ready`・`pr merge`）が `decide` で済ませているため。止めると、既定でマージ済みの PR が done に進まない。`human_only` だけで止めるのは、エージェントが越えない境目を、同じ側の照合も越えないようにするため。PR のないチケットのブランチのマージは `decide` で判定しないが、dg の外のマージと同じに受け入れる
- `abandon` と `reopen` の既定を `always_ask` にするのは、どちらも人の指示を受けたエージェントが実行する動きで、`human_only` では人が打ち直すことになるため。承認者の記録なしには進まないので、聞かずにやめる・戻すことは防げる
- 着手の既定を `ask_unless_auto` にするのは、着手は排他を取ってブランチと worktree を作るので、頼まれていない着手がほかの人の作業をふさぐため。チケットを進める指示と Plan の承認は着手の承認に数えるので、頼まれた作業で聞き直すことは増えない
- `agent_only` を持つのは、事実で表せない境目（PR を使わない進め方の review → done など）で人の誤操作を防ぐため。人が要るときに止まらないよう、理由を残す強制を用意する

## 採らなかった案

- **チケットごとに Workflow を選ぶ**（`workflows/<id>.yaml` と `default_workflow`）：チケットの外の判断を決める場所がなく、列の上限と流れの段階を持てない。進め方が違う仕事はカンバンを分ければ足りる
- **チケットに利用者が定義する任意フィールドを持たせる**（`fields` と `--field`）：1011 件のチケットで 1 件も使われなかった。束ねるのは Epic・Iteration・ラベルで足りる
- **`workflow set` を人だけにする**：人が頼んだ変更もエージェントが書けない。承認者の記録で、黙って権限を広げることは防げる
- **業務ごとのテンプレートを同梱する**：差は 1 つの既定で覆え、選んだ写しに同梱の更新が届かない
- **ワークフローごとに Status を定義し、category で抽象化する**：UI・CLI・照合に category を介す層が増える
- **step の語彙を Workflow に書かせる**：Run の集計に表記の揺れが残る
- **Core が固定の遷移表を持ち、Workflow は狭めるだけ**：一律の拒否が業務に合わず、緩める手段がない
- **遷移ごとに主体と条件を書く**（`transitions` の `by`・`requires`）：20 通りの遷移を 1 つずつ縛ることになり、飛ばす動きに抜けが残る
- **境目の `exit` に条件ときっかけを兼ねさせる**：依存が終わっただけのチケットが in_progress に進む
- **照合の規則を Workflow に書かせる**（`reconcile`）：進め方ごとの差がなく、境目の `requires` と食い違う規則を書ける
- **照合を、人の承認を求める値でも止める**：既定でマージ済みの PR が done に進まなくなる
- **照合に `decide` を当てない**：`human_only` の境目を、エージェントの `sync` が越える
- **PR の要らない作業の done を、人の `--override` に任せる**：手順のたびに人がコマンドを打ち、画面からは越えられない
- **`abandon` と `reopen` の既定を `human_only` にする**：人が頼んだ変更をエージェントが実行できない
- **着手の既定を `anyone` にする**：頼まれていないチケットを聞かずに始められ、承認者が残らない
- **強制の引数を `--force` にする**：`skill install --force` などで「上書きする」の意味に使っている
- **段（`gate`）ごとに権限の値を変える**：最初の版では持たない
- **手続きまで YAML に書く**：対話が硬直し、手順の変更のたびにスキーマが変わる
- **条件にユーザーのスクリプトを許す**：全員のマシンで走り、安全性と再現性が落ちる
- **受け入れ条件のチェックを遷移の条件にする**：マージ済みなのに done にならないチケットが残る。`sync` の警告にとどめる
- **Iteration に入れることを遷移の条件にする**：照合の遷移が止まる。`lint.require_iteration` の指摘にとどめる
- **`abandoned` を持たず削除で表す**：経緯と実績が消える
