## Summary

全体のテストを速くし、件が増えても時間が件数に比例して伸びないようにする。事実（ブランチ・PR・Run の記録）から結果を決める判定を、git・gh を読まない純粋な関数に分けて組み合わせを網羅し、本物の git を通す結合テストは経路の代表に絞る。

### 測った値（2026-11-17、main ae436adf、8 CPU、vitest のワーカー 4）

- `mise run check` は 150 秒で、うちテストが 144 秒。151 ファイル・2,430 件、ファイルごとの時間の合計は 494 秒（s40 の前は 564 秒）
- 上位 10 ファイルで 223 秒（合計の 45%）。merge.test.ts 31.9 秒、commands-flow-reconcile.test.ts 28.9 秒、pr.test.ts 26.1 秒、run.test.ts 21.3 秒、orphan-review.test.ts 21.3 秒、hook.test.ts 20.2 秒、commands-flow-ticket.test.ts 19.4 秒、commands-flow-reclaim.test.ts 19.4 秒、commands-data-remote.test.ts 18.0 秒、commands.test.ts 16.2 秒
- テストの時間は dg のコマンドを何回呼ぶかでほぼ決まる。コマンド 1 回が起動する git の回数（一時リポジトリ、データのリモートあり／なし）は init 26／23、ticket claim 23／18、sync 23／16、ticket create 19／14、ticket update 10／10、ticket show 7／7
- 上位 10 ファイルを単独で回すと git の起動は合わせて 31,627 回。回数の 53% は rev-parse と status の問い合わせ、git のプロセスの時間の 33% は fetch・rebase・push の同期

### 方針（テストの 3 つの層）

- 判定のテスト：事実の型を組んで決める関数を呼ぶ。組み合わせはここで網羅する（`packages/core/src/commands/flow.test.ts` の `facts({...})` から 1 つだけ変える形、`packages/core/src/workflow/workflow.test.ts` の表の形）
- 事実の読み取りのテスト：git・gh の状態から事実の型が正しく作れるかを本物の git で確かめる（`packages/core/src/git/facts.test.ts` の形）
- 経路のテスト（結合）：集める → 決める → 行う が通るか、push・lock・競合・gh の引数・記録の形を、経路ごとに代表 1〜2 件で確かめる。準備は雛形（`createFixtureFrom`）から写す。判定の組み合わせは結合テストで足さない

遷移の判定（`reconcileStatus`）と許可の判定（`judgeDecisions`・`operationPolicy`）はすでに純粋な関数。読む・決める・書くが 1 つの関数の中で混ざっているのは、ゲート（`judgeGate`）、照合の中で Run を閉じる処理（`reconcileAll`）、claim と reclaim、保留の見直しの数え方（`orphanReviewRuns`）。重い 5 ファイル（reconcile・reclaim・pr・gate・orphan-review）の約 130 件のうち、50〜70 件が判定のテストに移せる見当。

### 効きの見込み（見積もり。測っていない）

- 判定の層を分けるだけで、ファイルの時間の合計が約 33 秒、経過時間が 8〜10 秒縮む
- 1 件ごとの dg init をやめて雛形から写すことと合わせて、経過時間が 20〜25 秒縮む（150 秒が 125〜130 秒に）
- これから足す判定の組み合わせは 1 件 1 ms 未満で足せる（今は重いファイルで 1 件 1〜2 秒）

進め方：雛形への寄せ（独立）と、ゲートの切り出しで形を決め、規約にしてから、保留の見直し → 事実の導出 → 照合の Run の閉じ方 → claim と reclaim へ進める。各チケットは、前後の時間を PR に載せる。
